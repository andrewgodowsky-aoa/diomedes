## Automations — stable meanings and truthful state

An Automation is a versioned recurring/event-driven responsibility, not an Agent, model, Task or individual run. Its definition binds tenant/workspace, explicit Project target, accountable owner, execution-principal reference, pack/procedure revision, trigger, approved inputs/outputs, rules/grant references, permitted hosts/routes, limits, missed-run/overlap policy and verification requirements. References do not contain secrets or replace live authorization.

An occurrence records the trigger, stable identity, configuration revision, observation/deadline, admission or refusal and references to existing tasks/runs. Record skipped, duplicate, expired and deferred triggers even when no run exists. Do not copy an evolving HarnessRun state into a second authoritative lifecycle. Confirm existing equivalents before introducing new modules.

Automations is a first-class Console destination shared by Personal and Business. Business aggregation includes only the locations/projects/evidence the user may inspect. Auto To Do shows concrete tasks; Thread explains an execution; Team organizes workers; Files holds artifacts; Needs you owns decisions. These are linked views over the same records, not competing applications. Manual reusable jobs can appear but must say **Manual — not scheduled**. Inactive schedules, templates and rehearsals do not count as running automation.

Configuration (draft/enabled/paused/archived), present eligibility (host/data/route/authority/budget), authoritative run state, verified business result and human attention are separate facts. Display labels are projections, not stored execution states. Show source/event cursors and observation time; caches are rebuildable and never grant authority. An enabled definition may be blocked; a paused definition may still have a current run; a completed worker may not have a verified outcome.

Pause future runs is not Stop current run. A combined action must show partial completion. Run once uses ordinary admission and cannot bypass unresolved effects, budgets or policy. Editing creates a reviewed revision; in-flight work retains its admitted revision except through an explicitly authorized checkpoint. Resume revalidates live conditions. Archive disables future admissions while preserving evidence. Rollback never restores revoked grants, departed members, credentials, spent budget or old trigger identities.

A saved artifact is not proof of external delivery. Missing/stale/malformed inputs cannot produce a falsely complete or no-change result. A timed-out external effect is uncertain until reconciled, not automatically failed or safe to repeat. Lease fencing protects records, not effects already issued. Reversibility depends on the destination/action; recording before-and-after does not guarantee undo.

Progress uses observed stages and real denominators, never token-count percentages. Health is timestamped and may be unknown. Cloud model access is not an always-on execution host; guaranteed offline alerts require an independent observer. Timezone/DST, catch-up, overlap, queue/deadline, revision-race and duplicate-effect semantics must be explicit and tested. One shared Runtime scheduler feeds current admission; RunService itself is not a scheduler and packs do not create their own executors.

Accountable owner, execution identity, approver and organization owner are distinct. Enforce view/create/edit/enable/run/pause/stop/approve/sensitive-evidence rights at host/API, search/counts, exports, notifications, deep links and subscriptions. Recheck authorization on membership change and before consequential effects. Reassign safely when an employee leaves; never inherit that person's credentials implicitly. Quiet hours affect notification delivery, not safety enforcement; an unreachable reviewer never becomes approval.

Current source-audit boundary: app main 448448683458c2ef813035f344baa79a4c6817bd had manual-only schedule handling and no Automations ShellView. A01–A36 are required acceptance scenarios, not executed tests. Delivery A is existing-job visibility; B is one-host daily/weekly draft scheduling; C is named event paths and scoped production hardening; D is governed templates, remote extensions and measured value. Milestones A and B are implemented in source (2026-09-24): the weekly brief is manual until an owner or admin turns a schedule on, and a Run once press and a due slot are both TriggerOccurrences admitted into RunService by the same admission; labels are pure projections of records (`shared/automations.ts`). C–D remain planned, and nothing here is released.

**Scheduled** means a schedule is turned on, assigned to this computer, and this computer has checked it within the last few minutes; otherwise the label says **Paused**, **Waiting for computer** or **Manual — not scheduled**. A slot that did not start is recorded with its reason — **Missed — computer was off**, **Skipped — paused**, **Skipped — previous run still active** or a **Blocked** reason — and never runs later except the one bounded catch-up. **Turning a schedule on** is an explicit, recorded act by an owner or admin that grants authority for that schedule on that computer against that setup revision; a setup answer, pack activation, configuration change, restart or rollback never turns one on or revives one.

## Agent, Mode, Team and Project

Mode → Agent → Model → Effort expresses controls, not a rigid pipeline. An Agent is a versioned Diomedes-owned worker identity composing existing rules, context, capabilities, permissions, tools, models, evidence and collaboration policies; a Model is replaceable intelligence; Mode is the person's relationship to the work; Team composes Agents. Changes and handoffs never grant authority. Auto/manual selection and runtime-reported origin are retained historically; unknown identity stays unknown.

Diomedes Agent means the native supervisory operation: understand, plan, assemble context, select routes/workers, monitor/correct, obtain required authority, verify and retain progress. Direct-agent mode remains distinct and uses actual runtime attribution. Infrastructure actions may be Diomedes application actions; external reasoning is not renamed Diomedes reasoning.

A Project is the durable general-purpose container for outcomes, Threads/Tasks, context, files/artifacts, capabilities/rules, permissions and evidence. An Agent can work across it rather than being trapped in a Thread. Software repositories and business reports/spreadsheets/SOPs/exports use the same Project contract. Workspace/organization sits above it and owns membership, policy and entitlement.

Task priority is one number a person picks, 1 to 5, with the words 1 Do first, 2 Today, 3 This week, 4 When you can and 5 Backlog. The words are labels only, never deadlines, and they do not change on their own. A due date is a plain calendar date stored as entered. Every actionable work list sorts by priority, then dated before undated and the earliest date first, then when the task became ready. The ready queue uses the same order only inside each project's fair turn, so priority never lets one project jump another. Plan steps, History, conversation turns and messages keep their own order. A task's planning revision counts only priority and due-date edits. Decided 2026-09-25 (QUESTIONS.md R14) for OS01; not built.

Project-only single-agent, standalone Team, temporary workers and Project-plus-Team are supported product requirements. A selected-model lead Agent can plan bounded tasks, inspect workers and integrate verified results. Work must still have an authorized target. ## Work controls, verification and durable records (2026-09-24)

These meanings come from the 2026-09-24 lanes and hold for the source that carries them; roadmap sections 4 and 5 give each one's status.

**Ready queue.** A project's Ready tasks, in the order Diomedes would start them when the project's *Start ready work automatically* switch is on (off by default). A start from the queue is a Work command admitted by the same path as a person's Start and carries no authority Start would not; work that asks for approval stops at its Need. *Pause* stops the queue from starting anything and never stops running work. A task is *held* when it waits for the person's own Start: its engine and documents need their confirmation, the engine is off, or the start path refused it.

**Steer, Queue, Stop, Resume, Retry, Fork.** Six distinct controls on a Work run. *Steer* reaches the running turn and exists only where the route can do that; *Queue* holds a message for after the turn or task, and a route that only holds a message is offered Queue, named as a queue (*queued steering*: held by Diomedes and sent as the next turn of the same native session). *Stop* has three scopes. *Resume* continues a stopped run from its record after re-checking what it would run with, and never with wider authority; *Retry* is a new attempt with the same recorded inputs, linked to the original, blocked while an effect may already have happened; *Fork* starts a new task and thread that refer to a chosen run without changing it. Each leaves a *control receipt*: who asked, what it targeted, what the route did, and who did it — Diomedes for what it composed, the engine for what the route did itself. A *Codex thread* is the app-server thread a ChatGPT Work run used, recorded before its turn is sent and kept for Resume or Fork only when the installed Codex offers them. *Restarted fresh* means the engine could not honour a resume; a new native session or thread starts and the run says earlier messages were not carried.

**Effect record; uncertain effect.** Every harness tool call that could change something leaves an *effect record* written before it runs: which tool, a digest of exactly what it was given, what it may change, its idempotency key, on whose authority, and afterwards what happened. An effect is *uncertain* when Diomedes stopped between the record and the outcome; it is never repeated on a guess, and Retry and Resume wait until the tool's own record or a person says whether it happened.

**Verification result.** A finished run's result is one of four projected states: *Verified* (every declared acceptance check passed, bound to the exact output digests), *Not verified* (no checks declared, or none run — the default), *Failed verification* (a check ran and failed, with its evidence) and *Verification uncertain* (a check could not complete, the reviewer's independence is not shown, the declared checks changed, or bound bytes changed after verification). It is never stored; it is projected from the task's declaration, the verification's History evidence and History's digests. Finished does not mean verified.

**Diomedes work loop.** Work Diomedes itself supervises: a bounded plan, one action per turn through the registered tools and Trust, a recorded observation of each result, optional delegation, and a finish. The finish is the model's claim. A finish that is not Verified leaves the task in Review (*waiting · changes-ready*), even when no checks are declared, and a person or a verifier moves it to done (Andrew, 2026-09-24). Diomedes is named as the supervising actor of the loop's own steps; every model step names the model the runtime reported, and a fixture route names no model.

**Delegate sandbox; change set (Andrew, 2026-09-24; QUESTIONS.md R11, R13).** A delegate, or any helper Diomedes dispatches, works in its own *sandbox*: an isolated working copy of its scope, held in the parent run's own area. Every write and spawn goes through H12 containment rooted at that copy, and it never writes the project directly. When it finishes, its sandbox diff returns to the parent as a recorded *change set*, with P06's readable diff and per-change keep. The parent may apply changes that fall inside its own grant, through the one recorded write path and attributed truthfully. Anything else waits for a person as ordinary review. A helper's grant is the intersection of its parent's grant and the handoff's declared scope, and a helper's action is attributed to its own engine and model. For a loop, delegation is limited to depth 2 and 4 delegates per run, and delegates may run in parallel. A delegate's budget is carved from the parent's remaining budget, never added on top, and Stop cancels the whole tree. Delegate routes come from the project's H09 profiles: the person, or the profile's default, fixes the allowed routes at start, and the model picks among them but never chooses who pays. *Do not hamper*: sandboxing replaces read-only as the safety mechanism, so where it can, the system lets a helper work somewhere safe rather than refusing the work. Not built yet. Delegates and H14 workers are read-only in source today, and the sandbox is H13's next slice.

**Lead, worker, advisor (H14).** A *lead* is a Diomedes work loop admitted with a team. A *worker* is a bounded run the lead hands one task to. It has explicit files, a budget, an Agent and a profile, and never more authority than the lead; it is read-only in this build, until the sandbox lands. An *advisor* is a read-only run the lead asks one question; its answer is evidence under the model that gave it, never a permission. A *handoff* is the durable, append-only record of one such hand-over and how it ended. A worker's answer is a claim, and only the lead's declared checks verify the outcome it fed.

**Supervision (drift).** Diomedes watching a run's records for drift: work outside its selected folder or admitted scope, a loop that makes no progress, a budget pacing to run out, a write an instruction file forbids, or a Verified result the run broke. It answers on a ladder — note, ask the run to correct (a message labelled *Diomedes supervision*), pause and ask you — with corrections bounded. An *escalation* is an ordinary Need only a person answers (continue, redirect, stop); it grants nothing, and continuing re-checks the run as Resume does. Supervision actions are Diomedes application actions, not a model's reasoning. Andrew settled the following on 2026-09-24 (QUESTIONS.md R12):

- Supervision is on for every project, with no setting that turns it off or widens it.
- The thresholds are 3 / 4 / 6 identical calls, 4 / 5 / 8 identical observations, and a budget noted at 80 percent used and critical at 90 percent with a projected overrun. A project may tighten them and never loosen them.
- Scope is folder-level, and an unapproved recorded write outside scope pauses the run at once.
- An escalation is raised once per task and issue.
- On a route that cannot steer, a *supervision correction* may start the next run without a person. It shares the origin run's bound, is admitted with no wider permission, is labelled in the thread and History, and is cancelled by a pause or a Stop.

**Agent profile; routing preference.** A profile is a person's saved, versioned choice of one exact model: route, model id as the route lists it, reasoning level where the route has one, the Agent it works as, and the person's own rules. Editing appends a revision; a profile chooses intelligence and never grants authority. A routing preference is a project's ordered list of profiles, with an optional per-task override; fallback to the next profile is off unless the person turns it on, and every fallback is recorded on the run with what it skipped and why. At admission the resolved revision, route and model are pinned into the run record and never recomputed. A list never replaces an Agent the person chose for the thread or the run, and never routes a team member's wake. When the profiles file cannot be read, a run that a list would decide is refused rather than sent to the default route.

**Context used; compaction record.** On a Diomedes-owned model route, the per-answer record of what went into the model's context by section (estimated), what the provider reported (usage and cache reads), and which messages were left out and summarised when history passed its budget. A compaction record is a deterministic summary written by the application, never a model, naming each message it stands for by run, step and sha-256; the messages themselves stay in History. External engines manage their own context and carry no such record.

**Instruction scope, precedence and delivery record.** A discovered instruction file governs work on paths inside its own folder; a root file governs the whole project. Precedence is authority first (files are project rules), then the nearer folder, then AGENTS.md before CLAUDE.md in one folder. The delivery record on each run names which files were sent, in precedence order, and why every other discovered file was not; "truncated" means a file was left out whole for the byte budget, and a body is never cut.

**Pack manifest.** The installable description of a capability pack: id, version, publisher, the pack host contract range, typed contributions, requested permissions (a request, never a grant), dependencies and a content digest. **Installed** means the pack's verified content is in the pack store; **on** is a separate, per-Project decision. Neither is an authorization event.

**File identity; attachment.** A file's identity is the SHA-256 of its exact bytes, its project-relative path and the History version that first recorded those bytes — a projection of History, not a second record; a Thread reference opens that exact version or says it is no longer available. A Thread attachment is a project file carried by one message as one of its selected text sources; it widens no read scope, and a file the route cannot receive as text is refused in words.

**Hunk; review comment.** A hunk is one place a change touched a file, computed from the two recorded versions; a person may keep or undo each hunk, and the result is one recorded write whose History entry names every hunk's decision. A review comment is a person's note anchored to one line of a change or recorded file version, quoting that recorded line; it is durable and resolvable, never deleted, and reaches a run only inside a follow-up the person previewed and queued.

**Versioned durable records.** Every file Diomedes keeps in its data folder belongs to a registered family with a schema version. A build reads its own version, carries an older file forward one version at a time with a byte-for-byte backup beside it that is never deleted automatically, and refuses a newer file without changing it; a newer project or settings file stops the local service with the reason. A prepared write left by an interrupted save is held to the same version check as the file it replays.

**Contribution index; contribution load (P04).** The *index* is what a Project registers when it turns a pack on. It has one entry per contribution (kind, id, name, one line, triggers, body digest) and never the bodies. Only the index counts toward a request until a body is loaded. A *load* reads one contribution body for one run or one opened panel, through the indexes pinned when that run was admitted. The body is checked against the registered digest, and the load is recorded with the pack version and digest. A run admitted before a pack was turned off, updated or rolled back keeps the version it pinned. A load is a Diomedes application action and grants nothing.

**Guidance proposal; instruction revision (H10).** A *guidance proposal* is one line Diomedes offers for a loaded project instruction file after the same correction recurs three times. It carries its evidence and a replayed evaluation, and only a person's approval writes it. An *instruction revision* is an applied proposal or a rollback. It is recorded append-only with the previous and new content digests, the author, the time and the evidence, in a SHA-256 digest chain. A *rollback* restores the text from before a named revision, as a new revision, and never edits the chain. The *evaluation verdicts* are improved, unchanged, worse (it would flag a run whose write the person kept) and not evaluable (a prose line, or no recorded run to replay).

**Forced stop; couldn't resume; engine question (H03, H05).** A *forced stop* is a Stop the engine did not honour within its grace, so Diomedes ended the process tree. The turn's outcome is unknown, and the session is not resumed. *Couldn't resume* is what a thread or conversation says when its saved native session cannot take the next message: after a restart mid-turn, a forced stop, or a resume the engine refused. The next message starts a new session, or the interrupted turn ends with that sentence rather than staying Running. An *engine question* is a permission ask or a plan that an engine presents mid-turn and only a person may answer. It is shown as a Need, answered once and sent back to the engine; if nobody answers, it expires and stops the turn.

**Stale evidence (Discovery).** An observed fact whose approved file has changed since it was observed. The fact and its evidence stay as recorded; the record reports the evidence as stale with the recorded and current SHA and stays readable, correctable with fresh evidence and retirable. Stale evidence never backs a new observed fact.
