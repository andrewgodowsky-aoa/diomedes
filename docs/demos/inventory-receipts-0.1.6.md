# Stock receipt demonstration on the 0.1.6 source line

This run uses the built Console receipt component, the receipt HTTP consumer,
`InventoryStockService`, the authoritative stock document and actual Store History.
It is a development candidate on package version **0.1.6**, not a claim that the
published 0.1.6 installer includes this new screen. Do not use an older installed
copy or captures from an earlier inventory worktree to demonstrate this slice.

Stock and authorization are explicitly simulated. The isolated host imports a
test authorizer that supplies the service's expected authority result. It proves
the consumer's enforcement and durable behavior; it does not prove hosted login,
membership, pairing or a production stock grant. The normal desktop API remains
unmounted. No supplier, order, payment, reservation writer or live purchasing
connection exists in this workflow.

## Prepare and launch

Use the accepted feature commit in a clean checkout with its existing locked npm
dependencies available, including `services/control-plane` for repository checks.
From PowerShell in that checkout:

```powershell
git status --short
git rev-parse HEAD
npm run check
npx vite build
$env:DIOMEDES_RECEIPT_DEMO_ROOT = Join-Path $PWD 'test-results\receipt-demo-run-01'
$env:DIOMEDES_RECEIPT_DEMO_PORT = '47643'
npx tsx scripts/inventory-receipts-demo.ts
```

Open `http://127.0.0.1:47643/`. Leave the terminal running. The header identifies
the package version, source commit and whether local changes exist. The terminal
prints the owned profile and fixture revision `inventory-receipts-1`. The launcher
refuses a stale client build, an unmarked nonempty profile, an unsupported fixture
revision and a profile already held by another process. It uses built files from
`dist/`, never a mock of a prior release. It listens only on loopback.

Use a **new** suffix such as `receipt-demo-run-02` for a fresh baseline. Never delete
or overwrite a previous run to reset the demonstration. To prove persistence,
stop with Ctrl+C and restart with the same profile: its stock and History remain.
The launcher never seeds over existing stock. Runtime receipt IDs and times are
generated by Store; their exact values are recorded evidence, not fixed strings.

## Independent walkthrough

1. Open the page at desktop 1440 x 900, iPad Mini 768 x 1024 and iPhone 13
   390 x 664 CSS viewports. Browser emulation is sufficient for this local
   rehearsal. Keep its label in captures. Use separate browser tabs for separate
   pending receipt intents. These are not authenticated individual devices.
2. Choose M8 bolts / Sample workshop / Shelf A. Check the starting 12/2/10
   quantities and absent physical count. Enter quantity **3** and note
   **Synthetic delivery note 001**. Select **Review receipt**, inspect the item,
   bin, amount and expected version, then **Confirm receipt**.
3. Expect **Stock receipt recorded**, on-hand **15**, reserved **2**, available
   **13**, and exactly one **Received 3 each** History row. Open **Receipt and
   History evidence**. Compare the receipt's History ID with the displayed
   History entry; confirm **12 each to 15 each**, the actor and changed version.
4. Select **Check receipt status** repeatedly. The receipt and History ID stay
   identical and the on-hand quantity stays 15. Stop and restart the host using
   the same profile, refresh the page, and confirm the same evidence persists.
5. Choose **Start another receipt**, select cable and receive **1.25** m. Expect
   **13.75 m** on-hand. Inputs such as **1.251**, **1e2**, negative values and
   zero must not pass review. There is no implicit rounding or unit conversion.
6. Select Uncounted seals. The three stock figures remain **Unknown**. A receive
   attempt must refuse because the existing stock contract cannot establish a
   safe stock effect from those unknown balances.

## Two-device conflict

Use a new profile. Open two tabs before making any stock changes. In the first,
review a receipt for **3 bolts**; in the second, review **2 bolts** from the same
opening version. Confirm the first, then the second. The second must show a
stock conflict. The recorded on-hand stays **15** with one History entry.

Select **Refresh and start a new review** in the second tab. Review and confirm
the 2 bolts again with the refreshed version. Expect **17** on-hand and two
distinct receipt/History links. Refreshing alone must never dispatch the effect.

## Lost response and refusal cases

Run the automated scenarios below for deterministic network failure and access
changes. They intercept only delivery of the response, after letting the actual
service commit, or stop the request before it reaches the service. They do not
stub the stock response or replace Store with an in-memory ledger.

```powershell
npx vitest run tests/inventory-receipt-workflow.test.ts tests/inventory-receipt-client.test.ts tests/inventory-durable-stock.test.ts
npx vite build
npx playwright test --config playwright.inventory.config.ts
```

- A lost response retains the exact intent in this tab's session storage. Reload
  shows a pending status check. Checking status confirms the existing receipt,
  with one POST, one stock effect and one History entry.
- When status says not-found, **Retry same receipt** resends the identical
  operation ID, version, quantity and note. There is no automatic offline queue.
- Closing a tab can discard its session storage. Before beginning another
  receipt, inspect durable History for that delivery. Do not clear pending
  browser storage to force a second operation after an unknown outcome.
- Read-only access disables entry and the host refuses a forged POST. Revocation
  before replacement prevents an effect; revoked history/status reads disclose
  no receipt. A demonstration header can only attenuate the fixture's grant.
- Client actor/scope/path fields, non-receive operations and purchasing routes
  refuse. Unknown or damaged evidence is an error, never an empty successful list.

## Evidence and acceptance boundary

The Playwright config runs the same nine scenarios in iPhone and iPad emulation
and desktop Chromium. It saves `receipt-review.png` and `receipt-history.png` per
viewport, failure traces and `test-results/inventory-receipts/results.json`.
Record the commit, source status, package version, fixture revision, browser,
viewport, test counts and actual receipt/History IDs with the independent result.
Retain the profile path for restart/recovery inspection.

Real iPhone/iPad Safari, shared sessions, remote TLS ingress, deployed identity
and membership, production grants and a person's independent observed completion
remain OPEN. Do not tunnel this demonstration or change the desktop listen
address to obtain physical-device access. Those need the separately qualified
inventory gateway. The fixture is a local reproducible rehearsal, not MI-DEMO
completion, production deployment or a live purchasing system.

Before integration or independent acceptance, also compose the accepted stock
repository recovery repair identified in the [implementation record](../implementation/2026-09-20-inventory-mobile-receipt-history.md#integration-prerequisite)
and resolve the recorded broader gate failures. The ordinary fixture flows above
are verified; that does not qualify the pending recovery edge cases.
