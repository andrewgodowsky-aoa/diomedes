## Audit (what this builds on)

- **H11** (`server/capability-packs.ts`, `server/harness/instruction-delivery.ts`,
  `client/console/ProjectInstructions.tsx`): instruction files are discovered records with a sha, a
  project-authority rule pinned to that sha, and a per-run delivery record on the session. A changed
  file makes a changed rule. `server/instruction-digests.ts` is about *conversation mode* texts, not
  project instruction files — conversation lineages bind their mode's composed text, and project
  instruction files reach Work runs and the native loop only. So a revised instruction file cannot
  retire a lineage, which is what DIO-102 requires; this lane adds a test that holds it.
- **D5** (`server/trust/remembered-approvals.ts`): the "propose after repeated evidence" pattern —
  a tally keyed by an exact pattern, a threshold that is a product constant, an offer that never
  acts on its own, and a decline that is recorded. Mirrored here, with one deliberate difference: a
  D5 decline is final, while an H10 decline holds only until new evidence arrives (the work order).
- **P06** (`shared/text-diff.ts`, `client/console/DiffView.tsx`): the one diff model and view. The
  proposal's diff is `buildDiff` over the file as it is and as it would be, shown by `DiffView`.
- **H15** (`server/supervision/*`): supervision records (append-only) with answered escalations, and
  the `instruction-drift` detector, which holds a run to the machine-checkable lines of a delivered
  instruction file (`Do not edit \`path\``). That detector is the evaluation's engine.
- **H17**: nothing new is needed. An instruction revision is a recorded write by a person with no
  session, exactly like a P06 partial keep, so a verification that bound the file sees a new digest.
- **Key material**: there is none to sign with. The only HMAC in the tree
  (`server/connections/credentials.ts`) is an ephemeral fixture key that is never persisted. Hence a
  digest chain (proposed default 1).

## What shipped

### 1. Proposals from evidence (`server/guidance.ts`, `shared/guidance.ts`)

Three kinds of repeated correction are read off records that already exist. Nothing new is
recorded to produce them.

| Kind | Read from | One occurrence | Threshold | Proposed line |
|---|---|---|---|---|
| `undone-write` | `state.changes` | a distinct non-sample run whose Change to the same file a person undid | 3 | `- Do not edit \`<path>\`.` |
| `scope-drift` | `state.supervision` | a distinct non-sample run H15 paused for writing in the same folder, answered **Stop** or **Redirect** (Continue is not a correction) | 3 | `- Do not write to \`<folder>/\`.` |
| `review-comment` | `state.reviewComments` | the same comment (case, spacing and trailing punctuation ignored) on a distinct change or file version | 3 | `- <the comment, one line>` |

- `GUIDANCE_THRESHOLDS` is a product constant, not a setting (the D5 precedent).
- The line goes into the **nearest loaded instruction file whose folder holds every path** the
  evidence names (H11 precedence, `AGENTS.md` before `CLAUDE.md`), with the path written relative to
  that folder, so `kitchen/prep.md` becomes `Do not edit \`prep.md\`.` in `kitchen/AGENTS.md`. With no
  loaded instruction file, nothing is proposed (no file is created).
- A target the file already forbids, or a comment line the file already contains, is not proposed.
- A proposal carries every evidence item (kind, the record's own id, the run and task, the path, the
  time, one sentence), the exact `before` and `after` of the whole file, the file's sha, and its id —
  a digest of the pattern, the evidence, the file sha and the line, so the same evidence is the same
  proposal and anything that moves makes a new one.
- **It never writes.** `GET /api/projects/:id/guidance` only reads (it re-runs H11 discovery first,
  which persists only when discovery found something different, exactly as the packs listing does).

### 2. Approve, decline, and the decline-suppression rule

- `POST …/guidance/proposals/:proposalId/approve {expectedSha}` recomputes the proposals and writes
  only the one with that id — the text the person was shown — through `Store.writeRecorded` with the
  file's sha as the base hash. A file that moved since refuses with nothing written
  (`proposal_moved`). History: actor `you`, kind `guidance-revision`, no session, no task, sentence
  *“You approved Diomedes' proposed revision to AGENTS.md: “Do not edit \`reports/summary.md\`.””*.
- `POST …/decline` records `{ pattern, proposalId, evidenceRefs, at, by: 'you', via: 'decline' }`.
  **Rule:** a pattern is suppressed while every evidence ref it now has was in some decline of that
  pattern. One new ref — a fourth undone run, a new comment — and it is proposed again, with all of
  its evidence. A rollback of an applied proposal records the same kind of decline (`via:
  'rollback'`), so rolling a revision back does not make Diomedes offer it straight back.

### 3. Signed revisions (the chain)

`ProjectState.guidance = { formatVersion: 1, revisions, declines }`. Each revision:
`seq`, `id`, `action` (`apply` | `rollback`), `path`, `previousSha`, `newSha`, the exact
`previousText` and `newText` (so any revision can be restored without anything else surviving),
`author`, `at`, `evidence`, `evaluation`, `pattern`, `rollbackOf`, `historyEntryId`, `prevDigest`,
`scheme: 'sha256-chain-v1'`, `digest`.

- **Attribution (decision 8):** an applied proposal is `{ kind: 'proposal', proposalId, proposedBy:
  'diomedes', approvedBy: 'you' }` — Diomedes application code proposed it, a person approved it;
  the History write is the person's. A rollback is `{ kind: 'person', who: 'you' }`. A proposal is
  never an author on its own.
- `digest` = SHA-256 over the canonical JSON (keys sorted) of every other field, including
  `prevDigest`. `verifyGuidanceChain` walks from the first record and names the first break: a
  format it does not read, a record out of order (dropped or reordered), a record that does not follow
  the one before it, a record changed after it was recorded, or a text that no longer matches its sha.
- A broken chain is shown as broken (`revisions · chain broken at N` and the reason) and **every
  further approve or rollback refuses** with `guidance_chain_broken` and writes nothing. Nothing
  repairs or rewrites the chain (decision 10). The chain is never evicted; at 1,024 records new
  revisions refuse.

### 4. Evaluation (`recorded-replay`)

Before a proposal is offered it is evaluated, bounded to 20 targeted and 20 control runs:

- **Targeted** runs are the runs the evidence names. **Control** runs are other non-sample runs
  whose Change to a path the new line governs was **kept**.
- Each run's durable records are read into H15's `DriftInput` (`driftInputFor`) and replayed
  through `detectInstructionDrift` twice: with the machine rules of the file as it is, and as it
  would be. No model is called and nothing is sent; this is the "scripted route" in the only sense a
  deterministic replay can honestly be one.
- **Verdict:** `not-evaluable` when the new line is not a machine-checkable rule (a review comment in
  prose) or none of the runs is on the record; otherwise `worse` if it would flag *any* run whose
  write you kept (it would have interrupted work you wanted), else `improved` if it would flag a
  corrected run the current file does not, else `unchanged`. The per-run results and one sentence
  (*“Replayed 3 recorded runs through the instruction check: with this line it flags 3 of the 3 you
  corrected; without it, 0.”*) are on the proposal and copied into the revision record.

### 5. Rollback

`POST …/guidance/revisions/:revisionId/rollback {expectedSha?}` restores that revision's
`previousText` in one step, as a new `rollback` record (`rollbackOf` names it). The base hash is the
file as it is now, so an edit made since is refused rather than overwritten (`rollback_moved`), and
restoring what the file already reads refuses. Earlier records are never edited. A rollback can
itself be rolled back.

### 6. H11 follows; open conversations do not reset (DIO-102)

After every approve and rollback, `discoverInstructionFiles` runs, so the instruction record's sha,
its rule's `provenance.source` and the next run's delivery name the new bytes (tested through
`assembleInstructions`). Conversation lineages are untouched, and a past session's delivery record
still names the bytes it was sent — both tested across a restart.

### 7. Console (`client/console/GuidanceMaintenance.tsx`, `guidance.css`)

Inside the existing inspector under **Project instructions loaded**: a **proposed revisions** section
(file, kind and `3 of 3`, the line in the code role, the verdict word and sentence, the evidence with
run and record ids) with **Review the change** opening the P06 diff and **Approve** / **Decline**
under it; and a **revisions** section, newest first, with `seq`, `Applied` / `Rolled back`, the path,
`previousSha → newSha`, the time, who (*Proposed by Diomedes · approved by you* or *You*), and **Roll
back to before this**. Machine strings truncate or wrap where they are written (decision 5); the
chain state is one line in the section head.

## Proposed defaults (Andrew's to confirm)

Each is the most conservative option that still delivers H10.

1. **"Signed" is a SHA-256 digest chain**, not an HMAC: there is no persisted local key material to
   sign with, and none was invented. A digest chain detects an edited, dropped or reordered record;
   it cannot stop someone who can write `state.json` from recomputing the whole chain. Moving to an
   HMAC needs a key-custody decision.
2. **Thresholds are 3 distinct occurrences** for every kind, as a product constant.
3. **A decline holds until a new evidence ref arrives**; a rollback of an applied proposal counts as
   a decline of its evidence.
4. **Rollback restores the text before the named revision**, not the text after it.
5. **`worse` wins**: a revision that would flag any run whose write you kept is `worse`, however many
   corrected runs it would also catch.
6. **Sample runs are not evidence.**
7. **Only an existing, loaded instruction file is revised**, by appending one bullet at the end; no
   file is created and no existing line is edited.

## Known gaps (not shipped; nothing claims them)

- **Two writes, not one.** The file write (with its journal) lands first and the chain record is
  appended after it. A crash between them leaves a `guidance-revision` History entry with no chain
  record; the file's sha then differs from the chain head, but nothing surfaces that automatically.
- A person's own direct edit to an instruction file (in an editor, or outside Diomedes) is recorded
  by History as always, not as a chain record.
- Proposals are computed when the inspector is opened; there is no notification that one is ready.
- Evaluation replays only H15's instruction check. A prose line is honestly `not-evaluable`; no model
  replay exists, and a model-backed evaluation route is not built.
- Comments are grouped by exact normalised text, not meaning. Repeated `instruction-drift` (a rule the
  runs keep breaking) is not a source; strengthening an ignored rule is not machine-checkable.
- The ledger is not validated when the Store loads (like the other additive fields); the chain is
  verified wherever it is used.
