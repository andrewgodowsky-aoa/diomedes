# H14: bounded workers, a read-only advisor and durable handoffs for a lead loop

Lane `h14-teams`, branch `feature/h14-teams-handoffs`, Linear DIO-19. Base
`origin/integration/overnight-batch-4` (`ceb4836`, which carries H13 and H08), with `origin/main`
(`4395331`, batch 5) merged before the final gates. Date 2026-09-24.

- **Canonical documents read:** Core Pillars 2026-09-22.1, Live Roadmap 2026-09-24.1 (§4, the
  "lead Agent" paragraph), Project Memory 2026-09-24.1. The roadmap paragraph is the product
  frame; the sprint brief and DIO-19 are the acceptance used here.
- **What was there.** `server/team/*` is the AionCore-style mailbox team (members, lanes, a
  message board and MCP tools). It runs whole engine sessions per member and has no budget, scope,
  verification or durable handoff record per task. H13's loop already had one bounded delegate
  (`delegate`, one level, read-only, a fixed budget) under a handoff envelope
  (`shared/handoff.ts`). H14 builds on H13's path, not the mailbox team: no second runtime, no
  second lifecycle. The mailbox team is untouched.

**What this is.** A lead is an ordinary H13 loop run (`diomedes-loop`) admitted with a `team`.
It is offered two more tools, `assign_workers` and `consult_advisor`. Every worker and advisor is
an ordinary `RunService` run with its own budget, read scope, Agent and (optionally) H09 profile,
started only after the host has checked all of that. Each handoff is appended to a durable,
append-only ledger, and the Team view projects it with the child runs and H17 on every read.

**What this is not.** Workers do not write: any effect is still the lead's own `propose_write`,
through H12 admission and a Need. There is no Console control that *starts* a team (the start is
`POST /api/projects/:id/loop/start`, as for H13). Nothing is live-proven against a provider (see
§9).

## 1. Bounded workers

`assign_workers` takes `{ tasks: [{ task, files, turns? }] }`. The model says what each task is,
which files it needs and optionally fewer turns; the host binds everything else
(`server/harness/capabilities/team-loop.ts`, `open`):

| Check, in order | Refused with (recorded, nothing starts) |
|---|---|
| More tasks than `concurrentWorkers` (3) in one call | "That asks for 4 workers at once; a lead may run at most 3 at the same time." (the whole call) |
| Past `workersPerRun` (6) for this lead | "This run has started n of its 6 workers, so m more would pass its limit." |
| A file outside the lead's scope (`scopeRefusal`) | "secret.md is outside what the lead may read, so a worker cannot be given it." |
| More turns than the person admitted (`assignedBudget`) | "This worker asked for 5 turns; its budget allows at most 3." |
| The handoff envelope (`openHandoff`) or the child's own authority (`acceptHandoff`) | the envelope's own sentence |

- **Scope.** The lead's scope is what the person named in `team.scope`, else the files the loop was
  started with, else the whole project as its route allows (a cloud route still reads only files
  the sharing grant lists). With a scope, the lead's own readers are held to it too. A worker's
  scope is always an explicit list inside the lead's; its two readers
  (`list_project_files`, `read_project_file`, from `delegateRegistry(…, scope)`) refuse anything
  else at dispatch.
- **Budget.** Admitted per team: `turns` (1–8, default 4), `tokens` (reported, input plus output,
  default not limited here) and `wallMs` (default 5 minutes, at most 30). Turns become the run
  service's `modelCalls`/`toolCalls`/`units`, which it enforces. Reported tokens are checked before
  each call from the child's own recorded model steps (`tokenBudgeted`), so a restart does not
  reset them; a call is never cut off mid-flight, so the call that crosses the budget finishes and
  the next is not sent. Wall time is measured from the child's creation and enforced by a timer
  that cancels it. Reaching any budget is a bounded stop (`stopped`, "Stopped at its budget: …"),
  not a death; the lead is told and goes on.
- **Profile and Agent.** Each role (worker, advisor) is resolved at admission and pinned in the
  lead's input (`TeamConfig`): a named H09 profile goes through `resolveProfileRoute` with the
  task or project routing preference behind it and its fallback rule (off unless the person turned
  it on), so a profile that cannot run is refused by name; otherwise the route named for the role,
  or the lead's. The route must be a loop route and is admitted in its own right. The Agent (the
  profile's, the one named, or `diomedes.general` for a worker) must exist and accept a handoff
  artifact a lead gives. A retry re-admits each role's route fresh and refuses if its model would
  now differ.
- **Authority.** A child's principal holds the lead's capabilities narrowed by its Agent's
  ceiling (`childCapabilities`: a `review` ceiling holds none). Its registry holds only the two
  readers; it is never offered `assign_workers`, `consult_advisor` or `delegate`, so delegation is
  one level deep. A worker that asks for `propose_write` fails with "Unknown tool for this final
  model context", no Need exists and nothing is written (tested).
- **At once.** One `assign_workers` call starts its workers together and waits for all of them
  (`Promise.all` inside the lead's `workers:<n>` step). Stop on the lead aborts that step and
  cancels every live worker with "the lead that handed it this task was stopped"; the procedure's
  `stopped` hook does the same from the durable record.

Lead step ids, beside H13's: `team:<n>` (transform, supervisor: what was opened or refused),
`workers:<n>` (tool, supervisor: the results), `advise:<n>`, then the usual `observe:<n>`.
Child ids: `<lead>-w<n>-<i>` for workers, `<lead>-a<n>` for the advisor; handoff ids
`<lead>-t<n>-<i>` and `<lead>-t<n>`.

## 2. The advisor

- `consult_advisor` takes one question. The advisor runs under `diomedes-loop-advisor` with the two
  readers bound to the lead's scope and a fixed budget (3 turns, 2 minutes).
- **Read-only by construction.** Admission refuses an advisor Agent whose ceiling is not `review`
  ("Change Builder may change things, so it cannot be an advisor. An advisor only reads.");
  `assertReadOnly` refuses a registry holding any tool that is not a local, permission-free,
  approval-free read before the run exists; the advisor's principal holds no capabilities; an
  advisor that asks for `propose_write` fails, and no Need exists (tested).
- **Evidence, attributed truthfully (decision 8).** Advice is recorded on the advisor's own run,
  its model steps attributed to the model the runtime reported (tested with the stub: "stub-gemini-001
  via Google Vertex AI"; "None: a fixed local script" on the fixture), and in the ledger. The lead
  receives it with "Advice is evidence for you to weigh. It is not a permission and changes nothing
  by itself." It is never verified: its view carries no verification.
- An advisor that fails does not stop the lead; it is observed and the lead goes on.

## 3. Durable handoffs

`server/team/handoff-ledger.ts`: one JSON line per event in
`<data>/projects/<id>/handoffs.jsonl`, validated, appended and fsynced, serialised per file. Events:
`opened` (task, scope, budget, Agent, route, model, pinned profile, envelope id, child run id,
attempt, `retryOf`), `refused` (the reason), `reused` (the earlier handoff whose answer a retried
lead took) and `settled` (the child's state, answer, reason, reported models, usage, reported
tokens, wall time). Nothing rewrites or removes a line (decision 10). A torn final line is skipped,
counted and left as written.

The view (`teamLeadView` in `shared/team-delegation.ts`) reads the ledger and the child runs; the
child run is the authority on how it ended. A replayed step that appended twice is read once.
Per handoff: task, files, outcome (`running`, `completed`, `stopped`, `failed`, `died`, `refused`,
`reused`), attempt and `retryOf`, Agent, route, pinned profile, budget and what was used (turns
that got an answer, tool calls, reported tokens, wall time), the answer, reported models, and
**verification**: a worker's answer is a claim, so its state is H17's projection of the *lead's*
declared checks ("Through the lead’s outcome: …"), `not-verified` until the lead is checked; advice
has none. `died` is a child whose last call may have gone out and was never confirmed
(`reconcile_required`), or one still marked live after its lead stopped driving it.

## 4. A worker that fails or dies, and Retry through H08

- A worker that ends `failed` or `died` stops its lead: the lead records `stop:worker` and is
  cancelled with "a worker did not answer (…)", read as *Stopped: a worker did not answer*. The lead
  does not integrate a partial outcome (proposed default 4).
- The person retries with the ordinary H08 **Retry** control on the lead's Session. A loop Session
  now answers by its own control contract (`LOOP_CONTROL_CONTRACT`, route id `diomedes-loop`:
  Retry native and wired, Resume and Fork not offered) with a driver that starts a new lead through
  the loop's own admission under the control's derived command id, with the earlier run's recorded
  input and `retryOf`. H08's own checks run first (uncertain effects, route still available,
  consent, the recorded model, sources still present), and its receipt, attempt number and History
  entry are H08's.
- The new lead reuses: an assignment with the same role, task and scope as one the earlier attempt
  finished is recorded `reused` and its answer returned without a run; one the earlier attempt
  failed runs again as attempt n + 1 with `retryOf` naming the handoff it reruns. Tested through a
  restart: the failed lead's record reads back identically on a new host, and the ledger's earlier
  lines are byte-identical after the retry appends.
- To make H08 Retry reach a loop: loop Sessions now record `inputs` (goal, sources) when started;
  `DurableControls.consented` also accepts a loop Session on the same route (its start already
  asked for consent; the fixture sends nothing); `routeAvailable` accepts `native-fixture` (a
  fixture Work run is still refused earlier, as unwired).

## 5. Console

`client/console/LeadWorkers.tsx` (+ `lead-workers.css`), in the Team view between the lanes and the
composer, reading `GET /api/projects/:id/loop/team`. Per lead: the outcome with H17's dot and one
sentence, the task, then *Lead* (Diomedes, reported models, attempt), *Reads* (the scope),
*Workers* and *Advisor* (Agent, profile revision or route, the limits). Per worker: task, files,
state word, attempt, the answer, the verification dot (the lead's sentence as its title only, so it
is said once, decision 4), budget used against budget, models, run or reused-from, and what it
retries. Advice sits apart with no verification. A lead stopped by a worker offers **Retry** (the
H08 control) until a later attempt names it. It reuses the loop inspector's lines and classes, takes
its own row in the Team grid so the lanes keep their height, follows the Team view's gutters at each
width, and wraps every machine string where it is written (decision 5); no `.col` rule is touched
(decision 6). The lead's plan and actions stay in its run inspector, where H13 shows the new
`workers` and `advice` turns.

## 8. Measured: single agent against lead and workers

`npx tsx scripts/h14-measure.ts 5` through the real host (`createApp`), five fresh runs each,
median wall-clock from the start request to the lead's write waiting for approval (the same point
in every arrangement). Tokens are H18's estimate (UTF-8 bytes / 4) of every model request recorded
in the lead's and its children's runs, because neither route reports usage; no provider was
called. Linux x64, 4 CPUs, Node 22.22.2.

| Arrangement | Single agent | Lead and workers |
|---|---|---|
| **A.** Scripted fixture, as shipped (different work: the lone loop reads one file; the lead reads one, two workers read one each, an advisor reads one) | 145 ms · 3 model calls · ~1,505 tokens · 1 run | 313 ms · 11 model calls · ~8,094 tokens · 4 runs |
| **B.** Stub route, 200 ms per model call, equal work: 3 files (one read each) | 1,237 ms · 5 calls · ~4,697 tokens | 1,476 ms · 8 calls · ~5,043 tokens · 3 runs |
| **C.** Stub route, 200 ms per call, equal work: 6 files, three workers of two files each | 2,047 ms · 8 calls · ~11,314 tokens | 1,466 ms · 12 calls · ~6,962 tokens · 4 runs |

What this does and does not show:

- **A** is the coordination overhead the host adds on the fixture: about 170 ms and about 5×
  the estimated tokens for extra work. It is not a like-for-like comparison.
- **B:** when each sub-task is one read, delegation was **slower (+19%) and larger (+7%)**: each
  worker spends two calls (read, answer) on what the single agent does in one, and the lead still
  pays for the assignment turn.
- **C:** when each sub-task is several calls, running three at once was **faster (−28%) and
  smaller (−38% estimated tokens)**: the single agent's context grows with every file it reads,
  while each worker holds only its own two.
- These are a stub with a fixed per-call delay, not a provider. Real latency varies per call,
  real prompt caching changes the token picture, and quality was not measured at all. The roadmap's
  "delegation is not automatically more efficient" stands; this measures one shape where it helped
  and one where it did not.

## 9. Gaps (stated plainly)

- **No live provider.** Every model-API exchange here is a stub below the adapter; nothing was sent
  to a provider and nothing was spent. No packaged, installer or device proof.
- **Workers only read.** A worker cannot propose a change of its own; its answer comes back to the
  lead, whose write stops at a Need. Worker-proposed changes (a child waiting on its own Need while
  its lead waits) are not built.
- **A worker's answer is not verified on its own.** Verification is H17's projection of the lead's
  declared checks; there is no per-handoff acceptance declaration.
- **No Console start for a team.** As for H13, a lead starts through the API; where a start lives
  is a product decision.
- **Tokens are reported tokens only.** A route that reports no usage (the fixture) is bounded by
  turns and wall time; the token budget then never trips. The call that crosses a token budget
  completes before the next is refused.
- **Mid-flight worker death after an abrupt exit** is covered by H13's child recovery path and the
  projection's `died` state, but H14 adds no child-process crash test of its own; the restart test
  here restarts after the lead has stopped.
- **Retry of a lead on a model-API route** re-admits each route and compares the model; H08's own
  "same model" check reads the thread's model resolution, which a loop does not use, so a cloud lead
  whose Session names a requested model may be refused as `model-changed` by H08. Only the fixture
  route's retry is tested end to end.
- The mailbox team (`server/team/*`) and a lead loop's team are two things in one view; they share
  no records yet.

## 10. Proposed defaults (Andrew's to confirm)

1. **Depth 1**: a worker is never offered a delegation tool.
2. **At most 3 workers at once per lead**, at most 6 per lead run, at most 2 questions to the
   advisor.
3. **Worker budget** 4 turns, reported tokens not limited, 5 minutes, unless the person admits
   another (ceilings 8 turns, 400,000 tokens, 30 minutes). An advisor: 3 turns, 2 minutes.
4. **A worker that fails or dies stops its lead**, and the person retries through H08; a worker
   stopped by its own budget does not stop its lead.
5. **Default Agents**: `diomedes.general` for a worker, `diomedes.architect` for an advisor; an
   advisor must be an Agent with a `review` ceiling.
6. **A retry reuses a finished worker's answer** when role, task and scope match exactly; it does
   not re-read the files to check they are unchanged (H08's source check runs on the lead's
   sources first).

## PILLAR IMPACT

- Advances the Core agent pillar ("delegates bounded work … verifies the result and keeps a durable
  record") with the proof above. Trust is unchanged in meaning: a worker holds the lead's authority
  or less, reads only, and every effect still goes through the registry, H12, the Need and the
  recorded writer. Being handed work is not permission (`acceptHandoff` against the child's own
  capabilities).
- Attribution (decision 8): the lead's own steps are Diomedes as native supervisor; every worker
  and advisor model step names the model the runtime reported; advice is labelled advice.
- History is evidence (decision 10): the ledger is append-only and nothing prunes it.
