# H15 — Drift detection, bounded correction and escalation

Linear DIO-20. Lane `h15-drift`, branch `feature/h15-drift-detection`, from
`origin/integration/overnight-batch-3` (H07, H08 durable controls, H11, H17 verification, H18
context accounting). Date 2026-09-24.

Canonical documents read: Core Pillars 2026-09-22.1, Live Roadmap 2026-09-23.1, Project Memory
2026-09-23.1. None defines H15's acceptance beyond the product promise ("watches for drift, asks for
authority where it needs it"), so the work order is the scope used here.

## What was missing

The 2026-09-23 audit found bounded correction limits in place (`CORRECTION_LIMITS` and
`correctionWithinBounds` in `server/harness/lifecycle.ts`, the native agent's `maxCorrections`) and
nothing that watched a run for drift or escalated one to a person.

## What shipped

### 1. Five detectors, pure functions over durable records

`server/supervision/detectors.ts`. Each takes a `DriftInput` (`shared/supervision.ts`) — a
route-agnostic view of a run's records — and returns `DriftFinding`s with a stable `code`, an
`issueKey` (the underlying issue, stable while it is the same issue), a `severity`
(`info` / `warning` / `critical`), a one-sentence `summary`, the `ask` a correction carries, the
`evidence` (each item points at the record id it rests on: History entry, Need, harness step, rule,
budget line, verification entry) and an `evidenceDigest`. Nothing reads a transcript, a file body or
a model's account of itself.

| Code | Fires when | Severity | Issue key |
|---|---|---|---|
| `scope-drift` | A touch outside the folders of the task's declared source (`Task.sourceDocument`, `Task.from.plan`) and the run's selected sources (`Session.inputs.sources`), not covered by what a person approved exactly or a task scope grant admits (`grant.roots`); or any path outside the project folder; or a destination not in the run's admitted list (harness: the capability's tools) | unapproved **recorded write** outside scope, or anything outside the project → critical; a read, or a proposal a person is already being asked about → info | `scope:<folder>` (`scope:/` for the root), `scope:outside-project`, `scope:destination:<label>` |
| `no-progress` | The same tool with the same input in a row (loop), or the same tool returning the same output for ≥ 2 different inputs in a row (observation) | by streak length (table below); a streak the run already left is only info | `loop:call:<tool>:<input12>`, `loop:observation:<tool>:<output12>` |
| `budget-burn` | While live, a budget line (harness units, model calls, tool calls, wall time; H18 context tokens where a window is declared) at ≥ 80 % → info; with a declared plan, projected use at plan completion over the limit → warning, and critical once ≥ 90 % is used | as stated | `budget:<dimension>` |
| `instruction-drift` | A write into a path a delivered instruction file (H11 `Session.instructions`, the exact sha delivered) forbids in a machine-checkable line | unapproved recorded write → critical; a proposal, or a write you approved exactly → info | `instruction:<file>#L<line>:<path>` |
| `verification-regression` | A run that projected **Verified** (H17) over History without this run's entries now projects uncertain or failed, and the changed files are ones this run wrote — an outside edit or another run is never blamed | warning | `verification:<verified run id>` |

**Machine-checkable instruction lines** (`machineRules`): a line that starts (after an optional
bullet or number) with "Do not / Don't / Never" + "edit / modify / change / write (to) / touch /
delete / overwrite / commit to", naming one or more paths in backticks. Paths are read relative to
the folder the instruction file governs; a trailing `/` names a folder; `..`, absolute paths and
globs are ignored. Everything else in an instruction file is prose for the model and is not judged.

`server/supervision/records.ts` builds the input for a Work run from: History entries with the
run's `sessionId` (recorded writes; `saved-version` snapshots and verification entries excluded),
the run's Needs (open or declined proposals; go-ahead Needs make their files approved), task scope
grants, the linked harness run when there is one (tool steps → actions and touches; budget and used;
the newest H18 `ContextAccount` on a step output), the delivered instruction files (read from the
History object store by sha, else from disk only if the bytes still hash to the delivered sha), and
the project's History, sessions and task declarations for H17. The native plan/act/observe loop (H13)
can build the same input from its own records and call `detectDrift`; `plan` progress is an input
for it to fill (Work runs declare none today).

### 2. Bounded correction on a declared ladder

`server/supervision/ladder.ts` `nextStep(finding, context)` — pure:

- **Entry by severity**: info → **note**, warning → **correct**, critical → **escalate**
  (`DRIFT_LADDERS`, one per detector).
- **Bound**: corrections per detector per run ≤ the detector's `maxCorrections`, capped by
  `CORRECTION_LIMITS.maxAttempts` and checked through `correctionWithinBounds` (so a correction can
  only ever change the attempt). A finding that persists with new evidence after a correction is
  corrected again while the bound allows, then escalated. A run that a queued supervision correction
  started shares its origin run's bound (`lineage`), so corrections can never chain into a sequence
  of runs each with a fresh bound.
- **Idempotent**: the same evidence digest is never acted on twice; info is noted once per issue per
  run.
- **Dedup per underlying issue**: while an escalation for `(task, issueKey)` is open nothing else is
  raised for it, on any run; once you answered **continue** (and Resume accepted it) the issue is
  yours, so later evidence of it on the resumed lineage is noted once, never re-raised. An issue
  already escalated on a run is only noted there afterwards.
- **Ended runs** are only noted ("The run had ended, so there was nothing to correct or pause.").

`server/supervision/service.ts` performs the step:

- **note** — a record only.
- **correct** — the message `"[Diomedes supervision] <Summary>. <ask>"`, through H08: **Steer**
  where the route's profile offers native steer and the run is working (a refused steer is queued
  instead), otherwise **Queue** (`waitsFor: 'turn'`, the run's route, agent and sources; model left to
  the thread at delivery). Both go through `DurableControls.perform` with
  `requestedBy: { actor: 'diomedes', via: 'supervision', recordId }`, so the control receipt,
  the follow-up (`queuedBy: 'diomedes-supervision'`) and the History lines ("Diomedes supervision
  steered…", "…queued a correction…", "Diomedes sent its supervision correction…") say who asked.
- **escalate** — H08 **Stop** (`scope: 'task'`) in supervision's name, then an ordinary **Need**:
  `what: "Diomedes paused this run: <summary>"`, the evidence as `why`, the consequence ("Continue
  resumes it after re-checking its permission, inputs and route. Redirect sends your instruction as
  its next run. Stop leaves it stopped. No answer grants anything new."), the evidence paths as
  `files`, `origin` a Diomedes application origin (`executorId: 'diomedes:supervision'`) and
  `supervision: { recordId, code, issueKey, choices }`. The task moves to Waiting (`needs-ok`) so the
  Ready queue never restarts it underneath the question. History: "Diomedes supervision paused
  <task>: <summary>."

Every action is a `SupervisionRecord` appended to `ProjectState.supervision` (never rewritten, never
pruned; 4096 per project, after which nothing new is recorded rather than anything forgotten).

**Trigger.** The store's `change` announcement (the one the follow-up queue already listens to)
queues an evaluation of each live run in that project behind the store lock. No poller. A detector
error is logged and never rolls the store back. `POST /api/projects/:id/supervision/evaluate
{ sessionId }` evaluates one run on demand; `GET /api/projects/:id/supervision[?sessionId=]` lists
records.

### 3. Escalation

- **Only a person answers it.** `POST /api/projects/:id/supervision/escalations/:needId/answer`
  `{ protocolVersion: 1, commandId, answer: continue | redirect | stop, text? }`, or the ordinary
  `/needs/:needId/resolve` (go-ahead → continue, declined → stop; `allowForTask: true` is refused).
  It carries no `approval` or `harness` binding, so no task scope grant, remembered approval or
  reviewer can resolve it (tested).
- **Never grants authority (decision 7).** **Continue** is an H08 **Resume** asked for by you, with
  every Resume re-check (route, sending consent, permission never wider than the stopped run's,
  model, source versions, uncertain effects). **Redirect** is an H08 **Queue** of your words, which
  starts the next run only through ordinary admission. **Stop** leaves the run stopped and returns the
  task to To do (moved by Diomedes, so the Ready queue does not treat it as a reopen).
- A continue or redirect the route or revalidation refuses leaves the Need open and records the
  refusal; the Console says "Not done: <reason>". On a route that does not offer Resume (today every
  provider route; H03/H05 wire it), Continue is refused with the route's words — say so, not hide it.
- Answers are idempotent by `commandId`; a second answer to an answered Need is 409.
- Restart: records and the open escalation are in `state.json`; the escalated run is already
  stopped, so restart recovery (which expires open Needs of *live* runs) leaves it alone.

### 4. Console

- `client/console/Supervision.tsx` + `supervision.css`, in the run inspector's register (caption
  type, hairline left rule, attention colour only for an escalation and for `critical`):
  **Supervision** section in `RunInspector` listing each record — rung (Noted / Asked the run to
  correct / Paused and asked you / You answered), detector, severity, time, who ("By Diomedes
  supervision · application action, no model", or "By you"), the finding, the H08 control and what
  the route did, the correction bound, the exact message sent, the ladder's reason, and the evidence
  (detail plus `kind · ref`, the ref truncated with its full value in the title).
- `EscalationBlock` replaces `NeedBlock` for a supervision Need in the thread: "Diomedes ·
  supervision · application action · needs you", "Diomedes paused this run: … — continue, redirect,
  or stop?", the evidence, and exactly three verbs (Continue, Redirect with a text box, Stop). No
  "for this whole task", no remember, no scope offer.
- `ControlReceiptLine` adds "asked by Diomedes supervision" on a receipt supervision asked for.
- Attribution (decision 8): Diomedes is named only on its own supervision actions, and as an
  application action; the drifting writes stay attributed to the run's engine and model.

## Proposed defaults (conservative; Andrew's to confirm)

1. **Thresholds** (`DRIFT_THRESHOLDS`): identical calls in a row 3 / 4 / 6 (note / correct / pause);
   same observation for different inputs 4 / 5 / 8; budget noted at 80 % used; pace projection once
   ≥ 1 plan step is done, critical at ≥ 90 % used with a projected overrun.
2. **Correction bounds per detector per run**: scope 1, no-progress 2, budget 1, instruction 1,
   verification 1; never above `CORRECTION_LIMITS.maxAttempts` (3).
3. **Scope is folder-level**: a selected source's folder is the run's scope; a source at the project
   root puts the whole project in scope; a task with no declared or selected source has no scope to
   judge (only paths outside the project count). Files a person approved exactly and folders a task
   grant names are admitted.
4. **An unapproved recorded write outside scope, or into a forbidden path, pauses at once**; reads and
   proposals are noted (a proposal already waits for a person).
5. **A queued correction becomes the next run** on routes that cannot steer (that is what H08 Queue
   is). It shares the origin run's correction bound, and a pause cancels it.
6. **Escalations are raised once per task and issue**; "continue" acknowledges that issue for the
   resumed lineage.
7. **Supervision is on for every project**, with no setting to turn it off or to widen anything.
8. **Instruction drift reads only backticked paths after an explicit prohibition**; nothing is
   inferred from prose.

## Known gaps / follow-ups

- Continue works only where a route wires Resume (today: the test-mode control fixture). On provider
  routes Continue is refused with the route's words and the person chooses Redirect or Stop; H03/H05
  bring Resume through `registerDriver`.
- Work runs declare no plan, so budget pacing fires only for a caller that supplies `plan` (H13).
  Spend (job caps) is an accepted input dimension but not wired from `server/job-caps.ts`.
- Reads are judged only where a record names them (harness tool steps); a Work run's engine reads
  are not recorded, so read-drift on provider routes is not detected.
- Native provider runs usually finish in the same locked step as their approved write, so drift found
  afterwards is noted, not paused.
- No stream-time triggers (H16), no learned thresholds, no per-project threshold settings.

## PILLAR IMPACT

- **Advanced:** the product promise "watches for drift, asks for authority where it needs it" now
  has a mechanism with evidence; scoped authority (an escalation is a question, never a grant;
  continuing re-checks and never widens); truthful attribution (supervision is named as Diomedes
  application actions, drifting work stays the engine's); history is evidence (append-only records).
- **Risks:** a queued correction on a route without steer starts the next run without a person
  (bounded, labelled, cancellable by Stop) — recorded as an open question.
- **No conflict found**; no new runtime, permission model or surface.
