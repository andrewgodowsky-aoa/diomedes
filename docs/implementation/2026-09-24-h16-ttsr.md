## What was missing

H11 resolves which rules govern and says, honestly, that a model adapter's `inspect` is "after-output
inspection … never stream-time interception". H15 reads a run's durable records after they are
written. Nothing watched a model's output while it streamed, and nothing let a rule act on a proposed
tool intent before H12 admitted it.

## What shipped

### 1. Declarative trigger rules (`shared/stream-rules.ts`)

A rule (`streamRuleSchema`) has an id, version, `enabled`, an optional `taskId` it is limited to, an
optional requirement key `constrains` (default `trigger:<id>`), what it matches, its intervention,
the correction `message` (steer only) and the `text` saying what it is for.

| Match | Matches | Notes |
|---|---|---|
| `text` | a literal phrase in the streamed text | case-insensitive unless `caseSensitive` |
| `pattern` | a regular expression in the streamed text, within a declared `window` (≤ 512 characters) | bounded grammar below; a match longer than its window may be missed |
| `tool` | a proposed tool intent: `tool` name, `effectClass` (H12 classes), `target` (a project-relative file, or a folder ending in `/`) | every named field must match; at least one is named |

Interventions, weakest to strongest: `annotate`, `steer`, `hold`, `stop`. `hold` is refused on a
text or pattern rule (streamed text has already been said), `steer` requires its message and no
other intervention carries one, and a target cannot be absolute, contain `\` or climb with `..`.

**Pattern grammar** (`patternProblem`): no `^`/`$`, `\b`/`\B` (a chunk's edge is not the text's
edge), no lookaround, no backreferences, no repeated group that itself repeats or chooses, and at
most one variable quantifier (`*`, `+`, `?`, `{m,n}`; a fixed `{n}` is free). Two variable repeats
can backtrack against each other and make the cost per chunk cubic; this was measured, not assumed
(the first draft allowed two and the performance test hung).

**Authority** is H11's, and only H11's: a rule is `organization` (in `settings.json`, for every
project on this installation) or `project` (in the project's state). `resolveStreamRules` maps each
rule to a `ScopedRule` (hold and stop → `forbid`, steer → `require`, annotate → `prefer`) and calls
`resolveRules`: one rule governs each requirement key, stronger authority first, then the more
specific (a rule limited to this task). So:

- a project rule on its own key **adds** a trigger;
- a project rule on a global rule's key that would relax a restriction is **blocked** (H11:
  "cannot loosen it") and never evaluated; the write is refused with `409 stream_rule_loosens`;
- a project rule can never turn a global rule off (there is nothing at project level that can);
- two rules of one authority that contradict on one key are refused at write
  (`409 stream_rule_conflict`); if such a pair ever reached evaluation (a hand-edited file), both
  are evaluated and the strictest intervention wins, so a conflict never loosens anything.

Routes (all behind the store lock): `GET|PUT /api/stream-rules` (organization) and
`GET|PUT /api/projects/:id/stream-rules[?taskId=]` (project), body
`{ protocolVersion: 1, rules: [...] }` (≤ 64 per authority). `GET` returns both layers and, for a
project, the resolution with each rule's outcome and reason. These routes are the only writers:
`streamTriggerRules` is listed in the settings defaults so a client echoing the whole settings
object back is accepted, and, like `home`, `validateSettings` never reads it, so an ordinary
settings save can neither drop nor change the rules.

### 2. Evaluation while streaming, and at admission

**Streamed text** (`server/stream-rules/evaluator.ts`, `StreamEvaluator`). It keeps only the last
`window − 1` characters between chunks and looks at that carry plus the new text, reporting a match
only when it ends in the new text: nothing is reported twice and nothing is missed at a boundary.
Chunks are evaluated in slices of ≤ 1024 characters, once per rule that has not fired; a rule fires
at most once per stream. After `end()` the evaluator is inert and its carry is dropped unmatched,
so nothing fires after the stream ends, and two consecutive streams are never joined.

The stream reaches it through one additive, optional sink on the harness contract:
`ModelAdapter.complete(request, signal, stream?)` (`server/harness/native-agent.ts`). The model-API
adapter fans its SDK `text-delta`s to the route's own preview sink and to this one;
`EngineService.loopAdapter` passes it through; the scripted loop route (`native-fixture`) now
streams its text in five-character chunks, as a provider streams tokens. `NativeLoop.callModel`
opens a watch for each model step attempt (`StreamRuleService.watch`) and, before the step returns,
awaits every firing being durable and handed on — so no tool the answer proposes can be admitted
ahead of a firing on the text that proposed it. A route that sends its answer whole is evaluated on
that text at the same point, and the firing says `source: 'final-text'`.

**Tool intents** are judged by `StreamRuleService.hook`, a `RunService` hook: the place H12
admission already runs, after mandatory policy and before the durable commit that writes the effect
intent. There is no second path to an effect. `RunService` gained one thing: a hook may answer
`{ hold: { reason, refs } }`, which sends the step to the **same approval gate** an approval policy
uses, bound to the same intent hash, with a `step.held` event. Hooks also now receive the H12
effect declaration (`tool`, `effectClass`, `targets`) they judge; for a loop tool step that carries
none, the registry's declaration and the tool's own `targets(input)` are used.

### 3. Safe interventions only

Nothing rewrites model output or tool input. What each intervention does:

| Intervention | Where it can act | What happens |
|---|---|---|
| annotate | text, pattern, tool | a firing record; nothing else |
| hold (approval-gated intent) | tool intent whose own policy already asks for an exact approval — today the recorded write `propose_write` | waits at the approval gate as an ordinary Need whose `why` begins "A rule held this before it ran: <rule text>"; **no remembered approval (D5) answers it**; go-ahead binds to the exact intent; decline cancels the run; the effect intent is not even written before the answer |
| hold (any other intent) | e.g. `read_project_file` | refused at admission and handed to H15, which pauses the run through H08 Stop and asks you; the Need reads "Diomedes paused this run: a project rule (<id>) held the proposed <tool> call: …" |
| steer | text, pattern, tool | handed to H15 as a `rule-trigger` finding (warning): the ladder asks the run to correct through H08 **Steer** where the route steers natively, else **Queue**, with the message `[Diomedes supervision] <summary>. <rule message>`; the tool intent itself is not blocked |
| stop | text, pattern, tool | handed to H15 as a critical `rule-trigger` finding: H08 **Stop** in supervision's name and an escalation Need (continue / redirect / stop). If supervision does not pause the run — H15 raises nothing more while an escalation for that rule is already open on the task — the intent is refused at admission, or the model step fails before its answer is acted on (`trigger_stopped`), so nothing runs after a stop |

Why two kinds of hold: the bridge's Need machinery — the exact approval identity, the recorded
writer and the load-time receipt validation in `server/approval-admission.ts` — carries a person's
exact OK only for the recorded write. Extending it to arbitrary tools would widen a Trust interface
(AGENTS.md: coordinate with its owner first). The invariant still holds for every intent: the
effect never runs before a person answers.

**Records.** Every firing is a `StreamTriggerFiring` appended to
`ProjectState.streamTriggerFirings` (never rewritten; at 4096 nothing new is recorded rather than
anything forgotten): the rule's id, version, authority, key, text, message and **sha-256 digest of
its exact declaration**; the run, step and attempt; the matched span (offsets, the matched text cut to
120 characters and scrubbed by the host's secret redactor, `stream` or `final-text`) or the intent
(tool, effect class, targets, **intent hash**); the intervention; how it was handled
(`recorded`, `held-for-you`, `handed-to-supervision`); and the actor, Diomedes supervision as an
application action (decision 8). Firings are idempotent by run, step, rule digest and span or intent
hash, so replays after an answer record nothing new.

**Feeding H15, not duplicating it.** `DRIFT_CODES` gains `rule-trigger`; `detectRuleTriggers`
(`server/supervision/detectors.ts`) turns the run's handed-over firings into findings, one issue per
rule (`trigger:<authority>:<id>`), the firings as evidence (kind `rule`, ref = firing id). Severity
is the intervention: steer → warning, stop or an ungated hold → critical. The ladder is H15's own
(`DRIFT_LADDERS['rule-trigger']`: the standard entry, two corrections), so a steer that keeps firing
is corrected twice and then pauses the run for you; escalations dedupe per task and issue exactly as
H15's do. The stream-rule service asks supervision to evaluate the run at once (through the store
lock) rather than waiting for the next store `change`, so a stop lands while the stream is running.

### 4. Console (`client/console/Supervision.tsx`, `supervision.css`)

H15's Supervision section in the run inspector, extended, not duplicated. Firings are rows of the
same list, in time order: the intervention and "Rule trigger", time, "By Nectovia supervision ·
application action, no model", "<Organization|Project> rule <id> v<n>: <text>", what it matched
("Matched “helper to check” at 27–42 of model:plan, while it streamed." / "Matched the proposed
propose_write call on Harness report.md, before it was admitted."), the outcome read from the record
that owns it (`triggerViews`: the Need a hold waits on, or the supervision record and H08 receipt a
steer or stop was handed to), the exact correction message when one was asked for, and the rule
digest (truncated, full value in the title). A supervision record that only acts on a firing is said
on the firing's row, not again (decision 4); a person's answer keeps its own row. Outcome words
follow what the route did: "Correction not sent: …" when H08 refused, never "queued". A stop, or a
hold still waiting, carries the attention rule. Machine strings wrap or truncate where they are
written (decision 5); no `.col` rule touched (decision 6).

## Proposed defaults (conservative; Andrew's to confirm)

1. **Where rules come from:** the local person, through the local client, writes both layers; on a
   local installation that person administers it, so organization authority is theirs. Team- or
   company-distributed rules are not in scope. No model output, imported document or connector result
   can become a rule (there is no path from content to these routes; H11 `admissibleAsRule`).
2. **A rule fires at most once per stream** (per model step attempt) and once per tool intent.
3. **A hold waits at the approval gate only where that gate carries an exact approval** (today the
   recorded write); any other held intent is paused and asked about through supervision.
4. **A remembered approval never answers a held step.** "Go ahead and remember" is still offered on a
   held write's Need (the Console cannot tell it was held); the grant it records covers later
   unheld steps only.
5. **Steer rules climb H15's ladder**: two corrections per rule per run lineage, then a pause.
6. **Pattern grammar:** one variable quantifier, windows ≤ 512, slices of 1024 characters; phrases
   are the default.
7. **Stream-time evaluation is on wherever rules exist**, with no setting to widen anything.

## Known gaps / follow-ups

- **Only the Diomedes loop (H13) is watched.** It is the one route where Diomedes owns tool
  admission and the model stream. Work runs on external engines (Codex, Claude Code, OpenCode,
  ACP routes) run their tools inside the engine (H12: observed, not mediated), and their preview
  streams are not evaluated; NativeAgent turns (format-report, the loop's delegate child) are judged
  at tool admission but their text is not streamed through a watch.
- **Steer does not reach a loop run today.** The loop routes' contract declares Steer unsupported, and
  H08's Queue refuses a follow-up on `native-fixture` ("… is not a route this build can use") even
  though the inspector lists Queue as offered — a pre-existing H08 inconsistency. The firing, the
  correction and the refusal are all recorded and shown as "Correction not sent". A native loop
  steer channel (the loop owns its message list) would need the route contract and H08's pinned
  per-route table to change; it is a follow-up, not claimed.
- **Continue after a trigger pause** is H08 Resume, which loop routes do not offer; the person
  redirects or stops (as for any H15 escalation on these routes).
- **A stop on an external model call** in flight cancels the run, and the call is parked as
  `reconcile_required` (H13's existing Stop semantics), never relabelled.
- **No Console rule editor.** Rules are written through the API; the Console shows firings only.
- The fixture streams fixed text; provider streaming reaches the watch through the model-API adapter's
  `text-delta` path, which is exercised by type and wiring here, not by a live provider call.

## PILLAR IMPACT

- **Advanced:** scoped authority (a rule can only ask, hold or stop — it grants nothing, a hold is
  answered by a person every time, and a remembered approval cannot answer it; precedence is H11's,
  so a project can never loosen a company rule); truthful attribution (firings are Diomedes
  supervision application actions; the model's text is quoted, never rewritten); history is evidence
  (append-only firings with the rule's digest); one runtime and one admission path (a RunService
  hook and H15's ladder, no second executor, store or surface; decision 14).
- **Risk:** stream-time matching sees only what streams through a route Diomedes owns; it is not a
  claim about external engines, and the Console and this record say so.
- **No conflict found.**
