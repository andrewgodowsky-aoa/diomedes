## Method

- **Reading.** Adversarial reading of each change against its record's claims and standing decisions 4, 8 and 10.
- **Probes.** For every suspicion, a probe test through the real HTTP stack:
  - `createApp` for H08 and H02;
  - the real Codex adapter and the fixture app-server child process for H02;
  - `selectHistory` / `compactTurns` for H18.
  A finding is confirmed only when its probe fails on the base.
- **Fixes.** Every confirmed finding got its probe kept as a regression test, a minimal fix, and the test shown green.
- **Test adequacy.** Each feature's key invariants were mutated in a scratch worktree, and the feature's own tests were re-run to see which mutations they catch (tables below).

## Findings

Severity: **P0** loses data or authority. **P1** breaks a stated invariant or safety property in a
reachable case. **P2** is a wrong record or claim, or an edge case.

### H08 durable controls

Tests: `tests/review-c-h08-controls.test.ts` (8 regressions plus 3 guards). Fix commit `9e930da`.

- **RC-H08-1 (P1): generation Stop was credited to the engine even where Diomedes did the abort (decision 8).**
  - Where: `server/durable-controls.ts`, `stop()`.
  - Bug: the performer was the engine whenever the route had a contract. It was never checked against `commands.interrupt.support`. On the model-API routes (`interrupt: host`, an HTTP abort), a generation Stop recorded `{kind: engine}` with support `native`.
  - Fix: the engine is credited, with `native`, only when the contract says `native` and the interrupt was acknowledged. Otherwise the performer is Diomedes with `host`.
- **RC-H08-2 (P1): Retry's uncertain-effects block could be bypassed by naming an earlier run.**
  - Where: `continueRun`, which checked only the named run.
  - Scenario:
    1. A fails.
    2. Retrying A gives B, whose approved write is `conflicted`.
    3. Retrying B is refused, but retrying A was applied and re-sent the same request.
  - Fix: the check is the union over the run's whole lineage (`lineageOf`: the root reached back through Resume/Retry receipts, and every descendant).
- **RC-H08-3 (P1): at 2048 control receipts, Stop itself was refused.**
  - Refusal receipts and supervision's own Stops count toward the limit, and the Console's Stop now goes through this route. A long-lived project could reach a state where neither the person nor supervision can stop a running run.
  - Fix: Stop is exempt from the capacity check. Proposed default 6 (never evict) is unchanged.
- **RC-H08-4 (P2): a Work start named `<id>:work` let control `<id>` claim a retry it never performed.**
  - The crash-window short-circuit took any run carrying the derived id.
  - Fix: that run must be this task's and this route's. Anything else is `409 control_command_conflict`.
- **RC-H08-5 (P2): Stop naming a settled run said "The stop was sent and not confirmed".**
  - This happened when another run of the task was live. Nothing was sent, and the live run kept running.
  - Where: `server/work-control.ts`, whose `wasLive` looked at the task, not the named run.
  - Fix: a Stop that names a run is "live" only if that run is the live one.
- **RC-H08-6 (P2): Stop(task) with nothing running but a cancelled queue said the stop was "sent and not confirmed".**
  - Fix: it now says "Nothing was running." plus the cancelled count.
- **RC-H08-7 (P2): retry attempt numbers repeated.**
  - Retrying the original twice gave "attempt 2" both times.
  - Fix: the next attempt is one more than the highest attempt reached anywhere in the lineage.
- **RC-H08-8 (P2): the legacy `POST /stop` stopped another task's run.**
  - This was pre-H08, but it has the same Stop semantics. `{taskId: T1, sessionId: <T2's run>}` stopped T2's run and filed its receipt on T1.
  - Fix: a named run must belong to the task, otherwise 404.

**Checked and correct (kept as guards):**
- Two concurrent identical retries perform once. The route runs under the global store lock.
- A crash between the retry start and its receipt replays to exactly one run.
- A control naming another task's run is 404 and leaves no receipt.
- The digest covers every request field.
- Host fork is atomic: the task, thread and receipt are persisted together.

**Mutations against the feature's own tests** (`h08-durable-controls`, `h08-control-profile`):

|---|---|

### H02 Codex native steer / resume / fork

Tests: `tests/review-c-h02-codex.test.ts` (6 regressions plus 2 guards). The fixture app-server
gains an `errors` / `probeErrors` knob that answers a chosen method with a given JSON-RPC error or
exits. Fix commit `7ab88ab`.

- **RC-H02-1 (P1): Resume and Fork hold the global store lock while Codex starts. NOT FIXED; proposed patch below.**
  - `store.locked` is one queue for the whole service. While a Resume waits up to 45 s (`CodexControls.waitMs`) for its run to open a Codex thread, every other request waits, in every project. That includes Stop and plain reads.
  - Fork has no overall bound. About 7 RPCs at 20 s each can hold the lock for about 140 s.
  - Probe: a `GET /state` waited 1,436 ms behind a Resume whose Codex took 1.5 s to start.
  - There is no deadlock: `settle` runs before `record` takes the lock.
  - The 45 s wait under the lock is H02's proposed default 5, so it is listed under *Decisions to revisit* rather than changed here.
- **RC-H02-2 (P2): Fork was offered, and credited to Codex, on a build that cannot resume the branch.**
  - A branch is continued only through `thread/resume`. With fork but no resume, the receipt said "the new task's first run continues it" (performed by Codex), and that run then restarted fresh.
  - Fix: native Fork needs both `fork` and `resume`, in `codexWorkContract` and in `forkCodexThread`.
- **RC-H02-3 (P2): an overloaded or internal Codex error was misread twice.**
  - As a capability: the probe treated any non-"unknown method" refusal as "has the method". An overloaded answer therefore recorded `resume: true` and kept an `ephemeral: false` thread (against H02 default 1).
  - As "Codex no longer has that thread": Resume treated any refusal that way, and started a new thread silently labelled as such. The record says only that answer may start fresh.
  - Fix, probe: a method is present only when its parameters are refused (-32600/-32602 without "unknown method"); anything else throws.
  - Fix, Resume and Fork: they start fresh or refuse only on a thread-not-found answer (`threadGone`); anything else fails the run.
- **RC-H02-4 (P2): `thread/resume` and `thread/fork` dropped isolation fields that `thread/start` sends.**
  - The dropped fields: `environments: []`, `runtimeWorkspaceRoots`, `selectedCapabilityRoots`, `dynamicTools`, `allowProviderModelFallback: false`.
  - This contradicts the code's own "the same policy as a new thread".
  - Fix: both now send them.
  - Live effect: whether 0.153.4 accepts these fields on resume and fork is a new live-acceptance item. If it refuses them, the run now fails visibly rather than resuming with less isolation.
- **RC-H02-5 (P2): resuming the same stopped run twice continued a thread that had moved on.**
  - The second Resume carried the first Resume's turn ("after 3 user turns"), while the receipt said Codex continued the stopped run.
  - Fix: Resume is refused (`not-applicable`) once another run has continued that thread, and the refusal names the run to resume instead.
- **RC-H02-6 (P2): the restart replay credited Codex with a resume it never did (decision 8).**
  - This is the gap H02 named.
  - Fix: `WorkControlDriver.recorded(session)` is a new optional seam. The Codex driver answers from the run's `nativeThread`: the engine plus its model with `native` only for `origin: resumed`, otherwise Diomedes with `host`.

**Checked and correct (kept as guards):**
- Codex exiting during `thread/resume` fails the run and never starts fresh.
- A Steer before the turn id is known is refused and not sent.

Also correct:
- `expectedTurnId` binding.
- `liveTurns` cleanup on success, failure and Stop.
- `nativeThread` is written and awaited before `turn/start` on every path.
- A fork task's branch is continued only by its first run.
- A fork writes nothing to the origin.

**Mutations against `h02-codex-controls.test.ts`:**
- Caught: dropping `expectedTurnId` (red), always `ephemeral: false` (red), every Start continuing the branch (red), and a fresh start credited to Codex (red).
- Not caught (green): treating a timeout as "gone", skipping the resume policy or same-id check, the probe treating a transport error as absent, not awaiting `onThread`, dropping the fork new-id check, and no `liveTurns` cleanup.
  - The RC-H02-3 test and the exit guard now cover "timeout or error as gone".
  - The rest are listed below as open test gaps.

**Suspicions, not confirmed:**
- Notifications are filtered by thread only, not by turn.
- The "failed before Codex opened a thread" detail is wrong after a policy mismatch on a resumed thread.
- An `experimentalApi` gate would read as "has method".
- A crash between `thread/fork` and the receipt leaves an orphan Codex branch, and a replay makes a second one. The same window exists for Steer.

### H18 context accounting and compaction

Tests: `tests/review-c-h18-context.test.ts` (5). Fix commit `e9b7af2`.

- **RC-H18-1 (P1): a message could be recorded as included but cut out of the text, and so be neither kept, omitted, summarised nor named in the marker.**
  - Where: `selectHistory`, which took the six newest messages and the opening message whatever their size. When they alone passed the room, `cutHistory` removed the opening message, and even whole "recent" ones, while `selection.included` still listed them.
  - This is reachable with ordinary long answers.
  - Fix: the protected set is size-checked newest first. The newest is always taken; each other recent message, and the opening one, only while it fits. One that does not fit is omitted and summarised.
  - A newest message that alone passes the bound is marked `truncated: true` (a new optional field) instead of being claimed whole.
  - Test change: the existing test `tests/context-accounting.test.ts` "…the oldest part is cut, never the newest" pinned the defect (`omitted: []` while about 6,000 characters of message 1 were cut). It now asserts the truthful outcome: message 1 omitted and summarised, the two newest whole, nothing cut. It is not weakened.
- **RC-H18-2 (P2): the 160-character summary excerpt could split a surrogate pair.**
  - A lone surrogate then reached the provider in the history.
  - Fix: the cut steps back off a high surrogate, as `cutHistory` already did.
- **RC-H18-3 (P2): "N summarised" counted messages the summary has no line for.**
  - With 60 short messages, 48 were "summarised" but 11 had a line.
  - Fix: `CompactionRecord.listed` (a new optional field) and `summarisedCount()`. The Console line, the history-section detail and "Left out" now say "summarised" only for listed messages, and "left out without a line in the summary" for the rest.
- **RC-H18-4 (P2, record only): the record's claim "the newest message is never the one cut" is false when the newest alone passes the bound.**
  - This was true before H18 too.
  - With RC-H18-1, that case is now recorded as `truncated`. The claim should read "the newest message's end is always kept" (see the patch below).

**Verified correct:**
- Byte identity with `boundedHistory` inside the bounds, including exactly 12 messages / 24,000 characters.
- The section sum equals the first call's bytes.
- Cache token mapping on Responses/Azure, Vertex and OpenRouter: every source reports cache as part of input, so no double counting.
- Decision 8 (application authorship) and decision 10 (runs untouched).
- Ranking determinism.

**Mutations against the H18 tests:**
- Caught (red): dropping a section, counting cache reads as zero, no newest-message protection, compaction of included messages, and taking the first call as the last.
- Not caught (green): `sameAsPrevious` comparing the oldest turn, the marker omitting carried numbers, and removing the omission reserve. These are open test gaps.

**Suspicions, not confirmed:**
- **The stable prefix hash leaves out the tool list.** An Ask/Plan switch changes the tools, and providers cache tools ahead of instructions. So "same as the previous message" can be shown while the provider cache misses.
- **Accounting gaps.** `reconcileContext` ignores billed but failed model steps. The first-call tokens come from the first *succeeded* step.
- **Marker numbering.** "Message N" numbers are not visible to the model or the person.

## Decisions to revisit

1. **H02 proposed default 5 (a Resume waits up to 45 s under the store lock).** The lock serialises the whole service, so this default also freezes Stop and every read, in every project. Fork has the same problem with no overall bound (RC-H02-1). Proposed patch (a redesign, so not applied):
   - (a) Register `POST /controls` with `route(..., false)`.
   - (b) In `DurableControls.perform`, take `store.locked` around the parse, replay and admission checks. Release it before any `driver.*` await. Re-take it to re-check the replay (`findCommand`) and write the receipt, so a concurrent duplicate returns the first receipt.
   - (c) Move `forkCodexThread` out of the lock the same way, and make `forkTask` run under the re-taken lock.
   - (d) Keep the waiting behaviour so the receipt can still say whether Codex continued the thread.

   **Interim option, if (a)–(d) is too large for this batch:** drop the wait. The Resume receipt then says "Diomedes started <run>; the run records whether Codex continued thread <id>", performed by Diomedes. That is truthful, and the run's `nativeThread` answers the rest.
2. **H08 proposed default 6 (refuse new controls at 2048 receipts).** It is kept for every control except Stop (RC-H08-3). Andrew may prefer the same exemption for Queue with `waitsFor` cancellation. Not changed.

## Verdicts

- **H08 durable controls — ACCEPT WITH FIXES.** The contract, receipts, identity and host semantics hold under concurrency and restart. Three P1s (engine credit for a Diomedes abort, the lineage bypass of the uncertain-effects block, Stop refused at capacity) and five P2s are fixed here with regression tests.
- **H02 Codex native controls — ACCEPT WITH FIXES.** Five P2s are fixed. One P1 (RC-H02-1, the service-wide lock during a Resume or Fork) remains as a proposed patch, because it sits on H02's own proposed default 5. H02 is still not DONE until the live Windows acceptance its record names.
- **H18 context accounting — ACCEPT WITH FIXES.** The P1 (included-but-cut messages) and two P2s are fixed. One claim in the record needs rewording.
