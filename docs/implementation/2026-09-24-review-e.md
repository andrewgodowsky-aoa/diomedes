## Method

1. Read each record in full, then each lane's own commits (`git show`), then the current code paths
   they touch, including the routes, the Store write funnel and the recovery path.
2. Hunted the named risk classes for each feature: path guards and CSP in previews (decision 9,
   DIO-98), partial keep applying hunks to the wrong base, comment anchoring after edits, schedule and
   DST edges, missed-run and host truthfulness, remembered approvals matching too broadly, profile
   resolution mutable after admission, and migrations that are not crash-safe or reversible.
3. For every candidate, reproduced it (a script, a scratch test, or a run of the pure function)
   before calling it a finding. Candidates that did not reproduce are listed as checked.
4. For every finding fixed here: wrote the test first and showed it red on the base code, fixed it
   minimally, and showed it green. Where a finding was a test-adequacy gap, the new test was proved
   by mutating the guarded code in place and watching the test fail, then restoring the code.
5. Proposed defaults recorded by each lane were not re-litigated. Where one looks wrong, or where the
   code does not match what a record states, it is under *Decisions to revisit*.

Severity: **P0** authority widening, security or data loss; **P1** wrong behaviour a person will
meet; **P2** minor, or a defence-in-depth gap.

## Findings

### H09 — Agent profiles

**H09-1 (P0) A project or task profile list replaced the Agent the person chose, which could widen
authority. Fixed in `08a5df1`.**
- *Where:* `server/native-work.ts:448` overwrote `input.agentId` with `profile.agentId` whenever a
  list resolved. `threadChoosesItsOwnModel` (`server/agent-profiles.ts:320`) looks only at the model
  and WorkStyle, and the Work start command's `agentId` (`server/app.ts:2344`) was dropped the same
  way.
- *Scenario:* a thread on `diomedes.reviewer` (ceiling `review`), a project list with a profile whose
  Agent is `auto`. The run resolved as `diomedes.builder` (ceiling `auto-review`), which also skips the
  Reviewer-ceiling guard that keeps a scope from applying its changes automatically. That breaks
  decision 7: a profile chooses intelligence, never authority.
- *Fix:* an Agent the person chose (thread `requested.agent` or the Work start command's `agentId`,
  anything but `auto`) keeps a task or project list out of the run, exactly as a chosen model or
  WorkStyle already did. A profile the thread itself picked is unchanged.
- *Tests:* `tests/agent-profiles-routing.test.ts` "a project list never replaces an Agent the thread
  chose for itself" and "a Work start that names its Agent is not overridden by a project list" (red
  on base: `expected 'diomedes.builder' to be 'diomedes.reviewer'`).

**H09-2 (P1) A damaged `agent-profiles.json` fell open. Fixed in `08a5df1`.**
- *Where:* `AgentProfileStore.load`, `server/agent-profiles.ts:163-169`. A parse failure blocked
  writes only; `routing()` then returned an empty list and the run took the pre-H09 route and model.
- *Scenario:* a project whose fallback-off list refuses a run (409). Truncate the file and restart:
  the same start returned 200 on another route and payer.
- *Fix:* when the file could not be read, resolution refuses with `409 profiles_unreadable` and the
  file's own sentence, and the file is left for the person to inspect.
- *Test:* "a profiles file that cannot be read refuses the run instead of falling open" (red on base).

**H09-3 (P1) Archived profiles could grow the file past the bound its own load enforces. Fixed in
`08a5df1`.**
- *Where:* `create` counted active profiles (`:205`); the file schema caps all records, archived
  included, at `PROFILE_MAX_PROFILES * 4` (`:111`). The 257th save succeeded and the next load
  refused the file, which then fell open (H09-2).
- *Fix:* `create` refuses in words at the file bound.
- *Test:* `tests/agent-profiles.test.ts` "archived profiles count toward the file cap…" (red on base).

**H09-4 (P1) A team wake was routed by the project list, which the record says does not happen.
Fixed in `08a5df1`.**
- *Where:* the member wake sets `memberThread.requested = null` when the member has no model
  (`server/app.ts:1284`), and `NativeWorkService.start` did not skip `input.team`, so a project list
  replaced the member's engine, model and Agent.
- *Fix:* profiles do not resolve for a team run (native Work start and the thread send path).
- *Test:* `tests/team-any-route.test.ts` "a member with no model of its own wakes on its own route,
  never on the project list" (red with the fix reverted: the list's model reached the generator).

**H09-5 (P2) A pinned profile was not held to its own digest on load. Fixed in `08a5df1`.**
- *Where:* `validateAgentResolutions`, `server/agents.ts:351-358`, compared engine, model and the
  fallback policy only. The pin carries every field the digest covers, so an edited `rules`,
  `effort` or `agentId` in `state.json` loaded with the original digest still naming it.
- *Fix:* the digest is recomputed from the pin and must match.
- *Test:* `tests/agent-profiles.test.ts` "editing any pinned field in saved state fails load…" (red
  on base).

**H09-6 (test adequacy) Nothing proved that dispatch uses the pin rather than the live profile.**
Making `requestedModel()` read the profile's latest revision passed all 26 H09 tests (reviewer's
mutation). Added "an edit while the run is in flight never reaches the dispatch it was admitted
for", which holds the generator on a gate, edits the profile to revision 2 mid-run and checks the
model, effort and rules actually sent. It passes on the base: the pin is immutable in practice.

**H09-7 (P2, not fixed) "`null` clears the task override" does not work over HTTP.** The route checks
`req.body === null` (`server/agent-profiles.ts:~498`), but `express.json()` in strict mode refuses a
bare `null` body with 400 before the route runs; only `{clear:true}` works. *Proposed patch:* drop
the `null` branch and the record's mention of it, or accept `{ "clear": true }` as the only form.

**H09-8 (P2, not fixed) A pinned effort can be lowered at dispatch with no record.** `effortFor`
(`server/native-work.ts:838`) caps a Fix run at the mode's ceiling, so a profile pinned at `xhigh`
may be sent lower. *Proposed patch:* record the sent effort beside the pinned one on the run and show
"Requested `xhigh`; sent `high` (Fix mode ceiling)" in run details (decision 8's spirit).

Checked and sound: the pin is a fresh clone (no shared reference), nothing re-resolves on recovery,
compare-and-set is serialised, fallback-off paths hold, archived profiles are refused as deleted, a
client cannot send a pin, availability reads host facts only, and `runtimeModelDifference` compares
exact strings.

### H21 — Migrations, crash matrix, perf gate

**H21-1 (P1) A prepared write in `pending/` bypassed the project version check. Fixed in `273cdd3`.**
- *Where:* `recover()`, `server/store.ts:1544`, passed `journal.state` to `persist()` with no
  `assertReadable`. `persist` spreads the state after the stamp (`:779`), so a `schemaVersion` inside
  the journal won.
- *Scenario:* a newer build killed after its journal append (the `journal-append` row) leaves
  `{…, schemaVersion: 2, futureField}`. This build's `init()` succeeded, persisted a version 2
  `state.json` and served `futureField`; the next start refused its own file. A pre-H21 build's
  journal likewise carried `schemaVersion: 1` into memory, against the record's "the version is not
  in memory".
- *Fix:* recovery runs the same `assertReadable(PROJECT_STATE)` on the journal's state and drops the
  field before replaying it. A newer journal stops recovery with the project file and the journal
  untouched, as a newer `state.json` already did.
- *Tests:* `tests/migrations.test.ts` "a prepared write from a newer Diomedes stops recovery…" and
  "a prepared write at this version never carries its file version into memory" (both red on base).

**H21-2 (P2) The backup was not byte for byte. Fixed in `273cdd3`.**
- *Where:* `server/migrations/files.ts:87` and `:48` read and compared the file as UTF-8 text.
- *Scenario:* invalid UTF-8 inside a JSON string (`0xff 0xfe`) became U+FFFD in the backup (59 bytes
  in, 63 out), and the original was then overwritten. The backup is the decision-10 evidence of what
  the file said.
- *Fix:* read, hash, back up and compare `Buffer`s. For valid UTF-8 the backup name is unchanged.
- *Test:* "the backup holds the original bytes, even when they are not valid UTF-8" (red on base).

**H21-3 (test adequacy) The "changed while it was carried forward" guard had no test.** Disabling it
passed all 41 migration tests. Added "a file that changed while it was being carried forward is not
overwritten"; with the guard disabled in place it fails, restored it passes.

**H21-4 (P2, not fixed) Three wired readers discard the migrated record.** `FileRunStore.read`
(`server/harness/run-store.ts:93`), the pack store (`server/pack-lifecycle.ts:235`) and the
definitions reader (`server/automation-definitions.ts:81`) call `migrateRecord` and keep the
unmigrated input. Harmless while every family is at version 1, but the first `n → n+1` step would be
silently skipped. *Proposed patch:* assign the result (`parsed = migrateRecord(FAMILY, parsed).record`)
in all three, and add a registry test that runs each `throughFramework` reader over a synthetic
older record once any family gains a step.

**H21-5 (P2, not fixed) Any migration failure marks an automation file unreadable with the wrong
reason.** `server/automations.ts:~175` catches every error from `openVersionedFile`, including an
I/O error writing the backup and "backup holds different bytes", and reports "written by another
version". *Proposed patch:* only a `MigrationRefusal` of kind `newer-version`/`unknown-version`/
`not-a-record` marks the file unreadable with that sentence; any other error is rethrown so the
service says what actually failed.

Checked and sound: backups go through the durable write (no torn backup under the right name); the
pre-H21 build opens a stamped `state.json`; nothing writes settings before the version check;
`recoverAndReload` checks versions; the crash matrix is not vacuous (each row asserts its `reached`
marker and the kill signal).

### P05 — Files drop and paste, previews, attachments, identity

**P05-1 (P1) A tiny workbook could hold the store lock for minutes. Fixed in `1c384a4`.**
- *Where:* `server/xlsx-preview.ts:107-159`. Every element was found with a lazy regular expression
  (`/<c\b([^>]*?)(?:\/>|>([\s\S]*?)<\/c>)/g` and the same shape for rows, shared strings, `<t>`,
  `<v>`, and attributes). For each unclosed tag the engine rescans to the end of the part, so the
  cost is quadratic, and the `/documents/sheet` route runs it under `store.locked`.
- *Scenario:* a row of `'<c>'.repeat(N)` compresses to about 1 KB. N = 20,000 took 0.6 s; the 8 MB
  part cap allows about 2.8 million, which blocks the event loop for hours, and reopening the file
  after a restart does it again. The review's test with N = 200,000 did not finish in 120 s on base.
- *Fix:* one forward `indexOf` scanner (`elements`) for every element and attribute; once no close
  tag follows, no later open tag is scanned for one. Same results for every existing workbook test,
  including a self-closed cell after a normal one.
- *Tests:* `tests/file-drops.test.ts` "a small workbook of unclosed cells, rows or strings is read in
  linear time" (unclosed `<c>`, `<row>`, `<t>`, `<v>` and unterminated attributes, 200,000 each,
  under 2 s) and "a self-closed cell after an unclosed one still reads, as it did".

**P05-2 (P1) The version a message sent disappeared from History after a quick second edit. Fixed in
`1c384a4`.**
- *Where:* `Store.writeRecorded`, `server/store.ts:~1390`, folds a person's edit into their last
  entry for the same file within 10 minutes, overwriting that entry's `after`. `versionBytes`
  (`server/file-drops.ts:218`) opens only versions History names.
- *Scenario:* save `notes.md` as A; send a message carrying it (`sourceVersions` names A); save B
  within 10 minutes. The chip's version now says "History has no record of this version", although
  the object is still stored.
- *Fix:* a person's edit is not folded into an entry whose version a Thread turn names. Folding
  otherwise is unchanged (tested).
- *Tests:* "a quick second edit does not fold away the version a turn referenced" (red on base) and
  "without a reference, a quick second edit still folds into one entry as before".

**P05-3 (P1, security-adjacent) The GIF pixel limit read only the logical screen. Fixed in
`1c384a4`.**
- *Where:* `gifSize`, `shared/file-drops.ts:153`, used by the drop check and the picture route.
- *Scenario:* `GIF_1X1` with its first image descriptor set to 65535×65535 was accepted and served as
  `image/gif`. Browsers grow the canvas to a frame that overruns the screen, so "refused before any
  window decodes it" did not hold for GIFs.
- *Fix:* `gifSize` walks the extension and image blocks and returns the furthest frame edge.
- *Test:* "a GIF whose first frame is larger than its declared screen is held to the pixel limit"
  (red on base: `{ width: 1, height: 1 }`).

**P05-4 (P2) Crash recovery recorded preserved picture bytes without the binary flag. Fixed in
`1c384a4`.**
- *Where:* the recovery conflict branch, `server/store.ts:1670`, saved the bytes as bytes but pushed
  an `outside` entry with no `binary: true`, so History would describe, and `restore` would try to
  write back, picture bytes as text.
- *Test:* "bytes that changed during an interrupted drop are recorded as binary…" (red on base).

**P05-5 (test adequacy) The bytes guard's text-and-bytes case had no test.** Narrowing
`store.ts:1342` to the actor check alone passed all 31 drop tests. The test now also refuses a write
carrying both `text` and `bytes`, and an approval-path bytes write; the narrowed guard fails it. (An
approval-path bytes write is also refused earlier by the receipt check.)

**P05-6 (P2, not fixed) Version order and deletions in the identity projection.** `versionsOf`
orders by first appearance, so after A→B→A it lists B as newest; `versionAt` ignores deletions, so a
turn sent after a delete resolves to the deleted version. *Proposed patch:* order versions by the
newest entry that recorded each sha, and let `versionAt` return null when the latest entry at or
before the turn deleted the file.

Checked and sound: every read goes through `relativeName`/`projectFile` and refuses links; the
picture route sniffs the type from bytes, sets `default-src 'none'; sandbox` and inherits `nosniff`;
SVG never reaches `<img>`; the version route requires a `{path, sha}` pair History recorded, per
project, hash-checked; a batch is checked before any write; collisions cannot overwrite
(`expected: null`); ZIP64 is refused; inflation is capped; the JPEG scan skips segments by length.

### Automations Milestone B

**AB-1 (P1) A slot that fell due between the last pass and a pause, edit or resume vanished. Fixed in
`0ab7286`.**
- *Where:* the pass window starts at `max(control.since, revision.at, newest covered)`
  (`server/automations.ts:1421`), and `changeSchedule` (`:1608`) moved `since` or `revision.at` to the
  act's time without settling slots already due.
- *Scenario:* daily 08:00 New York; a pass at 11:59:50Z; an edit (or a pause) at 12:00:05Z; a pass at
  12:00:20Z. Nothing was admitted and nothing was recorded — against "visibly records why it could
  not".
- *Fix:* a schedule act, already under the store lock, first beats and runs a pass under the schedule
  as it stood, so the due slot is admitted (a pause then records the run it did not stop, A10) or
  recorded. A pass that fails never blocks the act.
- *Tests:* `tests/automation-scheduler.test.ts` "a slot that fell due just before an edit is still
  admitted…" and "…just before a pause is recorded…" (both red on base).

**AB-2 (P1) A missed run named the wrong "last seen" time. Fixed in `0ab7286`.**
- *Where:* `previousSeenAt` was set once, in `AutomationHost.init`
  (`server/automation-definitions.ts:173`), and used for every missed slot (`server/automations.ts:1438`).
- *Scenario:* a laptop that sleeps with Diomedes running: the 29 and 30 September slots said "last seen
  Mon 28 Sep 2026, 7:50 a.m.." — the process start, earlier than a run that had happened; the true
  last heartbeat was 9:30 p.m. The sentence also ended with two full stops.
- *Fix:* `previousSeenAt` is the heartbeat before the latest one; `init` keeps the saved heartbeat
  until the first pass beats. One full stop.
- *Test:* "a slot missed while the running computer slept names when it was last seen…" (red on
  base). The existing restart test ("last seen … 8:00 a.m.") still passes unchanged.

**AB-3 (P2) A calendar day a zone skipped whole produced two slots at one instant. Fixed in
`0ab7286`.**
- *Where:* `slotsBetween` / `nextSlots`, `shared/automation-schedule.ts:248`, `:263`.
- *Scenario:* Pacific/Apia, daily 00:00, 30 December 2011 (skipped): both "12-30 (gap)" and "12-31"
  resolved to `2011-12-30T10:00Z`. `planDue` returned it as both missed and due, so an on-time run was
  recorded as "Missed — computer was off" and its admission replayed as a duplicate.
- *Fix:* one slot per instant; the day that exists keeps it.
- *Test:* `tests/automation-schedule.test.ts` "a skipped calendar day never makes two slots at one
  instant" (red on base).

**AB-4 (test adequacy) Three guards had no test.** Removing `revision.at` from the window start, and
moving the on-time or catch-up boundary by one millisecond, passed every scheduler and schedule test
(reviewer's mutations). Added "moving the time earlier the same day never runs the new, already-passed
time as a catch-up" (fails with `revision.at` removed, verified in place), "the on-time and catch-up
windows include their last millisecond and no more", and "a slot exactly at the moment a schedule was
turned on or edited is not its own".

Checked and sound, by running the pure functions: Lord Howe's 30-minute gap and overlap; midnight gaps
in Santiago, Havana, Beirut and Tehran; St John's half-hour offset; Troll's two-hour shift; Dublin's
negative DST; New York's repeated 01:30 (first occurrence); weekly slots on the local date; the
400-day cap.

### D5 — Codex remembered approvals and the task scope's account

**D5-1 (P1) A task scope bound the account of a declined proposal, then covered it after a switch.
Partly fixed in `f01c958`; the rest is a proposed patch.**
- *Where:* `accountRouteSeen`, `server/trust/scope-grants.ts:150`, took the latest Need with a
  connection, declined ones included, and never reads the account Codex is on now.
- *Scenario:* propose under account A and decline; Codex switches to B; confirm the scope. It bound A.
  B's next proposal asked with a false reason, and a switch back to A was covered. The record's
  default 4 says "stale knowledge can only cause an extra ask, never a wrong cover".
- *Fix here:* only a waiting or approved proposal supplies the account. The reported scenario now
  asks on both accounts, and confirming again on the waiting proposal binds the account in use.
- *Still open:* approve under A, switch to B, confirm with no proposal waiting: the scope still binds
  A. *Proposed patch:* bind only a proposal that is waiting when the scope is confirmed, else record
  `codex:chatgpt` ("no account seen"), so the first proposal asks once and confirming on it binds the
  account. That changes proposed default 4 and one existing test's expectation ("a task scope still
  decides first…" expects A bound after an approval), so it is Andrew's call; see *Decisions to
  revisit*.
- *Test:* `tests/remembered-approvals-codex.test.ts` "a scope confirmed after a declined proposal on
  another account never covers that account" (red on base).

**D5-2 (P2) Saved evidence validated when re-pointed at another grant for other files. Fixed in
`f01c958`.**
- *Where:* `validateRememberedAuthorization`, `server/trust/remembered-approvals.ts:862`, tied the
  evidence to a grant and to the Need's account but never to the Need's own file set.
- *Scenario:* grants G1 (`Fall menu.md`) and G2 (`Specials.md`), same account; a menu proposal covered
  by G1; in a copy of the state, re-point the evidence and its History entries to G2. Load
  validation passed, so History attributed a menu write to the Specials grant. (The Store funnel would
  still refuse a pending write by its subset check.)
- *Fix:* the Need's own pattern (`patternForProposal`) must be the grant's pattern.
- *Test:* "covered evidence re-pointed at a grant for another file cannot authorize" (red on base).

**D5-3 (test adequacy) Nothing held the team-member and route checks in evidence validation.**
Replacing them with `false` passed all 14 tests (reviewer's mutation). Added "covered evidence on a
team member's session or a non-Codex session is refused on load"; it fails with that mutation,
verified in place. Not added: a test that a team member's run is never counted or offered, and one
that the task's account outranks the project's latest (the reviewer's M1 and M3). Both are cheap

**D5-4 (P2, design) Files that run code are rememberable.** `classifyProposal`
(`shared/remembered-approvals.ts:~590`) holds back SVG, HTML and XML only. `deploy.sh`, `run.ps1`,
`x.bat`, `app.js`, `package.json`, `.github/workflows/ci.yml` and `AGENTS.md` are rememberable after
three clicks. The v2 task scope has the same boundary. Not changed here: see *Decisions to revisit*.

Checked and sound: proposal paths are normalised and case-folded for duplicates; a case difference
makes a different pattern (an ask, not a cover); `.htm`, `.xhtml`, `X.SVG` and `credentials.JSON`
ask; `Need.connection` is set only by native Work; the Reviewer ceiling runs before any scope or
remembered approval; harness and direct grants never cross.

### P06 — Diffs, partial keep, review comments

**P06-1 (P2, near P1) A comment on a change drifted when the same run wrote the file again. Fixed in
`e01d7bb`.**
- *Where:* `ReviewComments.add`, `server/review-comments.ts:120`, accepted a comment on a change whose
  run was still working. `writeRecorded` folds a session's writes into one entry, so the change id
  stays while `after` moves, and the Console places comments by change id and line.
- *Scenario:* comment on line 3 ("Soup $8") while S1 works; S1 inserts a line. The comment shows
  beside "Starters", and a revision sends "change 1, line 3" for the wrong line.
- *Fix:* a change whose run is queued, working or waiting takes no comment yet (409, in words) —
  partial keep already refuses that state.
- *Test:* `tests/review-diffs.test.ts` "a change whose run is still writing it takes no comments yet…"
  (red on base).

**P06-2 (P2) A comment chosen twice was sent twice. Fixed in `e01d7bb`.**
`revise` (`:207`) did not de-duplicate `commentIds`; it now does. Test: "a comment chosen twice is sent
once" (red on base).

**P06-3 (P2, not fixed) Line-ending and final-newline changes make hunks with no visible difference.**
`splitLines` strips `\r` (`shared/text-diff.ts:125`) while `diffLines` compares with it, so a CRLF→LF
change shows "3 added, 3 removed" with identical text, and `Tea $2` → `Tea $2\n` is removed and re-added
looking the same; the hunk evidence sha (`server/change-review/partial-keep.ts:114`) hashes text
without the ending. *Proposed patch:* keep the line ending on `DiffLine` (`eol: '\n' | '\r\n' | ''`),
mark a line whose text is equal but ending differs as "line ending changed" / "no newline at end of
file", and include the ending in the hunk sha.

Checked and sound: 20,000 randomised before/after pairs (CRLF, missing final newline, empty lines,
one-sided hunks) through `buildDiff` and `applyHunkSelection`: keep-all is `after`, keep-none is
`before`, and a single kept hunk yields exactly that one hunk. The server recomputes hunks from
recorded objects, checks `after` against the entry, writes with `expected` under the lock, and quotes
comments from the recorded text; a version sha opens only for its own path. Eight mutations of these
guards were each caught by the existing tests.

## Decisions to revisit (Andrew's; not changed here)

1. **D5 default 4 (task scope account).** Its stated invariant, "stale knowledge can only cause an
   extra ask, never a wrong cover", does not hold while the account is taken from an approved
   proposal that was not waiting (D5-1, still open). Proposed: bind only a waiting proposal's account,
   else "no account seen".
2. **D5 always-ask boundary.** "Can run code when it is opened" is applied to SVG, HTML and XML only.
   Scripts, CI workflows, `package.json` and the project's own instruction files (`AGENTS.md`,
   `CLAUDE.md`, which steer later runs, decision 14) are rememberable. Proposed: add instruction files
   and executable or CI files to the always-ask list for both remembered approvals and the v2 scope.
3. **Automations B default 16 vs the code.** Section 3 says items other than missed ones clear "when
   the schedule is turned on again"; enable and resume clear `blocked` items only (a `skipped` or
   `failed` item stays until a clean run or Mark as seen). Section 2 describes the narrower behaviour.
   One of the two should be corrected; the code's narrower behaviour is the safer one.
4. **P06 version comments ride by path.** A version comment on a file the task changed may be sent
