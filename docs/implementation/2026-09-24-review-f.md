## Method

1. Read each lane's non-merge commits and the files its record lists: the driver
   (`claude-session-run.ts`), the Claude session transport (`claude-session.ts`), the Console
   controls (`NativeSessionControls.tsx`, `native-session-view.ts`, `DiomedesHome.tsx`), the
   interaction route changes, the ACP client and session (`acp-client.ts`, `acp-session.ts`), the
   engine-ask broker (`engine-asks.ts`), and restart recovery.
2. Looked for the classes of defect the work order names: races between a queued turn, a steer
   and a Stop; Stop escalation when the child does not cooperate; promises that never settle or
   settle twice; a session offered as resumable when its state is not proven; an engine ask
   resolved by anything but a person; untruthful attribution (decision 8); and a fact or control
   said in two places (decision 4).
3. Reproduced every suspicion with a scratch test through the real transport: the scripted
   stream-json child for Claude Code, and the ACP fixture agent process for Cursor and Devin.
   Only reproduced defects are listed as findings. For each one a permanent test was written
   first, run red on the unchanged code, then the fix was made and the test run green.
4. Mutation testing: key guards in both features were changed one at a time, the feature's tests
   were run, and every surviving mutant was either closed with a test or recorded below.

A second, independent pass over H05 ran in parallel. Its findings were re-checked here before
being accepted: F5 to F7 were re-run as permanent tests, and F8 was reproduced from its scratch
test.

## Findings

Severity: **P0** means authority, security or data loss. **P1** means wrong behaviour a person
will hit, or a false record. **P2** means a narrower truthfulness problem, a robustness problem,
or a gap in the tests.

### H03

**F1 — P1. A Stop on a steered message Claude Code is already answering says "withdrawn" and
stops nothing.** `server/harness/claude-session-run.ts`: `sendSteers` did not mark an H08 `steer`
entry as `sending` while its turn ran, though it did mark an H03 queued turn. So `stop()`'s
`withdraw()` still found the entry `pending` and cancelled it: "Withdrawn by Stop before it was
sent." It answered `stop: "withdrawn"` while the turn kept running (`busy: true`). `closeAll()`
did the same thing to an entry already in flight, telling its caller "Diomedes closed before
this message was sent."

- Scenario: send a turn with `[slow]`. Steer `four` behind it with `[hang]`, and wait until
  `four` reaches the child. `interruptCommand('four')` returned `withdrawn`, and the child was
  still answering.
- Fix, commit `c9a2b22`. A steer entry is marked `sending` when the drain hands it to `request`,
  so it becomes the running turn, which Stop interrupts. `cancelSteers` no longer touches an entry
  in flight, because its own turn settles it.
- Tests in `tests/h03-claude-live-controls.test.ts`, "H03 review F": "Stop on a steered message
  Claude Code is already answering…" and "Diomedes closing while a queued message is being
  answered…". Both were red, and both are green.

**F2 — P1. A Stop before anything reaches Claude Code retires a healthy conversation.**
`server/engines/claude-session.ts` `run()`. Any abort of the turn's signal ran
`this.controller.abort()`, which ends the process, even before the message was written to stdin.
During the per-turn account recheck the saved state is still `idle`, so `stop()` answered
`SESSION_IDLE` and the driver aborted the turn. The recheck then threw a raw `AbortError`. The
catch block marked the session `uncertain` and closed it. The run became `reconcile_required`,
the page read "Couldn't resume. This operation was aborted" (a DOMException message), and the
next message was refused. Yet nothing had been sent. This also broke the H03 record's claim that
"the dropped request does stop that turn gracefully" for that window.

- Scenario: a live session with a 500 ms account check. Send, then Stop at 100 ms.
- Fix, commit `c9a2b22`. Before dispatch, an abort refuses only that turn, as `stopped()`, and
  leaves the process and the `idle` checkpoint alone. A Stop while the request is being recorded
  reverts the request and the `busy` state before throwing. `stop()` reports `SESSION_IDLE` until
  the message is actually on stdin, so an unsent turn is never force-killed or reported as
  `STOP_FORCED`.
- Test: "a Stop before anything reaches Claude Code keeps the live session…". It was red, and it
  is green: the turn is interrupted, continuity reads `live`, the next message goes to the same
  process, and the child never saw the stopped message.
- Not covered by a test: the window between the `busy` save and the write to stdin. It is a
  single `await` of a local persistence call.

**F3 — P2. An interrupt Claude Code never acknowledges is recorded as a plain stop whenever the
grace exceeds 5 s.** `claude-session.ts` `interrupt()`. The acknowledgement timeout (5 s) ended
the process without setting `forced`. When the Stop grace was longer than 5 s, the turn failed
as `CANCELLED` ("The request was stopped…") and continuity repeated that sentence, even though
Diomedes had ended the process. With the app's default grace of 5000 ms, the grace timer was
registered first and won the tie, so production was correct only because of that ordering.

- Test: "a Stop Claude Code never acknowledges is recorded as forced, whatever the grace". It
  uses the new fixture mode `[deaf]` and a 5.5 s grace. It was red, and it is green with the fix.
- Fix, commit `c9a2b22`. The acknowledgement timeout sets `forced`, so the turn fails as
  `STOP_FORCED`.

**F4 — P2, decision 4. After a forced stop the page said the same thing three times.** The
notice read "Claude Code did not stop in time, so its process was ended…" (`DiomedesHome.tsx`,
`STOP_FORCED`). The session line's state read "Couldn't resume". Its detail began "Couldn't
resume." again and went on to "…did not stop when asked, so its process was ended…".
`tests/h03-claude-controls.spec.ts` asserted all three.

- Fix, commit `9a4a917`. The session line is derived from the record, so it keeps the fact and
  the notice goes. `sessionLine` also drops the repeated "Couldn't resume." from the detail.
- Tests. `tests/native-session-view.test.ts` now expects the detail without the prefix; it was
  red, and it is green. The spec now asserts that "process was ended" and "Couldn't resume" each
  appear exactly once. That is a changed expectation, not a removed one.

**F5 — P2, test gap.** Removing the 8-message limit on queued conversation turns failed no test.
Commit `e7e903c` adds "at most 8 messages wait; the ninth is refused…", which kills that mutant,
and pins that two Stops for one turn get the same answer.

Checked and sound in H03:

- The order of a queued turn and a steer behind the same running turn. The drain sets `active`
  synchronously, so no other request can take the slot between turns.
- A Stop on the turn ahead cascades to everything waiting. A Stop while a queued turn is draining
  interrupts that turn and cancels the rest.
- One graceful Stop is shared between the route and a dropped caller.
- The Windows tree kill (`killOwnedProcess`: `taskkill /T /F`, then waiting for the exit) is not
  changed by H03.
- Attribution names only the runtime-reported model (`Claude Code · <reported>`). The requested
  alias is never shown as attribution.
- The H08 Stop menu and the H03 queue never render on the same thread.

### H05

**F6 — P1, authority. A go-ahead for one fetch was re-granted without asking, for any
address.** `server/engines/acp-client.ts`, `acpReadTurn`. `judge` accepted a fetch without web
access whenever its `toolCallId` was in `approved`, and `permit` then auto-selected `allow_once`
for any later `session/request_permission` that passed `judge`. So once a person approved call
`X` for `https://example.com/a`, the agent could ask again for `X` with another URL and be
allowed without a person being asked. The Need's own promise is "Go ahead allows exactly this call
once." A fetch can carry project content out in its query string.

- Scenario: fixture mode `fetchtwice`. The person says go-ahead to the first ask and no to the
  second. Before the fix only one question was asked, and the agent heard "first allow second
  allow".
- Fix, commit `ccbdcd9`. `permit` never auto-allows a fetch without web access, so each ask goes
  to a person. `approvedCalls` now records the address the person was shown, and `judge` accepts
  an approved call only at that address.
- Test in `tests/acp-session.test.ts`, "review F": "a go-ahead for one fetch is not re-granted…".
  It was red, and it is green.

**F7 — P1. A question outlived its agent.** In `acp-client.ts`, `answerLater` pushed the ask into
`replies`, and `close()` waited for every reply. The ask settled only on a person's answer, the
10-minute expiry, or the turn signal. The agent exiting or ending its prompt set none of these.
So the turn hung until the expiry. Meanwhile the Need stayed `open` and `EngineAskNeeds.resolve`
still accepted a go-ahead, recording it for a process that no longer existed.

- The independent pass reproduced this with the real broker: "resolve on dead process →
  go-ahead".
- Scenario: fixture mode `crashask` asks, then exits after 200 ms.
- Fix, commit `ccbdcd9`. The client owns an `asksEnded` signal. It is aborted by `fail()`, which
  covers the child exiting, a timeout and a protocol error, and by `close()`, which covers the
  turn ending. `acp-session.ts` passes it with the turn signal to the person's ask, so the broker
  expires the Need ("cancelled") and nothing more can be sent.
- Test: "an agent that dies while a question is open ends the turn and the question with it".
  Before the fix it took 8 s and hit the test's own fallback; now it takes well under 5 s and the
  ask's signal is aborted.

**F8 — P2, decision 8 (the record). A Stop while a question was open always recorded
`lastStop: "killed"`.** The cancelled ask carried `stop`, and `answerLater` called `fail(stop)` at
once. `fail()` saw a pending cancel wait and set `stopOutcome ??= "killed"` before the agent could
answer `session/cancel`. The checkpoint and the error then said the process was killed even when
the agent acknowledged.

- Fix, commit `ccbdcd9`. While a Stop waits for the agent's answer, a question the Stop cancelled
  leaves the turn to that wait.
- Test: "a Stop while a question is open, which the agent acknowledges, is recorded as
  acknowledged". It was red, and it is green.

**F9 — P2, test gaps, closed.** Mutation testing found two gaps, both closed in commit `ccbdcd9`:

- An expired or cancelled question could have sent the agent `allow` and no test would fail. The
  new test "a question nobody answers tells the agent it was cancelled, and never selects an allow
  option" reads what Diomedes wrote on the agent's stdin.
- Removing the restore checks on engine, scope or CLI version failed no test. The new test is "a
  saved session is continued only on the engine, scope and version it was saved with".

The mutants for these checks are now killed.

**F10 — P2, not fixed (proposed patch). A restart before the `busy` checkpoint is saved leaves
the run parked instead of resolved.** `claude-session-run.ts` `recover()` returns early unless
the saved checkpoint is `busy`. A kept ACP turn saves `busy` only in `beforePrompt`, after launch,
initialize, `session/load` and `set_model`. A restart inside that window leaves the run
`reconcile_required` with an `idle` checkpoint. The next message starts again (conservative), and
the thread reads "Diomedes stopped while Cursor was answering, so that answer's outcome is
unknown". In fact the prompt was provably not sent. The H05 record says the other cases are
"cancelled with couldn't resume"; this one is parked, not cancelled.

- Reproduced by the independent pass with a fixture whose `session/load` never answers.
- Nothing unproven is offered, so this is not a safety defect. The fix would change shared
  restart recovery for Claude Code too, so it is proposed rather than made. Proposed patch: in
  `recover()`, when `saved?.state === 'idle'` and the interrupted step is a `turn:` step, the
  prompt was never dispatched, because both transports save `busy` before writing it. Reconcile
  that step as not sent (`reconcileInterrupted(..., 'Diomedes restarted before this message was
  sent. It was not sent.')`) and keep the saved idle checkpoint, so continuity reads `resumable`.
  When there is no checkpoint at all, `runs.cancel` the run with the "couldn't resume" sentence.
  Test with an ACP fixture whose `session/load` never answers, restart inside it, and expect
  `resumable` followed by a resume by native id.

Suspected in H05, not confirmed:

- A replayed `current_mode_update` or `config_option_update` during `session/load` still reaches
  Devin's mode and model handlers (`devin.ts`). `rpc.replaying` drops only the history kinds. If
  live Devin replays these updates, an earlier process's history could satisfy the ask-mode check
  or overwrite `turn.model`, which is used for attribution. Whether it does is unknown. Proposed:
  ignore mode, config and model updates while `replaying`.
- A turn that fails without a Stop, on an agent that can load, returns to `idle` with no
  continuity note (`acp-session.ts`, the catch in `run`). The next turn loads a session whose last
  prompt may be half-recorded. Proposed: set a `lastFailure` note that the next turn's continuity
  line reports once.

Checked and sound in H05:

- `allowForTask` is refused.
- Neither an expiry nor a cancel ever becomes a go-ahead.
- A second answer is refused with 409, and an answer through another project gets 404.
- `expireOpen` runs at startup.
- Remembered approvals and scope grants never decide an engine ask.
- A load refusal other than "session not found" is a failure.
- Edit and command asks are never put to a person.
- Replayed text arriving after the load reply fails closed.

Remaining surviving mutants, recorded as test gaps:

- Any other load refusal starting fresh (no test drives a non-`-32002` refusal).
- The `!finish` dead-waiter check in `resolve` (only reached after `expireOpen` in tests).
- `reconcileInterrupted` accepting any effect.
- A non-`cancelled` `stopReason` after a Stop.
- In H03, sharing one Stop across callers (`stopping ??=`). This mutant is equivalent at the
  observable level: a second `session.stop` joins the pending interrupt.

## Verdicts

- **H03, Claude Code live controls: ACCEPT WITH FIXES.**
  - The queue, cascade, restart and continuity design holds up under adversarial ordering.
  - Two P1 defects made Stop report the wrong thing or retire a healthy conversation (F1, F2).
  - A P2 made a forced kill read as a plain stop at longer graces (F3).
  - A P2 said the forced stop three times on the page (F4).
  - All four are fixed with tests, and the fifth gap is closed.
- **H05, kept Cursor and Devin ACP conversations: ACCEPT WITH FIXES.**
  - Session load and restart resume never offered a session they could not prove.
  - The engine-ask path had one P1 authority defect: a person's go-ahead was re-granted
    automatically, for any address (F6).
  - A P1 left a question answerable after its agent died (F7).
  - A P2 recorded an acknowledged Stop as a kill (F8).
  - All three are fixed with tests, and the mutation gaps are closed.
  - F10 and the two suspected items are proposed patches.
  - Neither feature is DONE: live acceptance against real Claude Code, Cursor and Devin, and
    packaged qualification, are still open, as both records say.

## After integration (batch 7)

Integration batch 7 (#123, `67df53f`) merged this branch at `ddd2e68`. In that merge,
`tests/h03-claude-live-controls.test.ts` kept `world(stopGraceMs = 400)` alongside main's
`boot(recover, stopGraceMs = 5000)`. `boot`'s own parameter shadows `world`'s, so the F3 test
("…recorded as forced, whatever the grace") ran with a 5 s grace instead of 5.5 s. At 5 s the grace
timer wins the tie and nothing exercises the acknowledgement timeout.

A mutation run on `main` confirms it. Removing `this.forced = true` from the acknowledgement
timeout left all 15 tests passing. On this branch the same mutation fails the test.

This branch's follow-up:

- passes the grace through `boot(false, 5500)`;
- waits on the fixture's `received()` rather than on fixed pauses, as main's `c2a4b15` does for
  the other H03 tests;
- gives the Stop-before-dispatch test a 2 s account check, so on a slow runner the Stop still lands
  before anything is sent.
