## What was missing

H16's engine landed and its firings show in the run inspector's Supervision section, but a person
using the app could not use it:

- rules were written only through `PUT /api/stream-rules` and `PUT /api/projects/:id/stream-rules`;
  there was no Console rule editor (H16 record, "Known gaps");
- rules watch only work loop runs (`diomedes-loop`, H13), and nothing in the Console started one;
  `POST /api/projects/:id/loop/start` existed with no Console control (H13 record §6, `QUESTIONS.md`
  O23, whose default was "no Console start control").

## Audit

- `server/app.ts`: the four stream-rules routes call `StreamRuleService.list` / `setRules`, which
  validate with `streamRuleSetSchema` (so `patternProblem` and the hold/steer/message refinements),
  refuse an equal-authority contradiction (`409 stream_rule_conflict`) and a project rule H11 would
  block (`409 stream_rule_loosens`), and return `{ organization, project, resolution }`. Errors reach
  the client as `{ error: <sentence>, code }`, and `client/api.ts` raises that sentence unchanged.
- `server/native-loop-routes.ts`: `startSchema` needs `protocolVersion`, `commandId`, `taskId`,
  `goal`, `route`; `admitRoute` accepts the scripted route (`native-fixture`) and the four model-API
  routes, refuses anything else with `loop_route_unsupported`, then checks on-in-Settings, consent,
  the project's sharing grant and the route's own admission (`harness.loop.admit`, which reads the
  connection, model, credential and spend cap and never sends). A replayed command id returns the
  same run.
- `client/console/LoopInspector.tsx` is shown by the thread's run inspector for any loop run on the
  task, and `Supervision.tsx` already shows firings; nothing there needed to change.
- `ProjectInstructions.tsx` (H11) is a one-line indication in the thread head with a panel;
  Settings already has a **Rules** section ("How work is bounded"); the task's work panel in its
  thread (`Ledger.tsx`, "This thread's work") carries the task's Board and Team actions.
- History: project configuration decisions are History entries attributed to the person (turning a
  pack on or off, `server/capability-packs.ts`), only when something changed. Settings writes
  (`PUT /api/settings`) are not recorded in History, which is per project.

## What shipped

### 1. Rule editor (`client/console/TriggerRules.tsx`, `trigger-rules-model.ts`, `trigger-rules.css`)

One component, at one authority, in two existing places (decisions 1, 13, 14: no second surface):

- **Organization rules**: Settings > Rules, under "How work is bounded", headed "Trigger rules" with
  one sentence on reach ("a project rule can add to it or tighten it, never loosen it").
- **Project rules**: a line in the thread head directly under Project instructions,
  "Trigger rules · 1 watches this task · 1 project · 0 organization" (the count is the server's H11
  resolution for the thread's task), opening a panel with the organization's rules read-only and
  the project's rules editable (`ProjectTriggerRules.tsx`). The line is present in every project
  thread, including where no instruction files exist, so a person can find it.

A person can list, add, edit, turn on or off, and delete rules. The form covers every field the
schema allows: the rule id; what it is for (`text`); what it watches — a phrase or a pattern in
streamed text (with case sensitivity, and the pattern's window up to 512) or a proposed tool call
(tool name with the loop's tools as suggestions, any of the five H12 effect classes, and a
project-relative target file or folder); the intervention (annotate, steer, hold for you, stop, each
with what it does); the correction message (shown for steer, and whenever one is set so it can be
cleared); the task it is limited to (a project's tasks by name; an organization rule takes a task
id); the requirement key `constrains` (under "Requirement key", with what it means: two rules meet
only on the same key, and a project rule on an organization rule's key can tighten it and never
loosen it); and on/off.

**Validation is the server's.** A save sends the authority's whole set through `PUT`; the client
builds the declaration exactly as typed and refuses nothing (a test proves a hold on streamed text
is sent as typed). A refusal is shown in the form verbatim: the pattern grammar's sentence, "Only a
tool intent can be held for you; …", the `stream_rule_loosens` reason, a conflict. A changed rule
carries the next version (and toggling makes one), so a firing's version names the declaration that
fired; an unchanged save keeps it. Deleting asks once, and says the firings it recorded stay.

In a project view each rule carries the server's resolution for this task, as returned by `GET`:
"Governs · Governs trigger:…", "Blocked · reports-held (organization) restricts … and this cannot
loosen it.", "Overridden · …", "Off · Turned off.", or "Not this task · Limited to another task."

**Reach, said once.** Each editor opens with one sentence, derived from the server's new `watches`
field: "Trigger rules watch Nectovia work loop runs only. Runs on Codex, Claude Code, OpenCode and
other external engines use their own tools and are not watched." (The product's on-screen name
comes from `AGENT_NAME` under the name contract; the loop's own inspector is labelled "Nectovia
work loop", so this slice uses the same words.)

**History (decision 8).** A project's rule write is recorded in its History as the person's:
"You changed this project's trigger rules: added reports-read-first v1. A rule grants nothing." —
naming each rule added, changed, turned on or off, or removed, only when the write changed
something, and nothing for a refused write. Organization rules are written in Settings, and Settings
writes are not recorded in History, so an organization write is not either (proposed default 3).

### 2. Start a work loop run from the Console (`client/console/LoopStart.tsx`, `loop-start-model.ts`)

In the task's thread, the work panel ("This thread's work") gains **Loop run** beside Board and
Team. It opens "Start a Nectovia work loop" for that task:

- **Routes**: only those the server says it would admit now, from a new read,
  `GET /api/projects/:id/loop/routes`, which runs the start route's own admission (on in Settings,
  then `harness.loop.admit`: connection, model, credential, spend cap) for the scripted route and
  AWS Bedrock, Azure OpenAI, OpenRouter and Google Vertex AI, and returns each refused route with
  its sentence. The dialog lists those under "Not offered (n)" with the server's reason. The read
  admits, sends and records nothing. The scripted route is labelled "Scripted demonstration (a fixed
  local script, no model)".
- **Goal**: the task's statement (its description, else its name). **Files it reads**: the task's
  own document, or the files its name and description name (`selectTaskSources`, as Work does),
  editable. **Turns**: H13's default (8), up to 16; left out of the command unless changed.
- **Consent**: on a route that sends, a checkbox "Send the goal and the files it reads to …";
  sharing and every other refusal come back from the start route and are shown verbatim.
- One dialog is one command id, so a second click or a resend names the same run.

The started run appears in the thread's existing run inspector (LoopInspector), where Supervision
shows its firings. Nothing claims the loop is live-proven. H13's start contract is unchanged; no
Trust interface was touched.

## Proposed defaults (conservative; Andrew's to confirm)

1. **Where a loop run starts (answers `QUESTIONS.md` O23 provisionally):** from the task's work
   panel in its thread ("Loop run"), one task at a time, one lead with no team. H14 teams, delegate
   routes and apply scope are not offered from the Console; they stay API-only.
2. **The scripted route is offered** in the dialog, labelled as a fixed local script with no model,
   because the server admits it on every installation; it is the only way to try a rule without a
   model-API route set up. Hiding it outside tests is the alternative.
3. **Organization rule writes are not recorded in History**, as no Settings write is; the firings
   carry each rule's digest and version. A project's rule writes are recorded as the person's.
4. **A rule's version is bumped by the editor** when its declaration changes; the server does not
   yet refuse a changed rule that keeps its version.
5. **New project rules default to the thread's task** ("Applies to: Only <task>"); the person
   widens it to every task in the project.

## Known gaps / follow-ups

- Rules still watch only work loop runs; external engines are not watched (the editor says so).
- The **Loop run** control is in the architect view's work panel; the Conversation view hides that
  panel, so it has no start control there.
- Review G's P2 findings 6 and 7 are untouched: no budget for unbounded patterns, and rules read from
  disk are not re-validated. An invalid hand-edited rule is listed as it is, and a save that keeps
  it is refused with the server's sentence. Finding 8 is half done: the reads carry `watches` and
  the editor states the reach; the resolution's "Governs …" reason itself is unchanged.
- The start dialog's route list is read when it opens; a route turned on meanwhile needs the dialog
  reopened.
- Steer still does not reach a loop run (H16 record); the editor offers steer because the schema
  allows it, and Supervision says "Correction not sent" when it fires.
- No live provider run, packaged build or device proof.

## Release notes input (for the 0.2.0 notes)

You can now write trigger rules in the app: in Settings, Rules, for every project, and from a line under Project instructions in a thread, for one project or one task.
A rule watches what a Nectovia work loop run streams or the tool call it proposes, and can note it, ask the run to correct, hold the call for you, or stop and ask you.
A project rule can add to or tighten a rule written for every project, never loosen it, and the app shows you the reason when it refuses one.
You can start a Nectovia work loop run on a task from its thread, choosing only routes that are ready, and watch its rule firings in the run's Supervision section.
Rules watch Nectovia work loop runs only; work on Codex, Claude Code, OpenCode and other engines is not watched.
