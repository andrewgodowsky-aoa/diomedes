## 6. A budget for unbounded patterns

An unbounded pattern rescans its whole window on every delta, so its cost grows with the window
squared per delta, not per chunk. H16's grammar admitted 64 such rules at the full 512-character
window, in each of the two authorities.

`streamRuleSetSchema` now refuses a set whose unbounded patterns watch more than
`STREAM_RULE_LIMITS.unboundedWindow` characters in total:

> Patterns with *, + or a long repeat may watch 1024 characters in total; shorten a window or use a
> phrase.

- **Unbounded** (`patternUnbounded`) means a `*`, a `+`, a `{m,}`, or a counted repeat above
  `longRepeat` (32). A long count scans as far as a star does: `x{1,500}` at window 512 costs the
  same as `.*`. Escaped characters (`c\+\+`) and characters inside a class (`[+*]`) are literal
  text and are not counted. Phrases and bounded patterns fail fast at each start, so they are not
  counted.
- **The value is Andrew's to choose; the conservative option is taken.** The budget is 1024 per
  authority, so organization and project rules together (the evaluator runs both) stay within
  2048, the figure review G measured. It is per authority so a project's rules can never use up
  the organization's share.
- **Measured here** with 128 rules, 20-character deltas and a full carry, every unbounded rule
  failing at every start: median **1.27 ms** per delta at the cap (two 512-window `.*!` rules per
  authority). H16's admitted worst case was **25.5 ms** (64 per authority) and **55 ms** (both
  authorities full).

Tests (`tests/h16-rule-budget.test.ts`, 3): what counts as unbounded; the cap, refusal sentence and
what is not counted; the heaviest sets both authorities may write, built by adding rules until the
schema refuses, cost under 5 ms per delta. Red on `90f23fa`: the helper did not exist, 64 unbounded
rules were admitted, and the heaviest admitted sets cost 32.5 ms per delta.

## 7. Rules read from disk are re-validated and fail closed

`StreamRuleService.authored` read `settings.json` and project state as stored. A hand-edited rule
skipped the schema, grammar and budget, and a pattern that is not a regular expression threw a raw
`SyntaxError` inside the watch.

Each authority's stored rules are now held to `streamRuleSetSchema`, the same check a write through
the rules API passes, wherever they are read (`readLayer`). A layer that fails is refused, not
trimmed: dropping a rule would silently loosen what someone wrote.

- **A run the rules would watch fails closed.** The model step's watch, or a tool intent's
  admission hook, throws `stream_rules_unreadable` before the model is called or the intent is
  admitted:
  "A project trigger rule (hand-edited) on disk is not one Nectovia can run: <the schema's
  sentence> Fix or remove it through the rules API; until then no run it would watch goes ahead."
  The loop fails the run on that first attempt, before any provider call.
- **The rules read lists the stored layer as it is**, with `unreadable: [{ authority, ruleId,
  message }]` and no resolution, so the person sees which rule to fix. The Console's rule editor
  shows that sentence under its reach line.
- **A project write waits** (`409 stream_rules_unreadable`) while the organization's rules cannot be
  read, because they decide what a project rule may loosen. An organization write replaces the
  stored layer and is how it is fixed.

Tests (`tests/h16-rules-on-disk.test.ts`, 3): a project rule edited into finding 3's exponential
shape fails the run before any tool, naming the rule (red: the run went on to its write approval); an
organization rule in `settings.json` whose pattern is not a regular expression fails closed with
that sentence (red: `Invalid regular expression: /secret(/`); an over-budget organization layer is
listed with the reason, a project write is refused and an organization write fixes it (red: a full
resolution, no `unreadable`).

## 8. "Applied" says which runs it governs

`GET /api/projects/:id/stream-rules?taskId=` answered `applied · Governs trigger:<id>.` for a task
on any route, while H16 watches only work loop runs. The applied reason now names the reach, from
one shared constant (`STREAM_RULE_REACH`): "Governs trigger:<id> on Nectovia work loop runs." What
is not watched is said once per screen by the editor's reach sentence, not on every rule
(decision 4). H11's own resolver (`shared/rule-authority.ts`) is unchanged; the stream-rule
resolution rewrites its sentence, as it already did for rule names.

Test: `tests/h16-rules-on-disk.test.ts`, "the resolution for a task names the runs an applied rule
governs" (red: "Governs trigger:writes-held."). The Console's two decision-line assertions
(`h16-console-model.test.ts`, `h16-console.spec.ts`) now read the new sentence.
