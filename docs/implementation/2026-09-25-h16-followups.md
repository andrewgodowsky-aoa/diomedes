## 6. A budget for unbounded patterns

An unbounded pattern rescans its whole window on every delta, so its cost grows with the window
squared per delta, not per chunk. H16's grammar admitted 64 such rules at the full 512-character
window, in each of the two authorities.

`streamRuleSetSchema` now refuses a set whose unbounded patterns watch more than
`STREAM_RULE_LIMITS.unboundedWindow` characters in total:

> Patterns with *, + or a long repeat may watch 1024 characters in total; shorten a window or use a
> phrase.

- **Unbounded** (`patternUnbounded`) means a `*`, a `+`, a `{m,}`, or a counted repeat above
  `longRepeat` (32). A long count scans as far as a star does: `x{1,500}` at window 512 costs the
  same as `.*`. Escaped characters (`c\+\+`) and characters inside a class (`[+*]`) are literal
  text and are not counted. Phrases and bounded patterns fail fast at each start, so they are not
  counted.
- **The value is Andrew's to choose; the conservative option is taken.** The budget is 1024 per
  authority, so organization and project rules together (the evaluator runs both) stay within
  2048, the figure review G measured. It is per authority so a project's rules can never use up
  the organization's share.
- **Measured here** with 128 rules, 20-character deltas and a full carry, every unbounded rule
  failing at every start: median **1.27 ms** per delta at the cap (two 512-window `.*!` rules per
  authority). H16's admitted worst case was **25.5 ms** (64 per authority) and **55 ms** (both
  authorities full).

Tests (`tests/h16-rule-budget.test.ts`, 3): what counts as unbounded; the cap, refusal sentence and
what is not counted; the heaviest sets both authorities may write, built by adding rules until the
schema refuses, cost under 5 ms per delta. Red on `90f23fa`: the helper did not exist, 64 unbounded
rules were admitted, and the heaviest admitted sets cost 32.5 ms per delta.

## 7. Rules read from disk are re-validated and fail closed

`StreamRuleService.authored` read `settings.json` and project state as stored. A hand-edited rule
skipped the schema, grammar and budget, and a pattern that is not a regular expression threw a raw
`SyntaxError` inside the watch.

Each authority's stored rules are now held to `streamRuleSetSchema`, the same check a write through
the rules API passes, wherever they are read (`readLayer`). A layer that fails is refused, not
trimmed: dropping a rule would silently loosen what someone wrote.

- **A run the rules would watch fails closed.** The model step's watch, or a tool intent's
  admission hook, throws `stream_rules_unreadable` before the model is called or the intent is
  admitted:
  "A project trigger rule (hand-edited) on disk is not one Nectovia can run: <the schema's
  sentence> Fix or remove it through the rules API; until then no run it would watch goes ahead."
  The loop fails the run on that first attempt, before any provider call.
- **The rules read lists the stored layer as it is**, with `unreadable: [{ authority, ruleId,
  message }]` and no resolution, so the person sees which rule to fix. The Console's rule editor
  shows that sentence under its reach line.
- **A project write waits** (`409 stream_rules_unreadable`) while the organization's rules cannot be
  read, because they decide what a project rule may loosen. An organization write replaces the
  stored layer and is how it is fixed.

Tests (`tests/h16-rules-on-disk.test.ts`, 3): a project rule edited into finding 3's exponential
shape fails the run before any tool, naming the rule (red: the run went on to its write approval); an
organization rule in `settings.json` whose pattern is not a regular expression fails closed with
that sentence (red: `Invalid regular expression: /secret(/`); an over-budget organization layer is
listed with the reason, a project write is refused and an organization write fixes it (red: a full
resolution, no `unreadable`).

## 8. "Applied" says which runs it governs

`GET /api/projects/:id/stream-rules?taskId=` answered `applied · Governs trigger:<id>.` for a task
on any route, while H16 watches only work loop runs. The applied reason now names the reach, from
one shared constant (`STREAM_RULE_REACH`): "Governs trigger:<id> on Nectovia work loop runs." What
is not watched is said once per screen by the editor's reach sentence, not on every rule
(decision 4). H11's own resolver (`shared/rule-authority.ts`) is unchanged; the stream-rule
resolution rewrites its sentence, as it already did for rule names.

Test: `tests/h16-rules-on-disk.test.ts`, "the resolution for a task names the runs an applied rule
governs" (red: "Governs trigger:writes-held."). The Console's two decision-line assertions
(`h16-console-model.test.ts`, `h16-console.spec.ts`) now read the new sentence.

# H16 on external engines

Before this slice, trigger rules watched only work loop runs. `StreamRuleService.owner` needs a
harness run with a task and a Session, and no external route has one. Claude Code, OpenCode, the
ACP routes and model-API Work run as `engine-text-turn` runs with no task or Session, and Codex
Work is not a harness run at all. Branch `feature/stream-rules-external-engines`.

## What a Work request on an external engine passes through

Work on an external engine is a proposal. The engine's own file, shell and web tools are off, its
answer is the change it proposes, and only the person's approval (or a scope they granted) writes
it. The answer streams back through Nectovia before it can become a proposal, so it can be
watched on every route. `server/stream-rules/work-watch.ts` wraps the Work generator:

- The watch is opened per Work request (`StreamRuleService.watchWork`). Its owner is the Work
  run's Session, which is the request id.
- Codex hands over its raw `item/agentMessage/delta` text. The engine-service routes hand over
  their preview frames (`onPreview`), whose secrets are already removed. Those frames were always
  produced and bounded, so listening adds no new failure mode.
- Steer and stop go to H15 supervision at once, which acts through H08 on the Work run. Steer goes
  natively where the route steers a running turn (Codex), and falls back to Queue elsewhere. Stop
  cancels the request mid-stream.
- Before the answer can become a proposal, the watch ends on the whole answer. A route that
  streamed nothing is judged on its final text. A stop that supervision could not apply refuses the
  answer (`trigger_stopped`), so no proposal is made from it.
- A model-API team member's Work turn runs the team tools itself through `RunService.step`.
  `owner` now follows that run (`model-api-team-work`) to the Session named by its command id, so
  a tool rule judges a team tool call at admission, exactly as on a loop run.

Firings name the run and step the text streamed in: the text route's `textRunId` and
`text:dispatch`, the team turn's `teamWorkRunId` and `answer`, or `codex-work-<session>` and
`codex:turn` for Codex. Codex Work has no harness run, so its Session is the record of it.

## What is watched, and what is enforced

| Route (task Work) | Text rules see | Stop | Steer | Tool rules |
|---|---|---|---|---|
| Work loop runs (H13, any loop route) | every delta | enforced (H08 Stop; refused at the model step otherwise) | recorded; H08 Steer/Queue refused on loop routes (see below) | enforced at admission (hold, stop) |
| Codex | raw deltas | enforced mid-stream (H08 Stop aborts the turn); answer refused otherwise | enforced natively (`turn/steer`) where the installed Codex offers it | not watched: Codex runs its own tools (`approvalPolicy: never`); MCP team tools are not RunService steps |
| Claude Code, OpenCode, oh-my-pi, Cursor, Devin | preview frames, secrets removed | enforced mid-stream; answer refused otherwise | H08 Queue (no native steer on these text routes; not exercised by these tests) | not watched: tools run inside the engine |
| Bedrock, Vertex, Azure, OpenRouter (no team) | preview frames, secrets removed | enforced mid-stream; answer refused otherwise | H08 Queue (not exercised by these tests) | none are offered (`tools: []`) |
| Model-API team member | final answer only (the turn does not stream) | answer refused before it becomes a proposal | H08 Queue | enforced at admission for the team tools Nectovia runs |
| Kept conversations, Home, Ask/Plan | not watched: not task work | no | no | no |

A text rule that looks for a secret may not fire on the preview-frame routes, because the secret
is already gone from that text. The editor's reach sentence says so.

The resolution's applied reason now depends on the rule's kind. A text or pattern rule gets
"Governs trigger:<id> on what the model writes in Nectovia work loop runs and in task work on
every engine." A tool rule gets "Governs trigger:<id> on the tool calls Nectovia runs itself."
`watches` is `['diomedes-loop', 'external-work']`, and the editor's sentence follows it.

## Steer does not reach a loop run (unchanged; what is missing)

- `server/harness/route-contract.ts` (`HARNESS_COMMANDS`) declares steer unsupported on the loop's
  harness routes. No `WorkControlDriver` with `steer` is registered for them in
  `server/durable-controls.ts`, so H08 refuses Steer there.
- The fallback, H08 Queue, delivers a follow-up as a new Work run on the run's route.
  `WorkControl.queue` refuses a loop route (`server/work-control.ts`: "<route> is not a route this
  build can use"), because loop routes are not Work routes.
- A native loop steer needs three changes. First, a durable mailbox on the loop run: a recorded
  event, so replay stays deterministic. Second, `NativeLoop` reading that mailbox into its message
  list before the next model step. Third, a registered steer driver plus a changed contract and
  H08's pinned per-route table. That is H08/H13 work, not a small change, so it is left. A steer
  rule on a loop run is recorded and shown as "Correction not sent".

An annotate rule on  fired with  on , and the Work run completed. Codex stopped before sending anything ("The native Windows sandbox could not start"). No model-API key is reachable without copying connection secrets, so model-API routes have no live proof.
