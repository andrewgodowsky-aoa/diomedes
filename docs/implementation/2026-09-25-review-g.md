## Method

1. Read the code against each question in the review brief (matching, hold before admission,
   authority, interventions, ending, restart, races, attribution, the Console).
2. For every suspected defect, write a test through the real host (`createApp`, scripted loop route)
   or at unit level, show it red on H16's code, fix the defect minimally, and show it green.
3. Measure what the evaluator actually costs, rather than trusting the record's figures.
4. Mutation pass: break each safety-relevant line one at a time and run the H16 suites (21 mutants;
   script in the session scratchpad). Every surviving mutant is either explained as equivalent or
   closed with a new test.

### 1. P0: a delegate's, or an H14 worker's, tool intents skip every trigger rule

**Evidence.** The loop's delegate child run is started with `sessionId: null`
(`server/harness/capabilities/native-loop.ts:592`). `StreamRuleService.owner` returns `null` for any
run without a Session (`server/stream-rules/service.ts:291`), and the hook returns before looking at a
single rule. A second defect sits behind it: the child's tools go through `ToolRegistry.dispatch`,
whose H12 declaration for a reader names no targets (`targets: []`), and `facts` trusted that empty
list (`service.ts:305`), so a target-scoped rule could never match anyway.

**Consequence.** A person writes "hold any read of `delivery.md` until I say so". The loop hands
`delivery.md` to a helper, and the helper reads it: no hold, no firing, no record. The contents go
back to the parent and on to its model route. This breaks H16's headline invariant ("a tool intent a
trigger matches never runs before the person answers"). The H16 record also says the opposite
("NativeAgent turns (… the loop's delegate child) are judged at tool admission").

**Red.** `tests/h16-stream-triggers.test.ts`, "review-g: a hold on a read the loop hands to a delegate
still holds; the helper never reads it". On H16's code the child's `read_project_file` step is
`succeeded`, with "Delivered 94 napkins. Six napkins short." in its output.

**Fix** (`c021c57`, `e4398e0`). `owner` follows a run with no Session to its parent: `parentRunId`,
or the child input's `parent.runId`. It stops at four levels, and only within the same project and
task.
The firing records the child's run and step under the parent's Session, which is where H15 reads it,
so supervision pauses the parent through H08 Stop. The parent's abort cancels the child, and the
hook refuses the child's intent if the cancel hasn't landed yet. When a declaration names no
targets, `facts` judges the paths the input names. Green; mutating either half back turns the test
red (mutants 8 and 9).

**H14 (landed on main after H16 was written).** A lead's worker and advisor runs
(`server/harness/capabilities/team-loop.ts:408`) also start with `sessionId: null`, under their own
input kinds, so the first fix, keyed on the delegate's kind, still missed them. Red: "review-g: a hold
on a read an H14 lead hands to a worker still holds; the worker never reads it". The lead went on to
its write approval after the worker had read `delivery.md`. `e4398e0` follows any child input's
`parent.runId`, and the test is green. The H14 suites (`tests/h14-*.test.ts`) still pass.

### 2. P1: a tool rule's target can be dodged by spelling the path another way

**Evidence.** `targetMatches` (`service.ts:86`) compared the raw spelling from the tool input, only
stripping a leading `./`. The readers resolve that input through `relativeName`, which turns `\` into
`/`, and the file system then ignores case on Windows and macOS, which are the platforms Diomedes
ships on. So a model asking for `ledger\june.md` or `LEDGER/June.md` reads the file a `ledger/` rule
guards, and the rule never matches. Decision 11: a path is judged by what it resolves to, not by how
it is spelled.

**Red / green.** `tests/review-g-h16.test.ts`, "a target is judged by what it resolves to" (both
tests). Mutant 10 (drop `relativeName`) turns them red.

**Fix** (`c021c57`). Both the target and the rule's target are compared in the form `relativeName`
resolves them to. Case is folded where the platform's file names ignore case (`win32`, `darwin`);
the fold is a parameter, so both behaviours are tested on every platform. Folder rules still bound
what they cover (`ledgers/…` is not under `ledger/`).

### 3. P1: the pattern grammar admits exponential backtracking

**Evidence.** `patternProblem` refused a choice group only when the group itself was repeated
(`shared/stream-rules.ts:133`), and allowed one variable quantifier (`:144`). Choice groups in
sequence are not repeated, but each one doubles the paths tried at every start position:

| Pattern (all admitted by H16's grammar) | Input | Time |
|---|---|---|
| `(a\|a)` × 14 then `b` (71 chars) | 200 `a`s, one chunk | 197 ms |
| `(a\|a)` × 18 then `b` (91 chars) | same | 1,020 ms |
| `(a\|a)` × 20 then `b` (101 chars; limit is 200) | same | **9,046 ms** |
| `(a\|a…16 ways).*b`, 64 rules | 4 KB | 7,345 ms |

The evaluator runs synchronously inside the provider's delta callback, so a stall blocks Node's
event loop: every project, every run and every HTTP request, not one stream. The haystack is model
output, so a prompt-injected model can supply the worst-case text. A rule "someone authored" is the
brief's own threat model.

**Fix** (`c9b1451`). A group that chooses, `(a|b)`, counts as a place the pattern varies, alongside
`*`, `+`, `?` and `{m,n}`. The existing "varies in one place at most" rule then refuses sequential
choices, nested choices and a choice beside a repeat, and still admits one choice group
(`(foo|bar|baz) now`), a top-level alternation (`rm -rf|drop table`) and one repeat (`x.*y`). The
worst admitted choice shape is one group of as many ways as fit, failing at every start. With 40
distinct ways (184 characters), 64 rules and a 4 KB chunk, it takes 3.4 ms; the test uses 60 ways and a
1-second bound. Red then
green: `tests/review-g-h16.test.ts`, "the pattern grammar bounds backtracking". Mutant 16 turns it
red. H16's own refusal list still passes.

### 4. P2: a case-folded phrase records the wrong span and quotes the wrong text

**Evidence.** `server/stream-rules/evaluator.ts:44` searched `hay.toLowerCase()` and used the index
it found in `hay`. `toLowerCase` is not length-preserving (`İ` becomes two code units), so every match
after such a character was recorded a little later than it was, and the firing's excerpt, which is
the evidence of what matched, quoted the wrong text. Red: in "İstanbul İzmir: the API KEY is here",
sent whole, "api key" was recorded at 22–29 rather than 20–27.

**Fix** (`fcf7c12`). A case-insensitive phrase compiles to an escaped regular expression with the
`i` flag. The engine's simple case folding maps one code unit to one, so offsets are the text's own.
The window is still the phrase's length. A second test sends accented text and an astral character
(`🔥`) split at every code-unit boundary, and finds them once at exact offsets. It passed before and
after; surrogate pairs were already handled.

### 5. P2 (test adequacy): the refusal behind a tool stop or hold had no test

**Evidence.** When a rule's escalation is already open on the task, H15 raises nothing new and does
not pause the next run. What then keeps the intent from running is the hook's own
`throw new HarnessError('trigger_stopped', …)` (`service.ts:356`). H16 tests this case for text stops
only. Replacing the throw with `return` (mutant 5), or dropping the ungated-hold branch so the hold
goes to the approval gate (mutant 4), left every H16 test green.

**Fix** (`5c8f3e3`). Two tests, "a tool stop / hold whose escalation is already open on the task
still refuses the next run's intent", kill both mutants. The same commit adds "two stop rules firing
on one run pause it once and ask the person once": one H08 Stop and one open Need. H16 had no double
escalation; this pins that down.

### 6. P2: pattern cost at the grammar's limits is well above the record's figure (proposed)

The record says "64 rules including the slowest shapes the grammar admits … median under 100 ms". The
test behind it (`tests/h16-stream-evaluator.test.ts:113`) is 62 phrases and two slow patterns.
Measured here with 64 × `.*!`, window 512: about 500 ms per 4 KB chunk, and **16 ms per 20-character
delta**. Each delta rescans the whole ≤ 511-character carry, so cost scales with window², not with
delta size. At provider speeds (about 50 deltas a second) that is most of the event loop. It is
bounded, not exponential, so this is a limit to set rather than a defect to patch, and it is
Andrew's to choose. Proposed patch, in `streamRuleSetSchema.superRefine`:

```ts
// Unbounded patterns rescan their whole window on every delta; keep their total small.
const heavy = set.rules
  .filter((rule) => rule.match.kind === 'pattern' && /[*+]|\{\d+,\}/.test(rule.match.pattern))
  .reduce((sum, rule) => sum + (rule.match as { window: number }).window, 0);
if (heavy > 2048)
  ctx.addIssue({ code: 'custom', message: 'Patterns with * or + may watch 2048 characters in total; shorten a window or use a phrase.' });
```

Measured at that cap (four full-window `.*!` rules): about 1 ms per delta. The evaluator test should
then measure the cap itself (all heavy rules at their limit), and the record should quote that figure.

### 7. P2: rules read from disk are never re-validated (proposed)

`readSettings` and `readProjectState` load `streamTriggerRules` as stored, and
`StreamRuleService.authored` (`service.ts:154`) uses them without `streamRuleSchema`. A hand-edited
file bypasses the grammar (finding 3's patterns come back), and an invalid pattern makes
`new RegExp` throw inside `watch`, so every loop run on the installation fails with a raw
`SyntaxError`. Dropping an invalid rule would silently loosen what someone wrote, so the fix should
fail closed and say why. That is a product choice. Proposed patch:

```ts
private authored(state: Pick<ProjectState, 'streamTriggerRules'>): AuthoredStreamRule[] {
  const read = (rules: unknown[] | undefined, authority: StreamRuleAuthority) =>
    (rules ?? []).map((raw) => {
      const parsed = streamRuleSchema.safeParse(raw);
      if (!parsed.success)
        throw new HarnessError(
          'stream_rules_unreadable',
          `A ${authority} trigger rule on disk is not one Diomedes can run (${parsed.error.issues[0]?.message}). Fix or remove it through the rules API.`,
        );
      return { rule: parsed.data, authority };
    });
  return [...read(this.store.settings.streamTriggerRules, 'organization'), ...read(state.streamTriggerRules, 'project')];
}
```

`list()` would catch the same error and return it, so the person can see which rule to fix.

### 8. P2: resolution says "applied" where nothing is watched (proposed)

H16 watches only the Diomedes loop. It says so in its record, and the Console shows firings, which
only exist on loop runs. But `GET /api/projects/:id/stream-rules?taskId=` returns
`outcome: 'applied', reason: 'Governs trigger:…'` for a task whatever route it runs on. The API is the
only place rules are written, so a person guarding a Codex or Claude Code task is told the rule
applies when those engines run their tools themselves and H16 never sees them. Proposed patch: in
`resolveStreamRules`, the applied reason reads `Governs ${key} on Diomedes loop runs. Work on an
external engine runs its own tools and is not watched.`, and `list()` returns
`watches: ['diomedes-loop']`, so a future rule editor states the reach once (decision 4).

### Checked and found sound

- **Split matches.** A phrase split at every boundary, one-character chunks, and 1024-character
  slices are all handled; so are surrogate pairs and accents split at every code unit (finding 4's
  second test). Overlapping matches report once per rule per stream, by design. The carry never
  exceeds the longest window less one.
- **Nothing fires after the stream ends.** The evaluator is inert after `end()`. `NativeLoop` awaits
  `watch.end` before acting on the answer, and a text stop fails the step (`trigger_stopped`) or the
  aborted signal refuses it. Provider deltas are exactly the answer's `text-delta`s
  (`server/engines/model-api-core.ts`), so the "final text only when nothing streamed" fallback
  leaves no gap.
- **Admission.** The hook runs at the top of every `RunService.step`: first dispatch, retries and
  replay after a restart. A held gated step keeps no remembered approval (D5). A `trigger_stopped`
  model step is not retried (one attempt, one firing, probed).
- **Authority.** `resolveRules` keeps the strongest-authority rule governing each key, so a project
  rule on the same key is overridden or blocked and never replaces the organization's rule. A project
  cannot disable one. Project state and settings live under the data folder, not the project folder.
  The loop's only write is the fixed report path. `page_fetch` refuses loopback and private addresses
  and only issues GETs, so no agent or model can author or disable a rule.
- **Interventions.** No output or tool input is rewritten; the model-API adapter hands the same delta
  to both sinks. Steer falls back to H08 Queue and says "Correction not sent" where the route refuses.
  Stop goes through H08, and the parent's abort cancels a delegate. Firings are append-only and
  idempotent, and carry a canonical sha-256 digest of the rule. Two stop rules on one run make one
  Stop and one Need (finding 5's test).
- **Attribution and the Console** (decisions 2, 4, 5, 8). Firings are Diomedes supervision
  application actions. A supervision record that only acts on a firing is folded into the firing's
  row. Machine strings wrap or truncate where they are written.

## Mutation pass

21 mutants over the evaluator, service, RunService gate, bridge, loop, grammar, resolution and
detector. After the tests above, 19 are killed. Two survive, and neither is a gap:

- `end > boundary` → `>=` (evaluator): equivalent. A rule fires once, so a match ending exactly at
  the carry's edge was already reported by the previous slice.
- The immediate `handOff` on the tool path removed: the hook still refuses the intent when the run
  isn't cancelled, and the store's `change` schedules supervision moments later. The immediate
  hand-off buys latency, not safety.

Dropping `signal.throwIfAborted()` after the watch survived the first pass. It is defence in depth:
a cancelled run refuses the next step's commit anyway.

## Verdict

**ACCEPT WITH FIXES.** H16 is carefully built. Incremental matching, hold-at-admission through
`RunService`, H11 precedence, H15's ladder and the append-only record all hold up under adversarial
reading. But as submitted it let a delegate read what a hold guarded, and on today's main an H14 worker too
(P0), let a path spelling slip
past a target rule (P1), and let one authored pattern freeze the server (P1). With `c021c57`,
`e4398e0`, `c9b1451`, `fcf7c12` and `5c8f3e3`, those are fixed and tested. Findings 6–8 are P2 follow-ups whose
patches are above: a budget for unbounded patterns, fail-closed validation of rules read from disk,
and stating the watched routes in the resolution. None blocks 0.2.0. Canonical documents and
QUESTIONS.md are untouched; the H16 record's canonical-doc patch still stands, and its sentence about
the delegate child is now true.
