## 1. Product decision

A Bot is a persistent, recognizable representative of a workspace or business. It has a name, an accountable human owner, a clear job, an approved voice, scoped knowledge and supported ways to receive work. It can answer, prepare a plan, delegate bounded tasks, follow an authorized routine and return a checked result. Its identity persists when the underlying model changes.

Implement a Bot as a deployment and presentation of existing Agent contracts, not a new agent engine. A Bot references a lead Agent and optionally a Team. A Project contains its authorized work and evidence. An Automation defines a recurring responsibility. A Connector provides supported access to a system. A Channel carries a conversation. None of those objects grants permission merely by existing.

The visible personality matters: people should recognize the same point of contact, not configure a different model for every request. Personality does not imply a human employee, unlimited memory, authority, certainty or an independent consciousness. Make the AI identity clear and allow a person to take over.

Example proposed roles: an operations bot checks deliveries and prepares the management brief; a project bot keeps approved job notes and outstanding decisions together; a marketing bot prepares drafts in the company's voice. Roles are configurable examples, not industry forks or evidence of working integrations.

## 2. What the research supports

Primary pages accessed September 20, 2026. These observations describe published behavior, not independent reliability benchmarks.

**OpenClaw:** persistent agent workspaces, per-agent sessions, deterministic channel/account/peer routing and child runs are useful mechanisms to study. Its security model explicitly assumes one trusted boundary per gateway. Different agent identities or workspaces are not hostile-tenant isolation. Borrow explicit routing and bounded delegation, not a claim that a shared gateway safely hosts unrelated clients. [S1-S3]

**Grok Bot:** the official page emphasizes named Bots with jobs, parallel collaboration, retained context, demonstrated routines and computer access. Its FAQ says a user's Bots share one persistent cloud computer, including files, browser and logins; isolation is per user, not per Bot. That is a product/deployment choice, not the correct boundary for all Diomedes business roles. The page does not establish an embeddable Bot API or independently measured completion and uptime. [S4]

**Hermes:** current profiles documentation includes Bot Mode with named profiles, roster presentation and persistent Bot Chat. Therefore, the distinction is not that Hermes lacks bots. Diomedes should make business responsibility, company ownership, scoped information and verifiable work easier to configure and inspect. [S5]

**Channel transport:** evaluate Vercel Chat SDK for one channel rather than writing every adapter. It normalizes transport and provides state/locking facilities, not Diomedes task authority. In particular, force-releasing a lock does not cancel the existing handler. A transport lock is not proof of single execution. Validate the exact adapter, version, license, platform contract and durable state implementation before adoption. [S6-S8]

Three approaches were considered: embedding another bot runtime, building everything from scratch, and composing native Bots with a thin supported transport. Recommend native composition. Embedding adds a second execution/authority boundary; rebuilding every adapter wastes effort. Computer use remains a bounded worker capability when an API or deterministic operation cannot do the job.

## 4. Configuration and setup

A proposed versioned Bot configuration contains references, not copies of every existing contract:

- Stable Bot identity, workspace/organization, revision, name, optional approved avatar, job, accountable owner and lifecycle configuration.
- Lead Agent, optional Team, allowed worker roles, explicit Project targets, capability packs and business rules.
- Approved knowledge-source sets with provenance, audience, freshness and access scope. No raw secrets.
- Tone/language/response preferences and human-handoff wording, below operational rules and policy.
- Channel installation/account bindings, audience restrictions and permitted inbound/outbound modes.
- Allowed execution host and model-route policy references, budget account, deadlines, concurrency/delegation limits and verification requirements.
- Commercial entitlement reference, separate from permission and budget.

Saving creates a draft. Activation checks owner, target, source rights, route, host and entitlement. Rehearsal uses test data or explicitly approved read-only data. An edit creates a new revision; admitted work keeps its revision unless an authorized checkpoint changes it. Rollback cannot revive departed members, revoked access, credentials or spent budget.

Internal operations and public-facing Bots are separate deployments by default. Sharing voice or a name never means sharing private retrieval, browser sessions, secrets or raw worker output. A high-privilege worker returns only an authorized projection to a lower-privilege conversation.

## 5. Conversation to completed work

1. Authenticate the transport and installation. Persist the accepted inbound event before acknowledging durable acceptance. Verify signature, freshness/replay and size rules for the exact platform. Signed content is still untrusted content.
2. Resolve tenant and Bot from server-owned bindings, not user-supplied tenant IDs, display names or a claim to be the owner. For direct messages, scope continuity by tenant, Bot deployment, channel installation and verified participant. For groups, include channel/thread scope and explicit audience visibility; a privileged participant does not grant every reader that privilege.
3. Resolve intent and permitted context. A simple recorded lookup should not invoke a model or spawn a worker. A conversation does not automatically authorize an effectful task.
4. Admit work through the existing task/RunService path with source-event, Bot, conversation, accountable owner and Project references. Missing authority becomes an existing Need. Keep source facts, user instructions, retrieved material and standing policy distinct.
5. Dispatch only useful, bounded jobs. Each child gets a goal, source references, required artifact/schema, completion criteria, deadline, budget reservation, cancellation lineage and narrower authority. Proposed initial defaults: at most two active children per Bot and one delegation level, with a separate workspace-wide cap. These are implementation-review defaults, not existing provider limits.
6. Observe real Runtime events, inspect returned evidence and verify the result. A child claiming completion is not a verified outcome. Parent progress comes from records, not invented percentages or repeated status-polling model calls.
7. Recheck current authority before an effect or outward reply. Use the existing effect record and a durable outbox where transport needs one. Record provider identifiers and distinguish submission, delivery, failure and uncertainty according to actual provider evidence.

Event deduplication and business-effect identity are different. A retried webhook must not admit another task; an edited message is a new event that may supersede earlier intent. A provider timeout after acceptance is an uncertain effect requiring reconciliation, not automatic retry. Local leases fence local records, not an already-issued network effect. Do not promise universal exactly-once delivery.

Human takeover suppresses queued/future bot replies in that conversation until authorized handback. It neither erases running work nor proves an issued action was canceled. A bare 'yes' is not a consequential approval unless authenticated, bound to the exact unexpired action and accepted by Trust. Bot-to-bot communication needs provenance, bounded hops and loop prevention.

## 6. Learning, knowledge and warmth

Keep approved business facts, reviewed procedures, private conversation continuity and proposed lessons separate. Reuse existing source/memory machinery. A customer message cannot become company policy; an employee's access cannot become perpetual Bot access.

Learning follows observation, candidate revision, evaluation/rehearsal, human-governed activation and rollback. Repeated successful work may support a person's decision to promote a particular procedure. Model confidence, JEV confidence and successful repetitions never grant permission themselves.

The current site PRODUCT.md expressly excludes external messaging, spending money, paying people and access changes from unattended promotion. Preserve that boundary. The first customer-facing slice drafts replies for approval; independent customer replies require a later explicit policy amendment and proof. This does not block an internal Bot carrying out already-authorized work.

Use a warm, direct voice without fabricated familiarity or certainty. Example response: 'The invoice and order match, but the delivery note is missing the received quantity. I left that comparison open and drafted a question for the manager.' A task needing someone is a recorded Need, not a promise that a human is currently watching.

## 7. Deployment, paid service and efficiency

First proof: one internal Bot, one Project, approved file inputs, a worthwhile delegated child and a verified saved draft. Then add one authenticated channel in an owned test workspace; shared Automations and host support follow their accepted prerequisites. Customer channels, voice/SMS and computer use are distinct later proofs, not one toggle.

A cloud model is not an always-on computer. Hosted availability requires an actual execution host, durable work storage, protected credentials, supervision and an independently observable health path. A sleeping desktop is unavailable. Show timestamped health and recover missed work through the shared Automations semantics. Host migration needs ownership fencing and external-effect reconciliation.

Managed Bot deployment is a reasonable paid capability: business setup, maintained knowledge/procedures, hosted operation, supported channels, usage and operational support. Exact tier, count and price remain an owner decision; do not invent them. Preserve the strong free local/BYO harness, published licensing rights and shared basic safety. Pause/stop, evidence and resolution of uncertain effects remain available after downgrade. Do not charge an extra public 'request' for each internal worker call where the pricing authority counts the user's job once.

Route lightweight conversation to an eligible fast model and difficult work to an eligible stronger route. Data policy, authority and payer stay fixed unless explicitly changed. Use deterministic routing, source checks and progress events. Do not keep a model running simply because the Bot is available.

Use stable versioned instruction/tool prefixes. Provider prefix caches are not portable across models. A model-agnostic artifact cache can reuse an eligible deterministic result only when tenant, permissions, source versions, policy and freshness match; it must never reuse an approval as new authority. Preserve provider-bound native conversation history and opaque blocks in their own lineage; transfer plain facts/artifact references between models, not private reasoning.

Reserve for lead, children, correction, review and allowed retries together. Include provider/tool/message/voice/hosting costs in cost per verified job. Unknown cost is not zero. Compare against a single Agent and deterministic implementation; delegation is not automatically cheaper or better.

## 8. Acceptance and measurement

The paired work orders contain B01-B36, required scenarios rather than passed tests. Measure verified completion, unsupported claims on a labeled set, duplicate effects, authority failures, recovery, human interventions, first useful response, final result latency and total cost. Report actual median/tail values only from named runs. Do not infer ROI, zero hallucinations or an SLA from a demonstration.

Before production use: verify the actual channel/provider terms, permissions, recipient consent and opt-out handling where relevant, tenant isolation, retention/deletion policy, incident handling and offboarding. Voice adds interruption, transcription uncertainty and duplicate-turn handling; a text adapter does not prove telephony.
