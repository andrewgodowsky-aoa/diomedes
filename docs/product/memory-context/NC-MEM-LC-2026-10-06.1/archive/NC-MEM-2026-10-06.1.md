# Nectovia: governed memory, temporal knowledge, and bounded consolidation

**Design ID:** NC-MEM-2026-10-06.1  
**Research date:** October 6, 2026  
**Status:** Architectural recommendation and implementation handoff; not implemented, tested, merged, deployed, or an approved change to commercial terms.  
**Repository snapshot inspected:** `andrewgodowsky-aoa/diomedes` at `8d49f10c45ef2f0f15bb72229d8a1eeb06284d8c`.

## 1. Recommended decision

Build one Nectovia-owned memory service inside the existing Core/Runtime/Trust architecture. Reuse Agent Memory Repo's openly licensed format and reference behavior as an interoperability surface. Do not make a shared Git repository the permission boundary, authoritative business database, or multi-agent task scheduler.

The design has four complementary parts: source-backed durable memories; permission-aware retrieval; bounded consolidation of new evidence; and human-readable, portable projections. A graph is useful for relationships and provenance, but is not itself evidence that a statement is true.

The product promise should be: Nectovia can explain what it retained, where it learned it, which scope it applies to, whether it remains current, and how a person can correct or remove it. “Better than other harnesses” remains an evaluation objective, not an established finding.

## 2. What was actually released

Cognition's Agent Memory Repo is an open specification, a reference skill, and Devin plugin packaging. The published concept includes periodic consolidation called Dreaming. The inspected reference skill does not install scheduling or automatic startup. It works when invoked, defaults to local storage, and refuses autonomous resolution of a divergent Git history. It should not be described as the complete production Dreaming service. [E1–E4]

The format organizes Markdown entries behind a short `MEMORY.md`, optional metadata, and root-relative wiki links. This is a linked-document graph, not a supplied typed business-entity database or a turnkey authorization engine. [E2]

The repository carries the MIT license. A shipped adaptation must retain the applicable copyright and permission notices; exact dependency and artifact versions still need a release review. This research did not copy or install a third-party runtime. [E4]

### Useful comparisons, not a vendor ranking

| Reference | Useful design lesson | Nectovia adoption decision |
|---|---|---|
| Agent Memory Repo | Portable, inspectable linked notes and a deliberately small entry point. | Adopt the exchange format and reference compatibility tests. |
| Graphiti | Validity-aware temporal relationships and hybrid retrieval. Its runtime has additional database and model requirements. | Borrow temporal semantics; benchmark an optional backend rather than mandate it. [E5–E6] |
| Hindsight | Separate retention, recall, and reflection; retrieve through multiple strategies. | Borrow the separation and compare as an optional backend behind Nectovia's contract. [E7–E9] |

Graphiti's inspected repository license is Apache-2.0; Hindsight's is MIT. Neither license answers every dependency, hosting, customer-data, or deployment question. Do not install both simply to combine their feature lists. [E10–E11]

## 4. Sources of truth and memory categories

Use different handling for different information, even if one API exposes it.

| Category | Authoritative location | Memory's role |
|---|---|---|
| Working state | Existing Task/Run/Step records | Recover interrupted work; never invent completion. |
| Episodic experience | Source run, tool receipt, user correction | Preserve what happened, when, and how it was verified. |
| Stable facts and definitions | Attributed source-backed claims | Retain company vocabulary, entity mappings, enduring decisions. |
| Preferences | Explicit user or appropriately authorized organization preference | Apply at the correct person/team/project scope. |
| Procedures | Approved, versioned skill/playbook | Remember a reusable method with preconditions and verification. |
| Live operational data | Authorized source system, with freshness and physical-observation limits | Query current stock, schedules, balances, prices, and status. |
| Enforced policy | Existing Trust, account/permission, funding, and configuration authorities | Memory may explain a policy but may not create or weaken it. |

For example, retain the distinction between “available stock” and “on-hand stock,” the canonical item identifier, and the verified query method. Do not retain yesterday's available quantity as today's truth. Even a fresh inventory API reading is evidence of a digital record, not proof of physical shelf contents. The workflow must preserve an inspection requirement where the source process requires one.

A team-level statement does not automatically override a location-specific SOP. “Newer wins” is also insufficient: a newer message can be a suggestion, refer to a different location, or describe a future effective date.

## 5. Proposed architecture and execution flow

### Placement

Proposed new modules, subject to source reconciliation:

- `shared/memory.ts`: versioned records, evidence references, retrieval receipts, and lifecycle transitions.
- `server/memory/service.ts`: the application API and deterministic policy boundary.
- `server/memory/store.ts`: canonical memory storage contract; not another task database.
- `server/memory/retrieval.ts`: authorized exact/text/vector/graph retrieval and token selection.
- `server/memory/evidence.ts`: source revision, location, assurance, and dependency checks.
- `server/memory/consolidation.ts`: dirty-set maintenance orchestration using existing run admission.
- `server/memory/interop/agent-memory-repo.ts`: import, export, validation, and reviewable diffs.

The names are proposed, not claims that these files exist.

### The critical native integration

Use the existing model preparation and validation contract. Retrieval obtains a versioned evidence snapshot in a recorded read step. The subsequent context transform renders those frozen inputs deterministically. If embedding or reranking invokes a provider, that is a separately authorized, funded operation—not a hidden network call inside a step labelled pure.

Bind tenant, principal, access generation, source restrictions, and permitted destination in host code. Revalidate immediately before inference. Preserve the opaque provider transcript; durable memory is not a replacement for provider-specific conversation state. A resumed step uses its recorded evidence and receipts rather than silently searching today's memory and pretending to replay the old request.

When a new action needs current operational truth, perform a newly admitted live read. Replaying a historical result and querying fresh data are distinct operations and must be visibly attributed.

External engines need explicit per-adapter support: bounded file projection, supported context attachment, or scoped memory tools. Do not claim universal coverage merely because an MCP endpoint exists. Test whether each supported engine actually receives and uses the memory, can report omissions, and can safely reset a retained session after access narrows.

## 6. Proposed record contract

The following is a design sketch, not compiled implementation code. Model output proposes content and evidence IDs only. The host supplies authority-bearing fields.

```ts
type MemoryKind = 'fact' | 'preference' | 'episode' | 'procedure_candidate';
type MemoryState = 'candidate' | 'active' | 'disputed' | 'superseded' | 'tombstoned';
type Assurance = 'asserted' | 'source_supported' | 'live_verified' | 'inferred';

interface MemoryRecord {
  schemaVersion: 1;
  id: string;
  revision: number;
  tenantId: string;                  // host-bound, never trusted from a model
  scopeRef: string;                  // person / organization / department / project
  aclPolicyRef: string;
  kind: MemoryKind;
  state: MemoryState;
  assurance: Assurance;
  text: string;
  entityRefs: string[];              // tenant-scoped stable IDs, not display-name joins
  evidenceRefs: string[];
  derivedFromMemoryRevisions: string[];
  validFrom: string | null;          // world-time interval; unknown remains unknown
  validTo: string | null;
  recordedAt: string;                // system-time history
  supersededAt: string | null;
  lastVerifiedAt: string | null;
  refreshPolicyRef: string;
  sourceRestrictionRefs: string[];
  producerRef: string;               // actor/run/model/prompt version as applicable
  retentionPolicyRef: string;
}

interface MemoryReceipt {
  schemaVersion: 1;
  runId: string;
  stepId: string;
  principalRef: string;
  accessEpoch: string;
  snapshotRef: string;
  selected: { id: string; revision: number; evidenceRefs: string[] }[];
  omittedReasons: string[];          // access-controlled; must not leak hidden titles
  sourceRestrictionRefs: string[];
  serializerVersion: string;
  queryPlanVersion: string;
  tokenEstimate: number;
  digest: string;                   // of exactly what was delivered
}
```

An evidence record also needs the source identity, revision/hash, location or structured row/field locator, observation time, original actor type, and the applicable source policy. A hash proves correspondence to bytes, not truth or authorship by itself. Avoid depicting an ordinary SHA-256 chain as a cryptographic signature or a tamperproof audit under unrestricted same-user access.

Typed edges such as `supports`, `contradicts`, `supersedes`, `applies_to`, and `depends_on` require provenance and scope just as nodes do. Never infer business authority from an edge called `approved_by`; link to the actual authorization record and recheck its current status.

### Temporal and contradiction rules

Store the time a fact applies separately from the time Nectovia learned it. An October 8 policy learned on October 6 must not silently govern October 6 work. Preserve the earlier version for historical questions, subject to retention and access controls.

A contradiction creates a conflict group until source semantics resolve it. A manager's new statement can be recorded immediately as that manager's statement without automatically modifying an approved company policy. An expired live verification remains a historical observation, not a current live-verification badge.

## 7. Retrieval without an oversized prompt

The host decides the mandatory retrieval boundary; the model may request more evidence within that boundary.

1. Resolve principal, tenant, workspace, purpose, and current source restrictions.
2. Resolve stable identifiers and the question's temporal frame. Exact IDs take priority over fuzzy entity merging.
3. Search only authorized partitions using exact and full-text retrieval. Add semantic candidates where qualified.
4. Expand relevant typed relationships with access checks at each hop and bounded fan-out.
5. Resolve active versions, conflict groups, and freshness requirements. Request live verification where necessary.
6. Optionally rerank an already-authorized shortlist, with the same data-route checks as generation.
7. Select whole evidence units and their material exceptions, provenance, and uncertainty within budget.
8. Freeze the receipt and deliver lower-trust evidence separately from governing instructions.

A graph traversal that returns a restricted node's title, count, or relationship can leak information even without returning its body. Apply constraints to metadata and debugging output too. The safe visibility of a derived summary is the intersection of its supporting sources' permitted viewers unless it is explicitly recomputed and reviewed from an independently authorized subset.

Do not ingest H18's first-sentence extracts as newly verified facts. Use them to locate original messages. An extract can faithfully quote an early proposal while missing the correction or exception later in the message.

Proposed initial defaults to benchmark, not established optimal settings: 200–500 tokens for a small scoped index; approximately 800–2,000 tokens for ordinary retrieved evidence; at most two relationship hops; a bounded candidate expansion around 40 items. Broader research tasks need a separate higher allowance. Do not truncate a critical qualification merely to hit a cosmetic target.

## 8. Bounded Dreaming inside Nectovia

Implement consolidation as an ordinary admitted maintenance procedure, not an independent all-powerful agent.

**Trigger:** meaningful new source revisions, explicit corrections, verified outcomes, unresolved conflict groups, or a configured maintenance slot. Track dirty topics and source watermarks. No change means no LLM call.

**Read:** obtain only the affected, currently permitted records and bounded neighboring evidence. Reserve maintenance budget and record its payer and route. A source with local-only processing cannot be consolidated by a cloud model merely because the user's foreground model is local.

**Propose:** deduplicate, suggest entity links, identify invalidated dependencies, draft summaries, and identify repeated failure/repair patterns. Preserve original roots of evidence and distinguish inference from explicit fact.

**Check:** validate schema, citations, source visibility, independent supporting episodes, temporal consistency, retained exceptions, and absence of new authority. Repeated retellings of one model claim do not become independent corroboration.

**Commit:** use expected revisions and idempotency keys. A concurrent correction invalidates the stale proposal rather than being overwritten. A policy-authorized, meaning-preserving cleanup can publish automatically; a proposed new procedure or consequential instruction change enters the existing approval/evaluation path. The inspected H10 path requires a person for instruction writes; changing that would be a separate policy decision.

**Observe:** record changed IDs, original evidence, reasons, cost, and rollback/repair status. Return control cleanly on pause, stop, budget exhaustion, provider uncertainty, or lease loss.

A maintenance run must not send customer messages, order products, alter billing, install code, broaden permissions, or move a task to verified completion simply because it inferred those actions would help. It may propose a Board task under the existing task-creation rules.

Keep coordination scratch state in the existing task/run/handoff system. Consolidate verified lessons afterward. Git's line-level conflict behavior is not a semantic conflict resolver and is not an exactly-once business-action mechanism.

## 9. Agent Memory Repo interoperability

Use the release concretely, not just as inspiration:

- Pin and record the upstream spec/skill revision and license in the adoption record.
- Implement import/export compatibility for its entry point, topic entries, and wiki links.
- Produce a readable, authorized view from canonical Nectovia records, with stable IDs/revisions in a sidecar or metadata extension.
- Treat outside edits as candidate changes reviewed against the exported base revision; never as direct policy or database writes.

For a standalone local reference trial, preserve the skill's manual behavior and separate repository. For the integrated product, automatic recall is supplied by Nectovia's host, not falsely attributed to the reference skill.

Repository import must limit file count, size, path depth, and link traversal; refuse path escapes, symlink escapes, submodule surprises, executable hooks, and active remote content. Do not execute saved SQL or scripts. A reusable query becomes a separately admitted capability or reviewed artifact with parameter binding, source schema checks, read-only restrictions where appropriate, and current authorization.

Private Git synchronization is opt-in. One organization-wide Git checkout is not suitable for HR, sales, and operations with different access rights. Default to scoped, current-state projections; historical Git exports may preserve deleted secrets or revoked facts and therefore require an explicit retention/export design.

## 10. Storage, efficiency, and budget

**Local:** introduce a dedicated memory storage adapter; SQLite plus full-text search is a candidate implementation, not a claim about the present run store. Keep the existing file-backed run records as their authority. An optional vector index should be rebuildable. Validate packaging, transactions, locking, and Windows/macOS behavior before selecting a library.

**Business:** extend the existing controlled PostgreSQL/Neon environment for canonical memory records and revisions rather than create a second identity or funding system. Test available extensions, tenant isolation, transaction and backup behavior before choosing a vector backend. Large authorized evidence blobs belong in the approved object/source-storage layer, not casually embedded in every memory row.

**Graph:** begin with relational entity/edge tables. Add a specialized graph backend only after a measured retrieval or operational requirement justifies it. A graph UI can read these tables without requiring a new production graph service.

**Indexes:** exact/text search first; semantic search and reranking behind replaceable providers. Embedding model changes require a versioned parallel index and cutover, not mixing incomparable vector spaces. Switching the answer model alone should not require re-embedding the corpus.

**Cache:** include tenant, principal/visibility, access epoch, source restrictions, snapshot/revision, query plan, and embedding/reranker version. Invalidate on corrections, revocations, source replacement, and deletion—not only on an elapsed timer.

**Scheduling:** bounded per-tenant queues, idempotent dirty-set processing, cancellation, and one owner/lease for a consolidation scope. Yield to foreground work. Do not run an extra large local model or GPU embedding job concurrently by default just to maintain memory.

**Costs:** measure extraction, embedding, retrieval infrastructure, reranking, consolidation, incremental prompt tokens, storage, backup, and egress separately. Foreground generation and maintenance use the existing funding authority. Never equate a successful provider call with promotional-credit coverage.

A simple accounting identity is:

`total memory cost = extraction + embedding + reranking + consolidation + added generation tokens + storage/search/transport`

For illustration, 1,000 runs each receiving 1,200 additional input tokens add 1.2 million input tokens before any other memory work. The dollar amount depends on the actual admitted route. Savings must be measured against the real H18 baseline—not against an imaginary baseline that dumps all history on every turn.

Keep metadata-only analytics: latency, selected-record counts, unsupported claims, corrections, invalidations, maintenance costs, and outcome quality. Exclude memory bodies, raw evidence, sensitive source titles, and embeddings from default analytics, traces, and session replay.

## 11. Privacy, forgetting, and resilience

An explicit full-computer file grant is not permission to remember every file forever or upload it. Memory needs clear source-selection, retention, and egress controls in addition to filesystem access.

A user correction should synchronously invalidate the old active memory and affected caches, even if semantic rebuilding happens later. A forget operation needs to cover raw retained content where applicable, candidates, derived summaries, edges, embeddings, queued maintenance inputs, replica projections, and authorized backup expiration. Preserve the least information required to prevent an obsolete job from recreating the deleted item; do not preserve the sensitive text inside that suppression record.

A database tombstone does not erase external Git clones, previous recipients' copies, or provider state. Make export and backup limitations visible. An access reduction must also retire or sanitize a retained engine session before further inference; removing a file from future retrieval cannot make a model unsee its previous context.

When memory is unavailable, distinguish safe degradation from a required stop. A general question can continue without personalization and disclose that limitation. A source-dependent business commitment must obtain authoritative verification or stop rather than fill the gap from guesswork.

Customer-specific memories must not automatically enter a global learning corpus or another customer's graph. Reusable product improvements require a separate, consented and reviewed process. Memory storage is not implicit permission to train model weights.

## 12. Customer experience

Ship a readable memory inspector before a decorative global graph. Show the retained statement, applicable scope, supporting sources and locations, when it applies, last verification, unresolved conflicts, and recent uses. Offer correction, forgetting, pinning where suitable, and retention/source controls.

Distinguish “read from a source,” “explicitly stated by a person,” “inferred pattern,” and “verified against the current source.” Do not display an uncalibrated model-generated confidence percentage as a reliability guarantee.

A useful task-level receipt says: “Used the warehouse's available-stock definition, then checked today's source record; the supplier preference was remembered from an approved purchasing note.” It does not say “100% certain.”

Keep basic local read/edit/export separate from managed autonomous-maintenance entitlement and inference funding. Existing product decisions govern which workspaces and scheduled features are available; this design introduces no new paid gate or entitlement exception.

## 13. Implementation sequence and acceptance

| Phase | Deliverable | Required proof before advancing |
|---|---|---|
| 0 | Refresh source/branch ownership; define benchmark fixtures and source-of-truth boundaries. | Baseline behavior measured; no duplicate memory/runtime effort introduced. |
| 1 | Versioned ledger, scope, evidence, corrections, deletion, and basic inspector. | Cross-tenant and revocation tests; crash recovery; no fabricated source or authority. |
| 2 | Exact/full-text recall and immutable context receipts through native preparation. | Proven delivery, omission accounting, original transcript preserved, no hidden network/cost. |
| 3 | Scoped external-engine adapters and Agent Memory Repo import/export. | Actual round-trip and per-engine receipt/retirement checks; hostile imports refused. |
| 4 | Candidate capture from original evidence and verified outcomes. | Corrections retained; model claims never upgraded to physical/business truth by themselves. |
| 5 | Bounded dirty-set consolidation via existing Automations and guidance review. | Idempotency, stale-base refusal, source-ACL recheck, pause/stop, budget, and rollback proof. |
| 6 | Temporal relationships, optional embeddings/reranking, and a scoped graph explorer. | Paired evaluation demonstrates benefit over simpler retrieval within an explicit cost envelope. |

Start with synthetic tenant fixtures and shadow evaluation. Use limited opt-in rollout only after the security and deletion boundaries pass. A review document, successful mock, or one provider call is not packaged-platform or production acceptance.

### Evaluation protocol

Compare the same Nectovia harness and task distribution under: current context only; portable linked notes; native exact/text evidence retrieval; hybrid graph/semantic retrieval; and hybrid retrieval with consolidation. Keep models, question chronology, tool permissions, budgets, and source snapshots controlled. Include at least a small local model, a lower-cost hosted model, and a strong reference model permitted for synthetic data.

Use held-out business scenarios and corrections, repeat stochastic runs, and report paired uncertainty rather than a single flattering score. Measure answer correctness, unsupported assertion rate, citation validity and entailment, temporal accuracy, correction persistence, retrieval recall, task outcomes, action safety, latency, and end-to-end cost.

Zero observed cross-tenant exposure, unauthorized promotion, or forbidden-route calls is a release gate on the tested suite, not a proof that every possible production input is safe. Evaluate abstention on genuinely unanswerable questions so refusal cannot be used to game accuracy.
