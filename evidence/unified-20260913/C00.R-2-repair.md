## 1. C00-R2-1 — an unauthorized release no longer ends a legacy claim

### What was wrong

`legacyActiveClaims` decided a claim was over by **file name alone**:

```ts
const released = new Set(
  names.filter((n) => n.endsWith('.released.json')).map((n) => n.slice(0, -'.released.json'.length)),
);
...
if (released.has(claimId) || (await exists(attemptFile(layout, claimId)))) continue;
```

It never read the release, so it never checked the releaser's identity, process lifetime, host,
worktree or integrator reason. A correct `authoritative()` predicate already existed in the same
file, but `releaseOf` and `releaseClaim` both applied it behind a `!ordered` short-circuit, so it
protected *ordered* claims only. An unauthorized record already on disk therefore ended a legacy
claim permanently, and survived the retirement of the old executables.

### The repair

The `ordered` exemption is **removed, not narrowed**. `releaseOf` no longer takes the parameter, so
no call site can reintroduce the bypass:

```ts
async function releaseOf(layout: Layout, claim: Claim): Promise<ClaimRelease | null> {
  const recorded = await readJson<ClaimRelease>(releaseFile(layout, claim.claimId));
  if (authoritative(recorded, claim)) return recorded;
  const later = await readJson<ClaimRelease>(releaseRecordFile(layout, claim.claimId));
  return authoritative(later, claim) ? later : null;
}
```

`legacyActiveClaims` is now expressed in terms of that one judgment instead of duplicating
release-reading with a name `Set` — the duplicate implementation *was* the vulnerability:

```ts
if (await exists(attemptFile(layout, claimId))) continue;
const claim = await readJson<Claim>(path.join(layout.claims, name));
if (claim && !(await releaseOf(layout, claim))) claims.push(claim);
```

`releaseClaim` drops the same short-circuit in both places, which also gives legacy claims the
recovery ordered claims already had: when `<id>.released.json` is held by a record without
authority, the holder or the integrator still ends the claim, recorded at
`claims/releases/<id>.json`. An unauthorized record can no longer make a claim unreleasable.

Ambiguous legacy claims are therefore **retained**, not grandfathered, until an authoritative
release ends them — which is the conservative branch the reviewer asked for.

## 2. The launch-failure fallthrough

### What was wrong

`processStartOf` spawns a shell to read `Win32_Process.CreationDate`, and fell through to the
second shell for `ENOENT` only:

```ts
} catch (error) {
  if (errorCode(error) === 'ENOENT') continue;
  throw error;
}
```

A sandbox that forbids the spawn does not report `ENOENT`. `C00.R-2` dispatches 1 and 2 both died
on a raw `spawn EPERM` escaping this line, before any review work began.

### The repair

Any failure to *run* the shell is now a reason to try the next one and, if both refuse, to raise
the actionable guidance instead of the raw error. Output that did arrive is still judged: an
unreadable value remains an integrity error and still throws. The message names each shell and why
it refused, so the condition is diagnosable rather than silent:

```ts
refusals.push(`${shell} ${describeRefusal(error)}`);
continue;
```

### A/B proof against the reviewed candidate

Both shells shadowed by an unlaunchable `pwsh.exe`/`powershell.exe` that fails **`EFTYPE`** — a
non-`ENOENT` launch failure of the same class as the sandbox's `EPERM`. `OLD` is loaded from the
Git bytes of `b750406`:

```
=== OLD (candidate b750406) ===
threw, error.code = EFTYPE
message: spawn EFTYPE
actionable (names --start): NO — raw spawn failure escaped

=== NEW (repaired) ===
threw, error.code = undefined
message: Neither pwsh.exe nor powershell.exe can report process start times
         (pwsh.exe failed with EFTYPE; powershell.exe failed with EFTYPE); pass --start
         with the time the process started, taken from the launch record of the process itself.
actionable (names --start): YES
```

Launch-failure classes observed on this host, confirming `ENOENT` was the wrong sole test:

```
empty file             -> code=EFTYPE   isENOENT=false
text with .exe name    -> code=UNKNOWN  isENOENT=false
directory              -> code=ENOENT   isENOENT=true
```

The ordinary path is unchanged: `processStartOf(37844)` returns
`2026-09-16T03:32:18.4881660Z`, byte-identical to the value captured from the process's own launch
record, and an absent pid still returns `null` rather than throwing.
