TRUST CLARIFICATIONS
An egress grant authorizes sending a particular input to a particular provider; it does not approve the provider's proposed file changes. Exact write approval is a separate decision. Revocation blocks future authority; it cannot unsend an already dispatched request or guarantee cancellation of provider charges.
A worktree isolates edits, not operating-system access. A sandbox policy echo is not an outbound-network probe. Keep enforced / observed / instructional / unsupported guarantees distinct. A read-only provider step can still transmit private data and consume quota; effect: read is not a reason for automatic retries after ambiguous dispatch.
Local-first use does not require a cloud account, and paired remote access need not automatically require one. Opus's optional online-account track is actively authorized rather than deferred by older sequencing. Prefer standards-based passkeys and system-browser Authorization Code + PKCE, with explicit recovery/revocation design subject to the research decision. Local/offline operation must remain viable. Hardware-backed keys are a compatibility/assurance decision; Windows DPAPI-backed safeStorage does not protect against arbitrary malicious code running as the same user. Encrypted storage, credential brokering, process isolation and authentication remain distinct controls.
Preserve renderer isolation, narrow validated IPC, safe navigation, content sanitization and server-side authorization. Prompts and model output are not authorization. Logs, traces, receipts, packages and roadmap exports must not contain credentials. Broader client use still waits for tenant-scoped files, search, memory, events, credentials, delegation, retention/offboarding and recovery.

SEPTEMBER 9, 2026 — AGENT/HARNESS NORTH-STAR CLARIFICATION
This amendment records Andrew’s latest strategic direction and supersedes narrower language where it could imply that Diomedes is merely a wrapper, passive control plane, model picker, or external-agent launcher. It does not authorize broad implementation work out of sequence. The verified Runtime/Trust checkpoints above remain the immediate execution authority until deliberately reconciled.
PRODUCT IDENTITY — AN AGENT WITH ITS OWN HARNESS
Diomedes is intended to become a true general-purpose agent with its own universal harness/runtime and human workspace. The long-term default experience is Diomedes-led: the user describes an outcome, and the native Diomedes agent owns the operational loop around that outcome — understanding intent, assembling context, selecting an execution approach, routing to appropriate models/runtimes, invoking tools and skills, delegating bounded work, monitoring progress, reacting to failures or rule triggers, requesting human authority where required, verifying outputs, recording evidence, and preserving durable work state.
“Native Diomedes agent” means Diomedes owns the agent loop and operational semantics. It does not require a proprietary Diomedes foundation model. Reasoning may be supplied by a user-selected subscription-backed model, API model, local model, specialist runtime, or future Diomedes-hosted route. External models are cognition/execution resources participating in Diomedes, not owners of the project or operation.
Direct-agent use remains a first-class path. A user may deliberately work through Codex, Claude Code, OpenCode, Hermes, another supported agent, or a local runtime inside Diomedes. Diomedes should preserve useful native runtime capabilities while still owning the surrounding project state, rules, permissions, evidence, history, routing and coordination that the integration can truthfully enforce. Never claim identical interception or control guarantees across integrations that expose different capabilities.
The preferred long-term mental model is closer to Devin-style outcome ownership than to a model picker or GUI wrapper: tell Diomedes what needs doing, and Diomedes manages the work. External agents and models may perform substantial reasoning or execution, but the durable operation remains Diomedes.

Study Devin for outcome ownership, persistent work/session state, delegation, progress monitoring, supervised execution environments, and the user’s ability to inspect or take over work.
Study Hermes for general-purpose personal-agent behavior, durable continuity, memory, skills, schedules, messaging surfaces, multiple execution backends, and a model-agnostic assistant experience useful outside software engineering.
Study OMP for layered rules/context, triggered corrective intervention, stream-time regex/pattern interception where supported, tool reliability, standardized execution behavior, capability-aware provider adaptation, and explicit rule injection rather than one monolithic prompt.
Study both unrelated oh-my-hermes projects separately and disambiguate them by repository:
• witt3rd/oh-my-hermes — planning discipline, research/interview/planning composition, verified execution/iterate loops, and Hermes hook/plugin role/context injection patterns.
• rlaope/oh-my-hermes — routing natural-language requests into explicit capabilities, playbooks/workflows, executor-neutral handoffs, and evidence/approval/quality gates with prepared-versus-observed truthfulness.
These projects are design and implementation references, not competing authorities. Do not stack complete OMP/OMH/Hermes orchestrators inside Diomedes and create multiple owners of routing, state, policy or execution. Reuse patterns or bounded components only where they strengthen Diomedes-owned semantics.
RULE SYSTEM — A DEFINING DIOMEDES CAPABILITY
The layered rules system should become one of Diomedes’ defining differentiators. Preserve and expand the OMP-like work already started, including regex/pattern-triggered corrective behavior where technically supported, but distinguish three different rule classes:
1. Standing guidance — durable contextual instructions, user/project/business conventions, preferences, procedures and retrieved rules that shape reasoning.
2. Triggered correction — detectable output/tool/state patterns that can interrupt, redirect, inject targeted guidance, retry within bounded policy, or require review. Regex and stream-time matching are useful mechanisms but not the whole rule system.
3. Enforced policy — pre-action authority and safety boundaries that decide whether an operation may happen at all: data egress, credential use, external publishing/sending, destructive effects, budget/resource boundaries, restricted resources, client scope and exact approvals.
Never claim a prompt, regex or after-the-fact observation enforces a boundary that must be checked before an external effect. A rule should record what surface it actually governs: advisory context, generation correction, tool-call interception, pre-effect authorization, postcondition verification, or another explicit control point.
Normal users should be able to express rules in ordinary language. Diomedes may translate those requests into a proposed structured rule/capability configuration and explain what is advisory versus enforceable. Technical users may inspect and edit lower-level triggers, regex, precedence, scopes, hooks and evidence. Interface detail must not change the underlying authority model.
TOOL-CALL STANDARDIZATION — COMMON CONTRACT, NATIVE CAPABILITIES PRESERVED
Diomedes should standardize tool behavior without reducing every runtime to the lowest common denominator. Diomedes-owned operations should converge on a typed execution envelope that can answer: who/what requested the operation; which project/task/thread/worker it belongs to; what resource and action are targeted; what arguments/schema are valid; what authority/capability grant is required; whether external effects are possible; what outcome occurred; and what evidence proves it.
Provider/agent adapters translate that common Diomedes operation into the native tool protocol of the selected runtime and normalize results/errors/events back into Diomedes. Preserve runtime-specific strengths such as reasoning controls, sandbox modes, provider routing, context controls, local-model resource parameters, or specialist capabilities when available.
Routing should be capability-aware. A task requiring enforced pre-send approval must not be routed through an integration that only reports actions after completion. A runtime with unrestricted shell/browser access may invalidate narrower tool-level guarantees; claimed control must match the real execution environment.
DIOMEDES-LED EXECUTION VS DIRECT-AGENT EXECUTION
Support two coherent execution arrangements over the same durable workspace:
• Diomedes-led — the native Diomedes agent owns the loop and calls models, tools, skills and external agents as resources/workers.
• Direct-agent — the user deliberately chooses an external agent/runtime as the primary reasoner/executor for a thread or task while Diomedes retains the surrounding durable state and whatever policy/interception guarantees that adapter can actually provide.
Thread, Board and Team remain views of the same durable work object under both arrangements. Do not create separate project silos for native versus external execution.
AUDIENCE AND UX — UNIVERSAL CORE, ACCESSIBLE DEFAULT
Primary near/mid-term audiences are personal users, power users who want one coherent agent environment, and small/local businesses. Enterprise-scale administration is not the initial target, though architecture should avoid choices that make later tenant/organization expansion impossible.
Do not design the default experience for hardcore programmers. Programming depth, raw logs, runtime controls, rule inspectors, tool traces, local-model tuning and developer surfaces should be available to users who want them, but they should not be mandatory for ordinary operation.
Separate three independent concerns:
• Experience level — how much implementation detail the interface exposes.
• Workspace purpose — personal, business, software, research, content or another domain.
• Authority — what actions/data/resources the agent is permitted to use.
Changing Guided/Standard/Technical presentation must never implicitly grant more authority. Guided should reveal less machinery, not become a visually different watered-down product. Preserve the approved Field visual language across all levels.
GENERAL-PURPOSE AGENT, NOT SOFTWARE-ONLY
Diomedes should learn from coding harnesses without becoming a coding-only product. The same durable agent/harness should be able to coordinate software work, research, documents, browser tasks, personal workflows, business operations, integrations and local/remote tools. Software engineering is a demanding proof domain, not the definition of the product.
LEARNING AND SELF-IMPROVEMENT
Keep separate but interoperable concepts for user memory/preferences; workspace/business knowledge; reusable procedures/skills; behavioral rules/policies; and observable evidence about which approaches succeed. Do not collapse these into one giant memory file or allow learned preference to become authorization.
Preferred improvement loop: observed problem or human correction → proposed change to rule/skill/prompt/routing/workflow → replay/evaluation against relevant stored cases → compare quality/cost/latency/failure/corrections → human or policy approval where appropriate → versioned adoption → continued monitoring and rollback capability.
The system may learn that a deterministic calculation or stable procedure should replace repeated model reasoning. It may not silently expand data access, billing class, tenant scope, credential access, or approval authority merely because the user frequently approves something.
DEMONSTRATION-TO-AUTOMATION REINFORCEMENT
The recorder/teach-by-demonstration path remains strategic. A recorded human workflow should not merely become prose instructions. Desired result: semantic understanding of the demonstration → extract stable deterministic operations where possible → retain semantic/visual reasoning only where necessary → use generative steps only where necessary → define approval boundaries → define verification → package as a reusable, inspectable capability/workflow → test/version/publish as appropriate.
COMMERCIAL THESIS — SELL RESPONSIBILITY FOR OUTCOMES, NOT MODEL ACCESS
The Devin-like direction creates a stronger long-term revenue hypothesis than selling a model picker or generic chat frontend. The commercial product is a configured Diomedes system that can take responsibility for recurring work within explicit boundaries, produce inspectable results/evidence, and improve with measured use.
Potential commercial layers remain: personal software; configured business deployments; consulting/audits/pilots/implementation; Managed Diomedes support; optional customer-hosted local/remote workers; and later provider-authorized hosted Diomedes execution where economics and terms support it. Managed service does not require Diomedes Systems to pay for every customer’s compute; customer-owned hardware can remain a first-class deployment model.
Do not treat user-owned subscription access as resale inventory. Subscription-native routes are user-authorized execution options where provider terms permit. Commercial hosted/model offerings require provider-authorized commercial/API arrangements.
For early businesses, the visible value should be that the operation gets done with less coordination burden — not that multiple models participated. Lead with outcomes, approvals, evidence and continuity.
UNIFIED DIOMEDES PRODUCT / MODEL / COMMERCIAL SYSTEM — SEPTEMBER 9, 2026
Use the following naming and responsibility model across product, implementation, business and future-model discussions so that “Diomedes,” “Core,” “Agent,” external agents and hosted inference do not drift into conflicting meanings.
Diomedes Desktop — one primary downloadable client and human workspace. Personal, Pro and Business experiences should normally be entitlement/workspace modes of the same product rather than separate binaries. Thread, Board and Team remain views of the same durable work.
Diomedes Core — the Diomedes-owned harness/agent-semantics layer: model and agent routing, context/rules, capabilities/skills, memory, delegation behavior, profiles, learning interfaces and native agent semantics. The separately defined Diomedes Runtime remains the durable execution authority for admission, state, events, approvals, recovery, queues, budgets and effects. “Core” is not permission to collapse those authority boundaries.
Diomedes Agent — the customer-facing paid supervisory intelligence built on Core and Runtime. At the paid tier, Diomedes should act as the rigorous primary operational brain: understand the objective, form and revise a plan, choose models/agents/capabilities, distribute tasks, establish relevant context and constraints, monitor workers, intervene when evidence or rules require it, control budgets, request human authority, verify outcomes and synthesize the result. The value being sold is this Diomedes-owned orchestration and responsibility model, not mere access to whichever foundation model supplies reasoning underneath it.
The Diomedes Agent does not require proprietary Diomedes model weights at launch. Initially its cognition may come from a selected external API model, approved subscription-backed route, local model or other interchangeable route while Diomedes owns the loop, policies, state and evaluation. BYOK or customer-supplied inference therefore does not inherently make the paid Diomedes Agent free; the software fee and inference source are separate commercial concepts.
Direct-agent mode remains first-class. Astra, Codex, Claude Code, OpenCode, Hermes and other supported agents may still be deliberately selected as the primary reasoner/executor for a task or thread. In Diomedes-led mode they may instead be specialist workers/resources delegated to by the Diomedes Agent. Do not represent an external runtime as being under stronger Diomedes control than its adapter and execution environment actually permit.
MODEL EVOLUTION — BEHAVIOR FIRST, WEIGHTS LATER
Phase A: establish Diomedes supervisory behavior through Core/Runtime semantics, layered rules, routing, delegation, verification and evals while using interchangeable existing models. Compare routes empirically and avoid provider lock-in.
Phase B: use Observatory evidence to accumulate privacy-appropriate state → decision → outcome examples: decomposition choices, worker selection, context supplied, cost/latency, retries, corrections, verification results and human feedback. Do not collect hidden chain-of-thought or convert client data into training data without explicit lawful permission and a defined policy.
Phase C: only when enough evidence and economics justify it, evaluate fine-tuning, distillation or training of a specialized Diomedes Supervisor model. Its target specialty is orchestration — decomposition, routing, delegation, monitoring, cost/quality tradeoffs, approval recognition and verification — rather than competing immediately with frontier foundation models at every task. The supervisor can remain relatively small/efficient and delegate difficult work to stronger specialists. A future proprietary/hosted model is an implementation option beneath Diomedes Agent, not the definition of Diomedes Agent.
Phase D: optional managed inference and remote/cloud workers may use provider-authorized commercial APIs or rented/serverless GPU infrastructure when measured demand, reliability and unit economics justify it. This must remain separable from local/BYOK routes and must not silently change a user’s billing class or authority.

SCOPE CONTROL — UNIVERSAL NORTH STAR, NARROW PROOF SLICES
The architecture is intentionally broad, but the implementation strategy must remain narrow and sequential. “Universal harness” describes the responsibility model and long-term direction, not a requirement to implement every model, workflow, business integration, remote system, rule type and agent capability before shipping anything useful.
Do not open parallel implementation tracks merely because this amendment names them. Preserve the current verified Runtime/Trust critical path and extend it in the smallest slices that prove the universal architecture.
A strong future proof milestone, when prerequisites are ready, is one genuine Diomedes-led workflow in which the native loop uses a real model route, invokes typed Diomedes tools, encounters a triggered rule/correction, crosses an exact approval boundary, survives an interruption/restart, verifies its result, and records evidence/history. Then prove the same workflow or contract with a second supported model route without rewriting its durable semantics. Separately test an external-agent route and document exactly which Diomedes controls are enforceable, advisory or unavailable through that integration.
The goal is not to build six products at once. The goal is to prove one durable architecture repeatedly across increasingly broad tasks.

NORTH STAR
Diomedes is not merely a chatbot, GUI wrapper, workflow builder, or business-automation shell. It is intended to become a genuine model-agnostic agent harness/runtime and human workspace with a polished Windows-first GUI.
The long-term product combines:
• a crisp desktop workspace for ordinary and technical users;
• native Diomedes-owned runtime behavior rather than depending forever on another harness for core semantics;
• external coding/agent engines where useful;
• cloud, subscription-native, BYO-API, and local model routes;
• durable task/work state;
• deterministic workflows plus agent reasoning;
• strong permissions, approvals, evidence, and recovery;
• projects, documents, history, skills/capabilities, memory, rules, and evidence-grounded self-improvement;
• remote control and eventually portable execution;
• business/client workspaces using the same core;
• consulting as an early commercial discovery and delivery layer.
A model or external agent is a participant in Diomedes Runtime, not the runtime itself.
PRODUCT PRINCIPLES
1. Local-first, no forced cloud account. Core personal/local use should work without creating an online Diomedes account. An online account becomes appropriate for multi-device identity, remote/cloud services, sync, teams, Business, and hosted services.
2. Human authority where consequences matter. Approval must bind to the exact action being approved.
3. Capability honesty. Steer, queue, interrupt, cancel, undo, restore, restart, resume, retry, and reconcile are different operations and must be represented truthfully.
4. No hidden fallback that changes cost or authority. Local routes do not silently become paid cloud routes; subscription-native does not silently become API-key billing.
5. Evidence before “done.” Completion should be backed by appropriate observable proof.
6. Performance is product quality. Startup time, memory, CPU, first-token latency, long-session behavior, rendering, process cleanup, local-model lifecycle, reconnect time, and event-log growth are acceptance criteria.
7. The product remains GUI-first. Technical depth may exist, but core power should not require living in a TUI.

IDENTITY & TRUST V1
Security is not a later login screen. It is part of the runtime model.
Identity classes:
• Local Principal — local human owner; core use works without cloud account.
• Diomedes Account — optional online identity for multi-device/cloud/team/hosted features; prefer passkey-first rather than inventing a password-centric system.
• Organization / Business Tenant — business/client identity separate from the personal account.
• Device Principal — every trusted desktop/phone/laptop has its own independently revocable identity/key.
• Agent / Workflow Principal — agents receive explicit delegated capabilities for bounded work rather than implicitly becoming the user.
Local device identity should eventually create a local principal ID, device ID, device key pair, and assurance record describing private-key protection. On Windows, prefer non-exportable OS/hardware-backed key protection where available, with a documented fallback.
Never place private device keys, provider tokens, OAuth refresh tokens, or high-value secrets in prompts, transcripts, logs, ordinary project JSON, or crash reports.
Authentication is not authorization. A session proves who/device identity; every consequential request still receives server-side authorization against capability/resource scope.
Roles may exist for business UX, but underlying enforcement should be capability/resource scoped and deny by default when authority is absent or ambiguous.
A durable run should eventually record human requester, originating device, delegated agent/workflow identity, project/resource scope, granted capabilities, policy version, and expiration/budget where applicable.
Credential broker principle: agents get capability, not raw secrets. Agent requests a typed authenticated operation; Diomedes verifies policy/grant; broker resolves secret internally; adapter performs request; agent receives sanitized result/evidence. Provider account aliases and route metadata remain separate from secrets.
Step-up verification should be available for especially sensitive operations such as pairing a new device, changing account recovery/authentication settings, granting high-risk capabilities, or approving destructive/consequential actions.
Remote pairing should retain and strengthen the September 5 proposal: one-time pairing challenge/QR from an already trusted host/device, new device proves its own key, approval on an existing trusted surface, explicitly scoped grants, short-lived sessions, immediate revocation, terminal/high-risk rights off by default, and server-side metadata filtering.
Business tenant isolation must apply to files, search, memory, embeddings, history, private skills, events, credentials, agents, and workflows. Client-supplied tenant IDs are never trusted as authorization. Credentials are namespaced by client/environment. Offboarding/revocation must be testable.
Supply-chain trust matters because Diomedes may eventually install or execute skills, MCP servers/apps, plugins, adapters, models, updates, and workflow packages. Plan toward signed/trusted packages plus capability manifests covering network destinations, file access, secret aliases, process execution, remote-control privileges, UI embedding, and external effects. Diomedes application updates must be signed before serious public distribution.
Security invariant for every consequential action:
1. Who requested it?
2. From which trusted device/session?
3. Which agent/workflow acted on the user’s behalf?
4. Under what delegated capability/policy?
5. Against which resource/client scope?
6. What evidence proves what actually happened?
DURABLE EVENTS, APPROVALS, AND EXTERNAL EFFECTS
The September 5 replan already proposed append-only events, replay cursors, device pairing/grants, exact approval binding, and OS-keyring storage. Preserve those ideas, but implement them against the now-real September 8 runtime rather than creating parallel systems.
Representative event concepts may include COMMAND_ADMITTED, RUN_STARTED, MODEL_STARTED, TOOL_REQUESTED, TOOL_COMPLETED, NEED_CREATED, APPROVAL_DECIDED, WRITE_PREPARED, WRITE_APPLIED, ARTIFACT_CREATED, EXTERNAL_EFFECT_PREPARED, EXTERNAL_EFFECT_UNCERTAIN, EXTERNAL_EFFECT_CONFIRMED, RUN_COMPLETED. Actual vocabulary should follow the domain model and remain compact.
Exact approval means: this authenticated actor approved exactly this action against exactly this expected base state before expiry. Changed action, changed arguments, stale revision, expired approval, conflicting decision, and lost response must reconcile deterministically.
Uncertain external effects: a timeout after dispatch does not prove failure. Future email/post/form/service/business actions need durable states such as prepared, dispatching, confirmed, uncertain, reconciling, failed. Never blindly replay a consequential uncertain effect where reconciliation is possible.
